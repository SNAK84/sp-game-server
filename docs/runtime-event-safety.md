# Защита PlayerQueue и таймеров игрового цикла

## Причина сбоя 21.10.2026

Исходный маршрут занимал 761 байт, а старый `PlayerQueue.data` — 512.
После обрезания `unserialize()` возвращал `false`. Вызов
`FleetBattleService::assertPlayerMutation(..., false)` из EventLoop приводил
к необработанному TypeError. В core dump сохранён именно этот PHP fatal error.
Последующий SIGSEGV произошёл внутри Swoole 5.1.6 при создании coroutine для
`WSocket::onClose`: `EG(current_execute_data)` уже был null.

Первое исправление увеличивало буфер до 16384 байт и проверяло длину до
постановки. Теперь размер основной строки возвращён к 512 байтам, а большие
данные вынесены в отдельный ограниченный буфер (см. ниже). Защита от
повреждённых событий и исключений сохранена; native extension не меняется.

## Поведение

- `PlayerQueue::getByAccount()` и `popByAccount()` используют общую проверку
  serialized payload. Разрешён массив скаляров/массивов, включая пустой массив.
  Объекты не восстанавливаются (`allowed_classes=false`), вложенные объекты
  также отклоняются; глубина ограничена 64, рекурсивные структуры отклоняются.
- Обрезанные/повреждённые данные не заменяются на `[]` и не исполняются.
  Ошибочное событие удаляется из runtime-очереди с error log: ID, account/user,
  planet, action, число байт и причина. Сам payload в этот лог не записывается.
  Повторного выполнения или бесконечного повторения одной записи нет.
- Временный error handler декодирования восстанавливается через finally.
- EventLoop изолирует ошибку одного игрового события: пишет контекст и Throwable,
  отклоняет ещё не удалённое событие и продолжает соседние. Если ошибка возникла
  уже после удаления исполненного события, оно не восстанавливается и не
  исполняется повторно. Штатные LogicException guard-проверок сохранены.
- Каждый зарегистрированный Timer callback перехватывает Throwable. Следующие
  tick и соседние таймеры продолжают работу. При ошибке Logger используется
  системный `error_log` как запасной канал.

Это не универсальный rollback, не reliable delivery и не изменение механики
игровых действий. Атомарность мутаций по-прежнему обеспечивают конкретные
обработчики. При неожиданном исключении действие считается неуспешным и не
повторяется автоматически: повтор частично исполненной команды опасен.
Содержимое отклонённых событий не архивируется; в логах остаются их метаданные
и причина отклонения.

## Проверки

```bash
docker exec -w /var/www/html swoole_app sh -c 'ulimit -c 0; exec php tests/PlayerQueueSafetySwooleTest.php'
```

12 проверок на отдельных настоящих Swoole Tables, SQL запрещён fixture:
корректные payload/порядок/pop; обрезание 512 байт без gameplay-мутации;
неверный корневой тип/объекты/рекурсия/глубина; восстановление error handler;
настоящий TypeError из игрового обработчика; RuntimeException/Error;
ошибка после удаления исполненного события; штатный guard боя; исчезнувшая
планета; исключения в настоящих coroutine Timer и сбой Logger.
Искусственные failures не отправляются в работающий игровой сервер; core dump
исходного сбоя не изменяется. Ожидаемая строка CRITICAL в тесте Logger относится
только к проверке fallback, а не к ошибке живого сервера.

Файлы: `src/Game/Repositories/PlayerQueue.php`,
`src/Game/Services/EventLoop.php`, `tests/PlayerQueueSafetySwooleTest.php`,
`docs/runtime-event-safety.md`. Клиент, WSocket, игровые mission handlers,
RepositorySaver, SQL-схемы и версия Swoole не изменяются.

## Ограниченный буфер больших событий

`PlayerQueue.data` снова содержит максимум 512 байт. Маленькое событие остаётся
inline. Для большого события `PlayerQueuePayloads` хранит весь serialized
payload, а строка очереди — только `['_payloadId' => queueId]`.
Это относится также к большим запросам обычных миссий, не только к редактору.
Клиент продолжает отправлять полный план одним запросом, без нового протокола.

- Буфер создаётся из `PlayerQueue::init()` до запуска WebSocket workers.
  Данные и mutex общие для процессов; это не PHP-массив отдельного worker.
- Лимиты: 1024 больших события глобально, 4 на аккаунт, 16384 байта на событие.
  Большие данные резервируются только на эти 1024 слота, а не на все 16384
  строки PlayerQueue. Буфер имеет полный резерв hash-коллизий; основная Table
  буфера занимает около 32 МиБ плюс служебные поля и небольшая таблица квот.
  Изолированный замер shared mappings на Swoole 5.1.6: основная очередь
  13.25 МиБ, буфер с квотами 32.586 МиБ, суммарно 45.836 МиБ вместо примерно
  311 МиБ основной очереди с полем 16 КиБ. Неизменённые индексы и другие
  repositories сюда не включены; это резерв памяти, не замер resident RAM.
- Квоты и операции буфера защищены общим mutex. Внутри него нет SQL, игровых
  действий или coroutine-await. Ожидание mutex ограничено одной секундой:
  зависший держатель не блокирует процесс навсегда; при timeout запрос получает
  штатный отказ. Обычные inline-события не захватывают mutex при удалении.
  Ошибка периодической очистки логируется, но не прерывает обработку мира.
  Заполненный буфер отклоняет новый запрос до
  записи ссылки и до изменений маршрута/ресурсов. Размер проверяется до ID.
- Payload привязан к ID события, account, user, planet и action. Ссылку на
  payload другого события нельзя прочитать или использовать для его удаления.
- `getByAccount()` восстанавливает прежний формат `data` до вызова обработчика.
  Чтение не потребляет данные: его используют также предварительные проверки.
  `delete()`/`popByAccount()` освобождают и ссылку, и payload, и квоту.
- Неуспешный enqueue откатывает новую строку и освобождает payload. Проверяется
  фактическая запись строки и доступность через account index, не только
  возвращённый `BaseRepository::add()` ID. До проверки строка имеет `ready=0`
  и пропускается читателем; последняя атомарная запись публикует `ready=1`.
  Это исключает получение события EventLoop между записью и её проверкой.
- TTL — 120 секунд с момента помещения в буфер. EventLoop раз в 5 секунд
  удаляет просроченные payload и связанные ссылки, в том числе offline-игроков.
  При чтении срок проверяется независимо от периодической очистки. Маленькие
  события под этот TTL не попадают. Просроченный план не исполняется позднее.
- Отсутствующий/повреждённый payload отклоняется до gameplay и логируется без
  тела данных. При отказе игрового обработчика payload также освобождается.
- Составной маршрут не разбит на независимые игровые действия: по-прежнему
  проверяется целиком в `preparePlan()`, повторно проверяется версия в EventLoop
  и применяется через прежний `FleetControlService::commit()` с rollback.

Буфер намеренно временный: после рестарта он теряется вместе с PlayerQueue.
Это не исправление persistence/reliable delivery. ACK означает приём события,
а не успешное выполнение; истечение TTL не вводит отдельный command-result API.

```bash
docker exec -w /var/www/html swoole_app sh -c 'ulimit -c 0; exec php tests/PlayerQueuePayloadsSwooleTest.php'
```

Изолированные native проверки покрывают полный 12-этапный путь
PageAction → PlayerQueue → EventLoop, корреляцию ACK/error, inline/reference
roundtrip, TTL, отсутствующие/повреждённые/чужие ссылки, оба лимита буфера,
два отдельных процесса, граничный размер, неуспешную запись строки/индекса,
rollback игрового commit и успешный повтор. SQL запрещён fixture.
Ожидаемые WARNING про короткие колонки в двух failure-injection сценариях
относятся только к новым Tables тестового процесса, не к работающему серверу.

Проверка через реальную SPA 21.10.2026: тестовый `snak1`, флот #3, 12 этапов
у домашней планеты, без груза и погрузки топлива. Клиент отправил 1830 байт JSON
данных; в PlayerQueue сохранена ссылка 28 байт. ACK `status=ok` сопоставлен с
исходным requestId, последующий `ActualData` применён, requestCallbacks=0.
Диалог закрылся (его скрытый DOM сохраняется по текущему lifecycle клиента).
После полного reload флот у базы, груз и топливо нулевые. В работающий сервер
failure-injection не отправлялся.
