# B015 — прогноз возврата после потери ресурсной базы

Исправлено01.11.2026. Изменены только backend-проекции; клиент, execution,
топливные формулы, MySQL-схема и формат полей WebSocket не переписывались.

## Причина и исправление

После потери дома ResourceBaseService уже назначает резервную планету/луну.
Pending-команды неявного возврата ещё сохраняют прежний homeSiteId и target.
activateNextCommand при достижении такого хвоста штатно заменяет его через
commitRecallReturn/buildReturn. Но FleetsPage рассчитывала прежний хвост,
а FleetPlanService::steps представляла его как самостоятельный move.

Теперь buildFlightCommandProjection распознаёт тот же pending homeSiteId,
отличный от текущей приписки, и **только в локальной копии** строит buildReturn
из будущей точки курсора к ResourceBaseService::homeCoordinate. Timer,
commands и route_progress получают один хвост. Steps выдаёт один return.
У будущих несохранённых строк используются стабильные отрицательные view-keys;
они не являются реальными ID FleetCommands и не поступают в исполнение/редактор.
Сохранённые ID/enum и контрольная version реальной очереди не меняются.

Active/completed и явная цель без homeSiteId не перенаправляются. Уже неизвестное
расписание (пауза, активная добыча и другие прежние причины) не превращается
в обещание точного времени. Недоступная база проходит прежний обработчик ошибки
прогноза. Реальные команды, резерв топлива и авторизацию эта read-модель не меняет.

## Живой основной сервер и SPA

Подготовлен контролируемый **post-loss checkpoint**, не второй игровой мир:
QA qaown_260924, owner9, новая сцена Fleet128/129 с отдельными именами
`QA B015 implicit`/`QA B015 explicit`, по одному малому транспорту с XP7.
Home26/[1:6:2], утраченный site19/[1:7:3] уже свободен. У обоих активная MOVE
к26, затем UNLOAD17M/11C/5D. Только implicit имеет homeSiteId19 в старом хвосте;
у explicit цель19 задана без такой отметки.

Подготовка выполняется SQL-миграцией лишь при остановленном main, с guard точных
QA, планеты, свободного site19, состояния очереди и отсутствия новых имён.
Шаблоны Fleet122 и его состава только читаются. Их строки не изменялись.
Начальный активный участок и списанные ранее50 топлива заданы checkpoint,
а не рассчитаны новой отправкой. Новые боевой захват/SendMission и баланс
перелёта этим сценарием не проверялись. Луна отдельно не подготавливалась.

Последовательность прогона:

1. Штатный stop, `--prepare`, start на прежнем коде: **before5/5**.
   Raw и DOM показывали site19, steps содержал осиротевший move.
   Arrival1793513296.9283, missionEnd1793513697.9283: лишние401с.
2. Stop, `--rearm`, start исправления: **after11/11**. Неявный хвост идёт к26,
   явный к19 сохранён. Контрольный explicit отозван обычным RecallFleet.
3. Дополнительно устранено обнаруженное рассогласование общей шкалы: она ещё
   считала4 старых MOVE. Stop до завершения implicit, `--rearm-implicit`, start:
   **progress11/11** — теперь2 MOVE и boundaries[1,2]; список, timer и шкала
   согласованы, реальные SQL-команды и runtime version от чтения не меняются.
4. Main сам завершил оба флота: **completion8/8**. Без reload browser получил
   status0/исчезновение implicit из FlyingFleets. Затем проверены WS/SQL/DOM.
5. Финальный штатный stop/start и полный reload: **completion12/12**, включая
   состав/XP и ответы overview/galaxy/fleets. Во всех завершённых browser-прогонах
   runtime errors/unhandled rejection0.

Rearm меняет время только подготовленного активного QA-checkpoint, чтобы окно
наблюдения не истекло во время редактирования/restart. Поэтому сравнивается
добавка к arrival, а не абсолютные timestamps разных checkpoint.

У окончательного implicit прогноз и фактический current_position_time совпали:
**1793513302.2485** (09:08:22.2485 МСК). Нулевая добавка корректна именно здесь:
резервная база совпадает с планетой доставки, нового межсистемного рейса нет.
Сообщения100000427/100000428: единственная транспортная выгрузка17/11/5 и
единственный возврат1000 топлива. Explicit вернулся штатно; сообщение100000426
содержит17/11/5 и≈1000 топлива. Оба: home26/homeSite0, status0, бак/трюм0,
pending0, сохранён малый транспорт/XP7. Реальные IDs команд положительны.

Основной сервер после финального restart работает, startup
`2026-11-01T06:09:49.440742467Z`, OOMKilled=false, Server started присутствует.
В свежих file/Docker logs после найденной границы startup ошибок и warnings0.
Логи и история не очищались. Два QA-флота оставлены в базировании; их тестовый
груз/топливо выгружены штатно на QA-планету. Другие аккаунты не подготавливались.

## Браузерная среда и границы

Первоначальная навигация получила внешнюю ERR_NAME_NOT_RESOLVED для сайта/WS.
До pin endpoint проверен прямым TLS с SNI server.sp-game.ru: сертификат валиден,
обычный WebSocket upgrade даёт101. Использован только временный
`--host-resolver-rules` собственной тестовой Chromium-сессии; URL, TLS-проверка,
DNS игры/сервера и настройки провайдера не менялись. Это известный T003,
не новый игровой баг. Секреты не печатались. Сбой ожидания DOM в первом helper
исправлен: летящий флот находится в FlyingFleets, а не в FleetList.

Ограничение одного Accounts.frame из B042 сохранено: диагностический raw-канал
закрывается перед штатным чтением из SPA. Протокольный этап не начинался.
B016 (источник транспортного сообщения после смены дома) этим не исправлялся.
Другие боевые/межгалактические сценарии и пропажа последней планеты не объявляются
проверенными этим точечным прогоном.
