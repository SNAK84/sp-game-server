# B037 — переход страницы не зависит от анимации

## Причина и границы

Клик меню запускал цепочку `Overlay.Show(250) → Content.fadeOut(250) →
SendServer → Overlay.Show(250) → WS.Submit`. Последнее ожидание находилось
в существующем обработчике SendServer, а первые два — в BasePageClass.
Фоновый Show/render вызывает Overlay.Hide. Его `stop(true)` может отменить
ещё не выполненный callback; в этом случае запрос вообще не отправляется.
Аналогичная цепочка была у TopNav сообщений и у выбора планеты.

Это ошибка до отправки запроса, не изменение контракта WS и не гонка ACK /
применения PlayerQueue. Последняя по-прежнему асинхронна: planetselect ACK
сам по себе ещё не доказывает, что новая планета уже выбрана.

## Изменение

Только SPA `js/BasePageClass.js`:

- Меню показывает Overlay без callback и сразу вызывает существующий
  SendServer с NotOverlay:true. Это внутренний UI-флаг, в wire не передаётся.
- TopNav сообщений вызывает этот же setActiveMode, без второй копии цепочки.
- Смена планеты проверяет текущую активную страницу и сразу отправляет
  planetselect с тем же внутренним флагом.
- Переход больше не скрывает Content отложенным callback: текущая страница
  остаётся до штатной обработки ответа. Show/Hide и владение DOM не переписаны.

Общий Overlay не менялся. Принудительное завершение всех его callback
опасно: среди них есть игровые команды. Backend, схемы, протокол,
маршрутизация mode=none и ожидание применения игровых событий не менялись.

## Проверка основного dev

`tests/ClientNavigationLiveTest.py --dev` создаёт/закрывает собственную
Selenium-сессию. Используется уже существующий QA `qa_b018_home` с двумя
планетами: действующий токен читается только в RAM, не печатается и не
меняется. В конце исходный выбор планеты должен совпадать с начальным.
Новые аккаунты, планеты и флоты для проверки не создаются.

До правки реально воспроизведено: клик shipyard→defense, replay уже полученного
настоящего snapshot через50мс, отправленных defense-запросов0. Гонка зависит
от тайминга; отдельный клик сообщений в том же предварительном прогоне
успел отправиться. Это не приписывается новому серверному ActualData.

После правки проверяются desktop1440×900 и mobile390×844:

- Меню shipyard→defense и defense→shipyard, TopNav→messages, выбор другой

  Серверный ответ, обработка запроса и содержимое snapshot не подменяются.
- Каждый клик даёт ровно один wire-запрос и настоящий успешный ответ.

`--before` предназначен только для воспроизведения потери запроса **до**
установки исправления. На исправленном клиенте ожидание потери не выполнится.
Отдельный игровой сервер не запускается; restart основного main не нужен.
