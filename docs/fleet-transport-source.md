# B016 — источник транспортного сообщения

Исправлено01.11.2026, проверено на основном dev и в настоящем SPA обоих QA.
Frontend, шаблоны, схема SQL, стоимость/маршрут и исполнение UNLOAD не менялись.

## Причина и исправление

После выгрузки sendCommandNotification брал SourcePlanet из текущего
getHomePlanetId/getHomeSiteId. При потере ресурсной базы это уже резервная
планета. Для составного маршрута дом также не равен предыдущей остановке.
Notification корректно сериализовала неверно выбранный источник.

Теперь обычный buildTransport и компилятор этапов сохраняют в UNLOAD
`transportSource` — серверный снимок координаты начала именно этой перевозки.
При уведомлении он имеет приоритет. Клиент источник не задаёт.

Для уже существующих очередей без снимка read-only fallback проходит выполненную
историю до текущего UNLOAD: берёт start/предыдущее действие, пропускает cancelled,
сохраняет источник через последовательные MOVE одного плеча и разделяет разные
planStepId. Не подставляет физическую точку перехода или изменившийся дом.
Старые очереди и их params при таком чтении не переписываются.

Планета/луна разрешаются по действительной координате, поэтому прежняя
локализация названия для отправителя и получателя сохраняется. Для ресурсного
объекта остаётся прежняя подпись с сектором. Другие Coordinate не пытаются
разрешаться как ресурсный site: POINT подписывается известными координатами,
FLEET — известным ID без запроса его живой позиции. Это не раскрытие будущего
маршрута, груза или нового скрытого положения.

## Реальный dev, SQL/WS и браузер

Подготовка только на остановленном main, без второго игрового мира и SQL-схем.
`20261101_transport_source_qa.php` проверяет QA15/16, владельцев9/10, точные
планеты26/[1:6:2],27/[1:10:5], свободный site19/[1:7:3]/сектор2 и отсутствие
новых имён. Fleet122/его состав читаются только как шаблон, не изменяются.

Созданы отдельные QA-флоты с одним большим транспортом/XP11,31M/17C/9D и
5000 топлива после заданного начального списания30. Активное положение,
время и прошедшая история заданы checkpoint: это **не** полный вылет SendMission,
захват базы или проверка формул перелёта. Текущую доставку, уведомления,
возврат и сохранение выполняет обычный основной EventLoop.

Порядок подготовки/проверки:

1. Старый worker: stop→`--before`→start. QA130 доставил на свою26.
   Сообщение100000429 снова содержит неверный SourceCoordinate=[1:6:2]
   вместо пояса[1:7:3]. Репродуктор before6/6: raw и обычный SPA владельца.
   Его шаблон источник визуально не показывает; входящий текст проверен ниже.
2. Исправление: stop→`--after`→start. QA131 legacy,132 route,133 snapshot
   доставляют на чужую QA27. Legacy не имеет снимка, route имеет прошедшую
   остановку/UNLOAD26 и cancelled OBSERVE19 перед очередным плечом,
   snapshot получает поле из нового buildTransport.
3. After: owner15/15, target20/20. Обе пары видят верный source и31/17/9;
   у получателя проверены раскрытый текст и имя. Ресурсная перевозка не
   раскрывает будущую базу26. Клик/read/ActualData сохраняет тот же DOM node.
4. Финальный stop→`--move-only`→start дополнительно готовит QA134 без снимка:
   прошедший отдельный move-only на27, затем транспорт к26 с другим planStepId.
   Новый источник —27, не первоначальный site19 и не home26.
5. После restart/reload: owner20/20 и target20/20. QA134 добавлен только
   владельцу; получателю по-прежнему доступны лишь его три входящих отчёта.

Финальный finish5/5 после reload и обычного saver: все QA130–134 вернулись
на26/[1:6:2], status0/homeSite0, бак/трюм0, pending0; у каждого один большой
транспорт с XP11. WS, карточки базирования и MySQL совпали. Остаток топлива
выгружен штатно. Подготовленные QA-флоты оставлены на базе; пользовательские
флоты, технологии и схемы не подготавливались/не удалялись.

## Browser-harness и оставшиеся границы

Одна собственная Selenium-сессия штатно переключала оба QA через выход/форму
входа. Использовался проверенный TLS/101 endpoint с временным host mapping
только в тестовом Chromium; URL и DNS игры/сервера не менялись. Raw использует
тот же token и закрывается перед чтением DOM из SPA из-за одного Accounts.frame.

Первый repeat после restart столкнулся с `element not interactable` во время
анимации. Helper дополнен ожиданием видимого/неанимируемого UI и штатным read
NotOverlay; завершённый repeat20/20, JS/unhandled rejection0. Клиент ради теста
не менялся. В finish также повторилось отложенное B037: меню не переключилось
с Messages на Fleets за30с при pending0/errors0. Проверка состояния флотов
использует существующее read-сообщение без анимации меню; B037 оставлен открытым.

Отдельные живые отправления с луны, POINT/FLEET и новая постановка полного
составного маршрута через редактор в этом прогоне не проверялись. Никакие
остальные баги реестра, протокол/Android или баланс не объявляются исправленными.
