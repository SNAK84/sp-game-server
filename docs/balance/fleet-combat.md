# Групповой боевой расчёт

На 17.10.2026 реализованы **изолированный калькулятор** `FleetCombatService`,
координатор раундов `FleetBattleService` и адаптер миссии `FleetAttackService`.
Сам калькулятор не читает repositories и не меняет gameplay. Сбор участников,
runtime commit/rollback, обломки, восстановление, добыча и отчёты находятся
в адаптере ATTACK; порядок применения описан ниже.

## Правила залпа

1. Исходные группы одного типа сохраняют принадлежность флоту/планете.
   В пределах одного боя все они находятся у одного защищаемого объекта.
2. Щиты восстанавливаются в начале раунда по текущему количеству единиц.
   Повреждения корпуса сохраняются до конца боя; между миссиями этот модуль
   повреждённый корпус не хранит.
3. Обе стороны стреляют количеством на начало раунда: погибшая в раунде группа
   успевает ответить. Порядок собственных стреляющих групп случайный каждый раунд.
4. Цель выбирается среди живых групп с вероятностью `N_group / N_side`.
   После пакета вероятность пересчитывается по оставшимся единицам.
5. В пакет входит `min(нестрелявшие корабли, текущее количество выбранной группы)`.
   После пакета выполняется новый выбор; та же живая группа может выпасть снова.
   Например, 100 против двух групп по 50 дают пакеты 50+50, если число целей
   не изменилось после первого пакета.
6. `R = max(1, Vars.rapidfire[тип стрелка][тип выбранной цели])` — число выстрелов
   одного стреляющего корабля за залп по этому типу. Пакет даёт `N_packet * R`
   выстрелов. R не уменьшает число ещё не стрелявших кораблей и не запускает
   цикл дополнительных случайных выстрелов.
7. Разброс урона 80–120% определяется один раз для стреляющей группы в раунде.
   Избыточный урон после уничтожения выбранной цели теряется, не даёт опыта.

Это групповая модель: общее повреждение корпуса типа уменьшает число его
единиц через `ceil(остаток корпуса / корпус одной единицы)`. Состояние каждого
отдельного корабля, случайные взрывы и отдельное попадание каждого выстрела
не моделируются. Повреждения не превращаются в случайные округлённые потери,
как в доступном калькуляторе Nova.

## Купола

- Купола 409 → 408 → 407 принимают огонь по наземной обороне, включая купола
  меньшего приоритета. Оставшаяся энергия пробитого купола идёт дальше к
  прикрываемой выбранной группе в том же пакете.
- Выбор цели происходит **до** перехвата. Если выбрано орудие с RF=20,
  перехвативший его залп купол получает эти выстрелы с RF=20, а не RF купола.
- Сам купол — обычный участник случайного выбора с весом по его количеству.
  Если выбранный купол уничтожен, остаток не перенаправляется на случайные орудия.
- Корабли планеты и флотов не прикрываются. Техническая атака 1 куполов из Vars
  принудительно заменяется на 0. Орбитальная станция 411 не считается куполом.

## Число раундов

Стартовый лимит — **10**. Он фиксирован для всех составов, а не растёт от размеров
армии. Это начальная калибровка, не доказательство окончательного PvP-баланса.
Параметр чистого расчёта допускает 1–20 раундов для сравнительных проверок.

### Асинхронные раунды и подкрепления

`FleetCombatService::startBattle()` создаёт сериализуемое состояние,
`calculateRound()` выполняет ровно один раунд, `addReinforcements()` добавляет
новые группы между раундами. Старый `calculate()` остаётся совместимым полным
расчётом через тот же алгоритм. Корпус, компенсации округления, ledger урона,
стартовые характеристики и суммарные ограничения работы не сбрасываются.

`FleetBattleService` передаёт каждый раунд отдельным заданием в постоянный
Swoole Task pool (по умолчанию два процесса, `COMBAT_WORKERS=1..8`). Не создаётся
новый OS-процесс на каждый раунд. TaskWorker получает только snapshot и seed,
не загружает Fleet/AccountData и не пишет gameplay repositories. Результат
возвращается в общий mailbox, а принимает его только игровой цикл.

Плановый старт раунда N: `startedAt + N * 1 сек`. Прибытия обрабатываются
игровым циклом до dispatch очередного snapshot. Прибытие до/ровно на границе
входит в этот раунд, если snapshot ещё не отправлен. Прибытие во время расчёта
раунда N вступает не раньше N+1. Новое подкрепление НЕ перезапускает лимит
10 раундов. Последующие due раунды не запускаются циклом catch-up; за проход
может быть отправлено не более одного задания на бой. Очередь worker и
периодичность сбора ответов могут увеличить фактическую длительность.

Backend API координатора для адаптера прибытия:

```php
$battleId = FleetBattleService::begin($planetId, $attackers, $defenders,
    $eventTime, $rapidfire, $participatingFleetIds);
$round = FleetBattleService::reinforce($planetId, $battleId,
    "fleet:$fleetId:command:$commandId", 'defender', $preparedGroups,
    $arrivalTime, [$fleetId]);
```

Сторону определяет доверенный адаптер миссии, НЕ клиент. Адаптер ATTACK
подключает другие атакующие флоты того же владельца к атакующей стороне,
а прибывающие флоты владельца планеты — к защите. Атакующий третьего владельца
ждёт отдельного боя, не становится союзником автоматически. Общая политика
союзов пока не реализована. Группы подкрепления имеют новые
уникальные ID; повтор одного arrivalId с теми же данными идемпотентен.
Если вычисления задержались, подкрепление вступает в следующий ещё не
начатый раунд, а не исключается по истечении десяти секунд настенных часов.
Состав уже переданного задания immutable; ответ worker не заменяет pending
подкрепления, принятые координатором во время расчёта. Если бой закончился
до их вступления, они остаются pending для последующего адаптера миссий.

Состояние хранится в `PlanetBattles` (Swoole Table, обычный RepositorySaver).
Одна запись на планету, предельный JSON snapshot 256 KiB; переполнение
отклоняется до записи. Это ограничение хранения, не новый баланс боя.
Task attempt имеет уникальный token; поздние/повторные ответы не применяются.
Timeout 60 сек: до трёх попыток с тем же snapshot и серверным seed раунда.
Для повторяемости задания используется Xoshiro256StarStar PHP 8.2; seed
создаётся на сервере, не отправляется клиенту. Это новый execution-режим,
он не обязан повторять конкретные исходы старого random_int-калькулятора,
но сохраняет диапазоны и правила выбора. Ошибка вычисления переводит бой
в failed, не снимает блокировку и не объявляет фиктивный исход.

На занятой планете блокируются новые build/dismantle/cancel для построек,
исследований, верфи и обороны. Проверяются приём request, выполнение уже
принятого PlayerQueue event и прямые методы QueuesServices. При отмене
проверяется также реальная планета очереди (особенно исследования).
Дополнительно запрещены погрузка/отправка, ручное изменение состава,
создание и расформирование флотов у занятой планеты: нельзя спрятать груз
или корабли другим путём. Просмотр, смена планеты, переименование,
накопление ресурсов и работа ранее принятых игровых очередей не блокируются.

### Подключённый ATTACK

Рабочая цепочка: LOAD → MOVE-команды → ATTACK (пауза на раунды) → MOVE назад
→ UNLOAD → STAY. Предварительный запас топлива включает ОБА направления.
`FleetAttackService` собирает корабли планеты, наземную оборону и собственные
неподвижные флоты защитника; ракеты не превращаются в корабельные группы.
Перелёт на чужую планету/луну поддержан, ATTACK по свободной точке/FLEET — нет.
Новая цель/боевые timestamps не принимаются от клиента как готовые команды.

На прилёте повторно определяется владелец. Исчезнувшая/ставшая своей цель
не атакуется, флот начинает возврат. Дружественное прибытие UNLOAD/STAY
на воюющую планету приостанавливается и может войти в защиту со следующего
не начатого раунда. Snapshot уже отправленного раунда не меняется.

`finished` означает только готовность расчёта. До применения результата
EventLoop актуализирует цель штатным processPlayerStateAtTime/save, даже
если защитник offline. Не меняется формула ресурсов и очередей. Новые
произведённые корабли не затираются: потери исходных групп вычитаются из
текущего количества. Они не добавляются автоматически в текущий бой.

Подготовка результата не меняет gameplay. Восстановление обороны — как
в текущем Nova: `round(lost * random_int(56,84)/100)`, со стабильным seed
на повтор commit. Добыча только при победе атакующего: до половины КАЖДОГО
из ресурсов 901/902/903, пять шагов Nova, но из свободной вместимости вычтены
фактические груз и топливо. Несколько флотов делят добычу пропорционально
свободному трюму. Обломки кораблей используют FleetDebrisPercent, оборона —
DefenseDebrisPercent (по умолчанию 0), только по невосстановленным потерям.
Луна делит поле обломков со своей орбитой.

XP применяется к группам Fleet, без второго бонуса Fleet и без XP кораблям
планеты/обороне. Топливо теряется пропорционально потерянной ВМЕСТИМОСТИ,
не числу кораблей. Старый груз сохраняется, пока помещается; избыток после
потерь пропорционально сокращается, не превращаясь в дополнительные обломки.

Локальный commit включает корабли/оборону, топливо/груз/XP Fleet, ресурсы,
обломки, marker ATTACK и по одному штатному Fights-сообщению каждому владельцу.
Каждая runtime запись проверяется чтением и dirty marker. Ошибка откатывает
уже записанные значения в обратном порядке. Новые строки откатываются с
очисткой индексов и DELETE marker; retry получает НОВЫЕ IDs, без конфликта
старых delete/update markers. Ошибка rollback закрывает бой для ручных
изменений; оригинальная ошибка остаётся в логах.

После успешного commit сохраняется `settled`, затем отдельно продолжаются
команды и удаляются погибшие флоты. Повтор не применяет добычу/XP/доклады.
Кэш обновляется в том же экземпляре Fleet, без опасной замены объекта с
destructor. Только после этого releaseAfterCommit переводит бой в applied.
Имеющиеся ActualData обновляют обе стороны без нового push-протокола.
При невозможном возврате очередь флота сохраняется с blockedAfterBattle:
нет бесплатной дозаправки и блокировки планеты; флот остаётся в таблице
с приостановленной командой. Способ его последующей заправки/смены плана
нужно реализовать отдельно. ACS, союзы и захват не добавлены.

### Образование луны (Nova)

После боя на планете без луны шанс равен
`min(MoonChance, round((новый металл + новый кристалл) / 100000 * MoonFactor))`.
По умолчанию `MoonChance=20`, `MoonFactor=1`; старое поле не увеличивает шанс.
Победа атакующего не обязательна. Бой на луне и существующая луна исключают образование.
Диаметр по Nova: `floor(sqrt(random(10,20) + 3 * шанс) * 1000)` км.
Новая луна принадлежит владельцу планеты, имеет одно поле, нулевые ресурсы,
нулевые здания/корабли/оборону и использует orbital anchor родительской планеты.
Лунная база (41) расширяет число полей на `FieldsByMoonBasis` за уровень.

`DebrisMoon=1` (как дефолт Nova) использует всё поле, включая старый запас;
`DebrisMoon=0` оставляет старые и новые обломки для переработки.
Доклад отдельно хранит созданные боем обломки и фактически использованный запас.
Проверка и параметры воспроизводимы из отдельного потока seed боя; правила
фиксируются при начале боя. Retry после rollback не перебрасывает исход/диаметр.
Planets/Builds/Ships/Defenses/PlanetResources и поле входят в тот же локальный
runtime commit и rollback, что добыча и сообщения. После rollback выделяется
новый ID, чтобы не переиспользовать DELETE marker. Архив публикуется после commit.
Дополнительное поле `report.moon` совместимо со старыми докладами версии 1.

Проверки: `php tests/MoonFormationTest.php`; native Swoole/TaskWorker:
`php tests/FleetAttackTest.php --export-fixture | docker exec -i swoole_app php /var/www/html/tests/FleetAttackSwooleTest.php --moon --mysql-archive`.
SQL-проверка использует отдельные архивные и временные gameplay-таблицы;
боевые аккаунты и рабочие таблицы игры не изменяются.

Обычный periodic flush не гарантирует crash-safe commit нескольких gameplay
repositories. Тест потери mailbox проверяет повтор из сохранённого checkpoint,
НЕ сохранность последнего незаписанного состояния при падении всего сервера.
Неизвестные/failed бои остаются закрыты для ручных изменений до разбирательства.
Сохранённый application-план не применяется наугад к смешанным before/after
строкам после частичного восстановления MySQL: такой бой становится failed.

Проверки: `php tests/FleetCombatRoundsTest.php`, `php tests/FleetBattleTest.php`,
`docker exec swoole_app php /var/www/html/tests/FleetBattleSwooleTest.php`.
Последний запускает отдельный loopback Server на случайном порту, реальные
TaskWorkers и in-memory repositories без MySQL/живых аккаунтов.
Полный адаптер проверяет `php tests/FleetAttackTest.php`. Native end-to-end:

```sh
set -o pipefail
php tests/FleetAttackTest.php --export-fixture |
  docker exec -i swoole_app php /var/www/html/tests/FleetAttackSwooleTest.php
```

Это реальные Swoole Tables/TaskWorker, но виртуальное игровое время перелёта
и тестовые repositories, без подключения к MySQL или изменения аккаунтов.

Основа выбора: при текущих характеристиках одиночный ЛИ имеет корпус 400,
атаку 50 и щит 10. При среднем уроне дуэль требует 10 раундов; 6/8 недостаточно.
Равные тяжёлые щитовые составы вправе закончить ничьей, лимит не гарантирует
победу одной из сторон.

| --- | --- | --- | --- | --- |
| 66 линкоров против 1000 ЛИ | 100 ничьих | 8 побед атакующего | 92 победы атакующего | 100 побед атакующего |

экономики потерь; snapshot характеристик может устареть при изменении баланса.

## Вклад и опыт

`calculate()` возвращает участников до/после, остаток корпуса/щита, power
сторон, раунды и `hullDamage[sourceGroup][actualTargetGroup]` отдельно для
каждой стороны. В ledger включается только реально снятый корпус, без щитов
и overkill. При перехвате фактической целью является купол, не орудие.

После отдельного определения восстановления обороны:

```php
$battle = FleetCombatService::calculate($attackers, $defenders, $rapidfire);
$inputs = FleetCombatService::experienceInputs($battle, [
    'defender' => ['planet:11:401' => 7], // Количество восстановленных установок.
]);
$attackerXP = FleetExperienceService::calculateRewards(...$inputs['attacker']);
$defenderXP = FleetExperienceService::calculateRewards(...$inputs['defender']);
```

Это всё ещё расчёт, НЕ сохранение. Восстановление само не генерируется;
пустой список означает отсутствие восстановления для данной проекции.
Уничтоженная невосстановленная стоимость каждой группы распределяется между
источниками пропорционально их урону её корпусу, включая ранее погибших.
Повреждение выживших не создаёт уничтоженной стоимости. Планетарные корабли
и оборона входят в расчёт вклада и угрозы, но сами не получают опыт.

Входные характеристики одного корабля должны заранее включать технологии и
`FleetExperienceService::combatStats()` ровно один раз. Калькулятор не добавляет
второй бонус от сводного опыта флота и не пересчитывает опыт между раундами.

## Ограничение работы и оставшиеся вопросы

- Нет цикла по RF и заранее созданного массива на каждый корабль. Повторные
  пакеты по единственной оставшейся группе объединяются только до первого
  изменения её количества: результат равнозначен, поскольку разброс для
  источника уже выбран на весь раунд. После гибели цели новые корабли не стреляют.
- Для 1–8 групп используются кэшированные веса, для большего числа — дерево
  Фенвика: случайный выбор и обновление количества требуют O(log G), а не
  полного сканирования G целей на каждый пакет. Погибшие группы имеют нулевой вес.
  Приоритетные купола перечисляются заранее, без повторного поиска по всем целям.
- При сильном различии размеров групп попадания одного источника объединяются
  в безопасных окнах до 4096 выборов. **Каждый случайный выбор всё равно выполняется**
  с прежним диапазоном и размером пакета. Окно консервативно заканчивается до
  первой возможной потери единицы при любом распределении попаданий; число
  целей и веса в нём неизменны. Урон не заменяется средним/матожиданием.
  Если активен купол, такое объединение выключено: перехват связывает цели.
- Сохраняются пределы 100000 вычисляемых пакетов и 1000000 шагов работы.
  Выборы внутри окна тоже учитываются по одному. Бюджет работы теперь считает
  шаги кэша/дерева, обновления и подготовительные сканы, а не условные 6 полных
  сканов массива на каждый пакет. Превышение любого
  бюджета бросает исключение, **частичный результат не возвращается**.
  Это предохранитель, не аппроксимация боя; будущий handler обязан отклонять
  такой расчёт без runtime mutations. Очень длинные бои с множеством отдельных
  случайных выборов всё ещё могут быть отклонены; лимиты не повышались.
- Вероятность выбора взвешена по N, но размер пакета тоже зависит от N цели.
  Поэтому разделение одинаковых кораблей на разные группы всё ещё способно
  изменить дисперсию и распределение огня. Полная инвариантность к разделению
  не заявляется; это следствие согласованного пакетного правила.
- Некорректные числа, NaN/Infinity, опыт вне диапазона и количество участников
  выше точности целочисленного представления double отклоняются. Компенсация
  Kahan сохраняет округлительный остаток HP/щита при тысячах малых попаданий;
  щитовая компенсация сбрасывается вместе с восстановлением щитов. Эти служебные
  значения не входят в результат. Допуск зависит от машинного шага большого
  пула (4 EPS), ограничен 0.001% характеристики одной единицы с абсолютным
  минимумом 1e-9. Это устраняет ложные отказы 100 млн/1 млрд, но не разрешает
  погрешность, способную создать потерю целого корабля. Например, урон 0.5
  по 9007199254740991 единицам с корпусом 1 всё ещё отклоняется.
- Exactly-once, одновременные бои, сохранение потерь, пропорциональная потеря
  топлива по вместимости и переполнение груза этим этапом не реализованы.

## Проверки оптимизации

Без сервера и игровых мутаций:

```sh
php tests/FleetCombatTest.php
php tests/FleetCombatOptimizationTest.php
php tests/FleetCombatBalanceTest.php
```

Независимая пошаговая спецификация в `FleetCombatOptimizationTest.php` хранит
HP/щиты в целых сотых, не вызывает production-дерево, окна или методы округления.
Проверены 1000 смешанных боёв с 1–16 группами на сторону, 200 боёв резко неравных
групп и 800 боёв с 1 млн, 10 млн, 100 млн и 1 млрд единиц. Сравниваются каждый
раунд, потери, щиты, выстрелы, урон и хэш **всех** вызовов RNG с их диапазонами.
Дополнительно проверены 90 сочетаний слабого одиночного атакующего против
миллиардных групп всех типов из fixture, с дробным опытом. Политика начисления
опыта, источник RF, купола и число раундов не менялись.

Для крайне маленьких боёв кэш и компенсация могут стоить немного дороже старого
расчёта. Выигрыш оптимизации направлен на множество групп и длинные серии малых
пакетов; универсального ускорения каждого состава не заявляется.

### Локальные замеры 16.10.2026

PHP CLI 8.2, лимит 10 раундов, без БД/сети/сохранения/применения награды.
Сравнивалась копия калькулятора непосредственно перед оптимизацией, не Nova.
Медианы 200 запусков обычных сценариев и 20 тяжёлых; времена зависят от нагрузки
хоста и случайного хода боя, это не замер пропускной способности EventLoop.
