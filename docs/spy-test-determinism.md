# T001: нестабильный шпионский сценарий проверки маршрута

Исправлено02.11.2026. Изменения только в тестах и документации `/opt/sp-game`.
Производственный сервер, SPA, API и игровые аккаунты не менялись.

## Причина

В FleetPlanSwooleTest сценарий «шпионаж → доставка → возврат» рассчитывал на
выживание зондов, но выполнял настоящий случайный бросок. FleetSpyService
сравнивает random_int(0,counterLimit) >= random_int(0,100). При counterLimit0
пара0/0 всё ещё уничтожает зонды и тем самым прерывает ожидаемый маршрут.

Это совпадает с исходной Nova:
/opt/nova.snak84.ru/includes/classes/missions/MissionCaseSpy.class.php,
два mt_rand на99–100 и сравнение >= на170. Нулевой counterLimit здесь не
означает математическую нулевую вероятность потери. Формула не менялась.

Перед изменением чистый вызов существующего расчёта отчёта показал:
counterLimit0 + броски0/0 → destroyed=true;0/100 → destroyed=false.
Тест маршрута должен явно выбирать нужную ветку, а не зависеть от случайности.

## Совместимость старого fixture

Первый запуск существующего файла остановил все9 случаев до маршрута:
«Не удалось сохранить уникальный индекс Config/name», SQL calls0.
researchRepository создавал лишнюю колонку ids даже у уникального индекса.
Текущий BaseRepository проверяет точную строку ['id'=>id], тогда как старый
fixture возвращал ['id'=>id,'ids'=>'']. В production initIndex уже создаёт
ids только для неуникальных индексов.

В общем тестовом loader изменено только это условие; production-репозиторий
не ослаблялся. После актуализации, но до исправления случайности маршрута,
принудительный RNG0/0 только для FleetSpyService дал8 PASS/1 FAIL. Единственное
падение — «native: шпионаж → доставка → возврат: Маршрут не вернулся».
Остальные8 случаев прошли, SQL calls0. Общий fixture не сбрасывал живые данные.

## Исправление

tests/fixtures/FleetPlanSpyRandom.php предоставляет test-only namespaced RNG
и withFleetPlanSpyRolls. Вне явно заданной области вызывается настоящий
\random_int; внутри области управляются только вызовы от FleetSpyService.
Другие сервисы не получают чужую очередь бросков. Проверяются диапазон,
число использованных значений и отсутствие вложенной области; finally
снимает подмену даже при исключении. Это не параметр WS или production API.

FleetPlanSwooleTest задаёт0/100 только вокруг завершения шпионского маршрута.
Все проверки фактической доставки и возврата сохранены; попытки/падения
не игнорируются и не превращаются в допустимый случайный результат.

## Проверки

- Чистый SpyRandomContractTest:711 PASS, Tables0/SQL0. Перебраны все101
  значения второго броска при counterLimit0: погибает ровно0/0;500 раз
  подтверждено выживание на0/100. Проверены посторонний вызов RNG, нехватка,
  недопустимый диапазон, лишние броски и очистка после исключения.
- FleetPlanSwooleTest после исправления:9/9 PASS, затем ещё пять отдельных
  прогонов9/9. Итого54 успешных сценария, в каждом процессе SQL calls0.
- ResearchResourcesIsolationTest:27 PASS/0 FAIL/SQL calls0 после изменения
  общего loader; это регрессия затронутого fixture, не всего игрового baseline.
- PHP lint всех четырёх изменённых/новых PHP-файлов пройден.
- vendor/bin/phpstan analyse --memory-limit=1G: level3, существующий baseline,
  errors0/file_errors0 до и после изменения. Baseline/config/composer не менялись.
  По конфигурации PHPStan проверяет src, а не тестовые файлы; проверка тестов
  выполнена lint и описанными точечными прогонами, не выдается за PHPStan tests.

Новый игровой сервер или второй EventLoop не запускались. Это исправление
теста, поэтому реальная шпионская миссия через SPA не отправлялась;
вероятности работающей игры этим этапом не тестировались и не менялись.
Основной main оставлен работать, штатного restart не требовалось.
T002 и изменения клиент-серверного протокола в этот этап не включались.
