# B006 — согласованность runtime add/update

28.10.2026. Изменён только общий путь записи backend. Frontend, WebSocket API,
SQL-схемы, игровые ID и алгоритмы полёта не изменялись.

## Причина

Прежний `BaseRepository::update()` не проверял основной `Table::set()`:
даже после false он переносил ID в новые индексные группы и ставил marker.
`FleetControlService::patchCommand()` затем замечал несовпадение main row.
Но внешний rollback вызывал update(before), а main row уже была равна before:
это no-op, поэтому неправильное членство индексов оставалось.

До исправления дефект повторён28.10 на настоящем native Table и SELECT-снимке
QA-команды190/Fleet56: mainUnchanged=true, indexesUnchanged=false,
markersUnchanged=false. Старый BaseRepository подключён только к CLI-проверке
из сохранённой копии; работающий worker не переключался на старый код.

## Изменение

- `add/update` используют один внутренний `writeRuntimeRow`.
- До записи сохраняются main row, затрагиваемые unique/non-unique группы и
  marker конкретного ID. Неизменившиеся индексные ключи update не переписывает.
- Проверяется успешность основного set и точное чтение результата; только
  после этого обновляются индексы. Unique set/del и dirty marker также проверяются.
- При исключении возвращаются точные before-образы, включая отсутствие
  новой строки/marker и порядок ID в частях индекса. Возврат сам по себе не
  создаёт лишний DELETE или dirty marker. Уже поставленный marker не теряется.
- После отказа add не остаются новая main row и индексные ссылки на неё.
  Повторный add существующего ID не дублирует ID в индексной группе.
- Ошибка восстановления не маскируется: CRITICAL с именем репозитория, ID и
  ошибками отдельных частей, затем исключение. Значения строк/токены не логируются.

Публичные методы и порядок игрового commit остались прежними. Существующая
специальная компенсация пространственного боя не удалена. Counter last_id не
откатывается; проблему повторного ID после restart B029 этот этап не исправляет.

## Точечная проверка native-отказов

```bash
docker exec -w /var/www/html swoole_app php tests/RepositoryWriteProbe.php --dev-readonly
```

CLI читает существующий dev-мир через SQL-транзакцию READ ONLY, работает с
локальными Table-копиями и не вызывает saver/main.php. Доступ к SQL-записи
запрещён самой транзакцией. QA-guard проверяет аккаунт16, Fleet56 и команду190.
Новый игровой сервер/изолированный тестовый мир не запускается; это проверка
редких отказов, а не доказательство отказа в живом worker. Лог проверки —
`/tmp/sp-game-b006-probe.log` внутри контейнера, не общий игровой журнал.

Пройдены15 групп:

1. Основной set возвращает false до записи.
2. False после фактической записи.
3. Исключение после фактической записи.
4. Отказ новой non-unique группы.
5. Отказ перезаписи старой группы.
6. Отказ второй части длинной группы после изменения первой.
7. Отказ dirty marker.
8. False после фактической записи marker.
9. Внешний FleetControl rollback и успешный retry с правильными старым/новым индексами.
10. No-op и rollback после предшествующей успешной записи внутри commit.
11. Новая команда: отказ main set.
12. Новая команда: отказ индекса после добавления другого индекса.
13. Новая команда: отказ marker.
14. Отказ записи новой unique группы.
15. Отказ удаления прежней unique группы.

Сравниваются main rows, все индексные группы и markers, не только getById.
Группа второй части выполняется при наличии такой части в dev-снимке; в этом
прогоне она существовала и сценарий был выполнен. Сам probe не изменяет SQL;
Table-копии освобождаются при завершении CLI. Фоновая игра продолжает менять
свой мир независимо от этого READ ONLY снимка.

Артефакты: `/tmp/sp-game-b006.T1IpK2/before.log`, `after.log`.

## Проверки и границы

- PHP-lint BaseRepository и RepositoryWriteProbe; scoped diff-check.
- Финальный повтор native probe после двух restart: те же15 групп, все успешны.
  Настоящий WebSocket ответил ok/Page для overview/buildings/researchs/shipyard/
  defense/fleets/galaxy/messages,8/8. В свежем журнале последнего запуска
  ERROR/CRITICAL/Fatal0; основной сервер остаётся running.
- Main/native сценарии выше не заменяются старым общим suite; весь изолированный
  набор не запускался. Проверки не заставляли живой worker терять native память.
- Это локальная компенсация одной runtime-записи. Многопроцессная изоляция,
  exactly-once, SIGKILL/crash посреди операции, SQL-транзакция и автоматический
  repair уже повреждённых Tables не добавлялись. Startup заново построил индексы.
- Постоянная невозможность восстановить native-строку/индекс выявляется, но
  не превращается в успешный rollback. Универсальной quarantine здесь нет.
- EntitySettings переопределяет add/update; его отдельный составной ключ и
  прямые записи остаются B038. Непроверяемые del/DELETE marker — B039.
  Эти статические находки зарегистрированы, не исправлялись попутно.
- B002/B037 и отдельный разбор клиент-серверного протокола по-прежнему отложены.
