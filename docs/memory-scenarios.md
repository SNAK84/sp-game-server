# Память и заполнение мира: сценарии вместо полного нагрузочного прогона

Решение пользователя13.11.2026: полный нагрузочный прогон сейчас не обязателен.
Оценивать запас по таблице сценариев; исправлять рабочий dev без копий кода
или отдельных тестовых миров. Код восстанавливать из проверенных точек GitHub.
Цель20 000 аккаунтов/1 000 онлайн сохраняется. Это не заявление о выполнении SLO.

## Воспроизведение

```bash
docker exec swoole_app php bin/memory-scenarios.php
docker exec swoole_app php bin/memory-scenarios.php --accounts=20000 --online=1000 --active-fraction=0.02
docker exec swoole_app php bin/memory-scenarios.php --accounts=20000 --online=1000 --command-hours-per-day=4
docker exec swoole_app php bin/memory-scenarios.php --help
docker exec swoole_app php bin/audit-capacity.php --development --sql-counts
docker exec swoole_app php bin/audit-capacity.php --target
```

Скрипт читает реальные схемы/бюджеты через существующий аудитор и SELECT vars.
Он не вызывает init игровых репозиториев, не создаёт Swoole Table, аккаунты
или соединения игроков, не меняет профиль основного процесса. Все коэффициенты
можно изменить параметрами; --help перечисляет их. Модель native allocation
применима к установленному Swoole5.1.6/x86-64; другая версия требует сверки.

## Что именно считается памятью

| Величина | Development | Target |
| --- | ---: | ---: |
| Выделение всех учтённых Table, модель | 1 711 130 976 байт / 1,594 GiB | 15 106 369 888 байт / 14,069 GiB |
| Нижняя граница RAM только по стартовому guard70% | 2,277 GiB | 20,098 GiB |

Table выделяются целиком при запуске. Поэтому у одного профиля для100 и20 000
аккаунтов одинаковый модельный размер — но строки могут закончиться гораздо
раньше. Между профилями рост ступенчатый, а не «N байт на игрока».
Стартовая граница не является достаточной памятью для всего хоста.

Read-only замер процессов основного контейнера13.11.2026 около17:50 MSK:
сумма PSS пяти игровых процессов≈1008,1 MiB, SwapPss≈4,0 MiB.
Диагностический CLI не включён; взят /proc/PID/smaps_rollup.
RSS процессов не складывался, чтобы не считать shared-страницы несколько раз.
PSS — текущие резидентные страницы, а Table-модель — выделение; разница
не означает доступный запас. Это одиночный снимок маленького рабочего мира,
не измерение20 000 аккаунтов и не коэффициент для линейного умножения.

## Сценарии заполнения

Предположения, **не измеренный профиль игроков и не новые игровые лимиты**:
5 планет/лун на аккаунт,1 флот на базу,10% флотов активны,
24 будущих физических команды плюс24 уже выполненных на активный флот,
5 сообщений в сутки на аккаунт, хранение7 дней. На каждого online считается
предельное число8 подписок. Онлайн не ограничивает полёты офлайн-игроков.
История активного маршрута остаётся до завершающего STAY; после него текущий
движок очищает команды. Это не бессрочный архив каждого базированного флота.

Расширение14.11.2026 дополнительно считает:

- Квитанции:2 команды в минуту на каждого online, такой онлайн сохраняется
  24 часа в сутки; TTL берётся из ProtocolCommands(сейчас1 день).
  Это условный постоянный ритм, не измеренный суточный профиль. Каждая
  packed-квитанция384B, включая префикс после сжатия, требует1 блока1024B.
- Почта:25% писем имеют packed-тело1024B, остальные помещаются в inline256B.
- Доклады:0,1 свежего доклада на аккаунт в сутки, TTL7 дней, плюс1 отдельно
  сохранённый старый доклад на аккаунт; наборы считаются непересекающимися.
  Packed-тело доклада8192B,2 закладки на аккаунт. Сохранённый архив бессрочен:
  коэффициент1 — сценарий текущего запаса, не автоматический предел архива.

Размеры packed и доля overflow задаются параметрами. Они не выведены из
маленькой выборки dev. Сначала округляется число записей, затем число блоков
**каждого** тела; тела до256B не занимают overflow. Отдельно выделены
`demandBreakdown` и бюджеты строк/блоков. Размеры всех профилей прежние:
игровые Table и рабочий профиль не менялись.

в процессе повторного входа/переходов, а не только на устойчивый онлайн.

### Чувствительность к предположениям

При20K аккаунтов,24 будущих+24 выполненных командах и2% активных флотов
требуется96 000 команд (146,48% текущего target), при10% —480 000 (732,42%).
Старые48 000/240 000 воспроизводятся только с явным
`--history-commands-per-active=0`; они не учитывали выполненную часть маршрута.
Это разные сценарии, не измерение улучшения сервера. Текущий бюджет65536 не гарантирует
утверждённую цель для произвольного числа флотов/маршрутов; его нельзя считать
достаточным только по числу онлайн. При4 часах постоянного ритма2 команды/мин
на1000 online получаются480 000 квитанций: строки ещё вмещаются(45,78%), но
блоки при packed384B — нет(183,11%). Смена compressed-размера с256 на257B
меняет спрос от0 до1 блока на запись; средний размер без учёта этой границы
даёт неверную оценку. Новые размеры в этой работе не включались.

## Проверки расширенной модели

```bash
python3 tests/MemoryScenariosReadOnlyTest.py
```

Проверка запускает только read-only расчёт в действующем dev-контейнере.
Новый мир/Table/аккаунты не создаются, игровой профиль не переключается.
Проверяются история, разные TTL, строки отдельно от блоков, inline256/257,
округление каждого тела1025B, нулевой сценарий, воспроизведение прежнего
упрощённого расчёта явными нулями и отказ на неверных коэффициентах.
Флаги `modelNotRss=true`/`loadTestPerformed=false` остаются обязательными.

## Что остаётся вне точного прогноза

- PHP heap/кэши, производные индексы и copy-on-write процессов. Для ориентира:
  отдельная модель B076 на262144 закладки добавила≈29,78 MiB PHP heap;
  это не универсальный расход на аккаунт и не сумма PSS процессов.
- Пик подготовки/кодирования снимка и живой памяти saver. Лимит снимка128 MiB
  не равен суммарному PHP heap и не ограничивает все временные копии.
- Сокеты, ОС, MySQL, кабинет и другие процессы хоста. Их резерв нельзя выдавать
  за измеренную линейную стоимость одного игрока.
- Время тика, p95/p99 команд, боевой расчёт и восстановление. Таблица памяти
  не проверяет CPU/задержки; точечные проверки на основном dev сохраняются.

Прогресс фиксируется конкретно: выделенные байты, процент заполнения, запас
до бюджета и закрытые дефекты. Произвольный «процент готовности сервера»
не вычисляется. RAM-first не меняется: игра работает в памяти; MySQL содержит
периодические/финальные снимки для восстановления, не обслуживает игровой hot path.

Порядок рабочих изменений и GitHub описан в [workflow](development-workflow.md).
