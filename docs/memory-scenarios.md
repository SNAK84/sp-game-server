# Память и заполнение мира: сценарии вместо полного нагрузочного прогона

Решение пользователя13.11.2026: полный нагрузочный прогон сейчас не обязателен.
Оценивать запас по таблице сценариев; исправлять рабочий dev без копий кода
или отдельных тестовых миров. Код восстанавливать из проверенных точек GitHub.
Цель20 000 аккаунтов/1 000 онлайн сохраняется. Это не заявление о выполнении SLO.

## Воспроизведение

```bash
docker exec swoole_app php bin/memory-scenarios.php
docker exec swoole_app php bin/memory-scenarios.php --accounts=20000 --online=1000 --active-fraction=0.02
docker exec swoole_app php bin/memory-scenarios.php --accounts=20000 --online=1000 --command-hours-per-day=4
docker exec swoole_app php bin/memory-scenarios.php --accounts=20000 --online=1000 --pending-commands-per-online=4
docker exec swoole_app php bin/memory-scenarios.php --help
docker exec swoole_app php bin/audit-capacity.php --development --sql-counts
docker exec swoole_app php bin/audit-capacity.php --target
```

Скрипт читает реальные схемы/бюджеты через существующий аудитор и SELECT vars.
Он не вызывает init игровых репозиториев, не создаёт Swoole Table, аккаунты
или соединения игроков, не меняет профиль основного процесса. Все коэффициенты
можно изменить параметрами; --help перечисляет их. Модель native allocation
применима к установленному Swoole5.1.6/x86-64; другая версия требует сверки.

аккаунтов одинаковый модельный размер — но строки могут закончиться гораздо

Стартовая граница не является достаточной памятью для всего хоста.

PSS — текущие резидентные страницы, а Table-модель — выделение; разница

не измерение20 000 аккаунтов и не коэффициент для линейного умножения.

## Сценарии заполнения

Предположения, **не измеренный профиль игроков и не новые игровые лимиты**:
5 планет/лун на аккаунт,1 флот на базу,10% флотов активны,
24 будущих физических команды плюс24 уже выполненных на активный флот,
5 сообщений в сутки на аккаунт, хранение7 дней. На каждого online считается
предельное число8 подписок. Онлайн не ограничивает полёты офлайн-игроков.
История активного маршрута остаётся до завершающего STAY; после него текущий
движок очищает команды. Это не бессрочный архив каждого базированного флота.

Расширение14.11.2026 дополнительно считает:

- Квитанции:2 команды в минуту на каждого online, такой онлайн сохраняется
  24 часа в сутки; TTL берётся из ProtocolCommands(сейчас1 день).
  Это условный постоянный ритм, не измеренный суточный профиль. Каждая
  packed-квитанция384B, включая префикс после сжатия, требует1 блока1024B.
- В4Г отдельно от terminal-истории добавлен backlog:1 pending-команда на online
  (`--pending-commands-per-online=1`). Каждая accepted-квитанция физически
  занимает17 блоков до завершения, независимо от размера её текущего тела.
  Это сценарий, не лимит очереди и не измеренное число ожидающих действий.
- В4Е2 pending также считаются ожидающими событиями PlayerQueue. Доля больших
  событий задаётся --large-command-fraction=1: по умолчанию все имеют внешний
  payload. Счётчиков аккаунтов нужно min(online, больших pending). Прочие
  серверные события и недавно отключившиеся игроки в demand пока не включены.
  `largePayloadAggregateQuotaFit` проверяет лишь суммарную quota online×4;
  это не гарантия равномерного распределения по игрокам. Неверные по quota
  сценарии не обрезаются молча до доступного числа мест.
- Почта:25% писем имеют packed-тело1024B, остальные помещаются в inline256B.
- В4Е3В добавлены снимки фаланги: --phalanx-recent-account-fraction=1,
  по умолчанию все аккаунты имеют свежий снимок за последние300с, включая
  offline. Это верхний сценарий числа строк, не частота сканов; при online0
  demand не исчезает.20K/32768=61,04%, резерв есть. JSON/packed не усредняются:
  Table предвыделена под полный16KiB payload каждой строки.
- В4Е3Г добавлены --planet-battles-per-active-fleet=0.1,
  --space-battles-per-active-fleet=0.1, --expeditions-per-active-fleet=0.25.
  Считаются все активные флоты, включая offline; экспедиции также на обратном
  пути. Ещё --retained-checkpoints-per-account=0.025 и
  --checkpoint-sync-backlog-per-account=0.05 на каждый тип учитывают хвосты
  независимо от online/active. Sync demand включает все текущие строки как
  dirty плюс дополнительный хвост. Это модель, не измерение и не предел всех
  возможных миссий; коэффициенты не меняют игровой баланс.
- Доклады:0,1 свежего доклада на аккаунт в сутки, TTL7 дней, плюс1 отдельно
  сохранённый старый доклад на аккаунт; наборы считаются непересекающимися.
  Packed-тело доклада8192B,2 закладки на аккаунт. Сохранённый архив бессрочен:
  коэффициент1 — сценарий текущего запаса, не автоматический предел архива.

Размеры packed и доля overflow задаются параметрами. Они не выведены из
маленькой выборки dev. Сначала округляется число записей, затем число блоков

### Чувствительность к предположениям

При20K аккаунтов,24 будущих+24 выполненных командах и2% активных флотов
требуется96 000 команд (9,16% текущего target), при10% —480 000 (45,78%).
Старые48 000/240 000 воспроизводятся только с явным
`--history-commands-per-active=0`; они не учитывали выполненную часть маршрута.
Это разные сценарии, не измерение улучшения сервера. Новый бюджет1048576 не гарантирует
утверждённую цель для произвольного числа флотов/маршрутов; его нельзя считать
достаточным только по числу онлайн. При4 часах постоянного ритма2 команды/мин
на1000 online получаются480 000 terminal-квитанций плюс1000 pending:
481000 строк/497000 блоков,11,47%/11,85% при packed384B.
Прежний пул262144 не вмещал эти блоки; новый4194304 вмещает выбранный сценарий.
Однако packed1025B вместо384B для суточного сценария потребует5777000 блоков
с резервом1000 pending(137,73% нового пула),
хотя строки по-прежнему помещаются. Смена compressed-размера с256 на257B
меняет спрос от0 до1 блока на terminal-запись; резерв accepted остаётся17.
Средний размер без учёта этой границы
даёт неверную оценку. Новые размеры4Б не включались на рабочем dev.

поэтому потеря/повтор такого действия не заявляются воспроизведёнными.

Теперь accepted резервирует MAX_RECORD_BYTES+1=16385B, то есть17 настоящих
блоков, **до** публикации в PlayerQueue. Новый запрос при нехватке резерва
отклоняется без строки/очереди; дубликат продолжает читать прежнюю квитанцию.
SharedBlobStore::replace переиспользует блоки, сохраняет старые байты для
rollback и освобождает лишние только после публикации метаданных. Guard не
позволяет snapshot/lookup увидеть промежуточное тело. ACK pending сохраняет
резерв; terminal/удаление освобождают его. Snapshot содержит только packed
полезные байты, не пустой резерв; SQL-схемы и публичные payload не менялись.
После восстановления из MySQL резерв accepted строится заново в RAM.

Некодируемый или превышающий лимит результат переводится в явный terminal
unknown/outcome_unavailable: нельзя автоматически переисполнить действие.
Нормальный applied/rejected/unknown сохраняет полный результат.

## 4Д: память снимка(15.11.2026)

Native Table-модели в верхней таблице не изменились. Для snapshot добавлены
snapshotPolicy в обоих экспортёрах и пять gauges рабочего saver:
storage.snapshotBytes/PeakBytes/LimitBytes/BudgetHits/CaptureMs. Всего63 ключа
в прежних64 слотах. SnapshotRows теперь считает реальные строки докладов/
закладок, а не две пустые группы. Read-only проверки:83 PASS.

Capture хранит сериализованную/сжатую строку на запись, а не широкое дерево
PHP-массивов; SQL writer распаковывает ограниченную партию(по умолчанию100).
Снимок целиком остаётся в RAM. В MySQL по-прежнему обычные поля/JSON, одна
транзакция всех репозиториев и PlayerQueue; ACK после COMMIT. Дискового spool,
SQL в игровом hot path или частичного сохранения отдельных баз нет.

Бюджет128MiB теперь проверяет peak-delta PHP на границах capture/codec/write,
а не только текущую память после append. Entry ограничен64MiB; распаковка
ограничена этим размером, разрешены только внутренние array-образы. Бюджет
не гарантирует отсутствие OOM внутри одной аллокации/zlib/PDO и не равен RSS,
COW, PHP memory_limit или памяти всего хоста. При отказе нет COMMIT/ACK.
После COMMIT бюджетные исключения отключены до конца ACK(его пик измеряется):
это уже подтверждённая транзакция, её нельзя откатить задним числом.
Если даже packed-снимок больше бюджета, его нельзя объявлять сохранённым;
нужны достаточный настроенный лимит и отдельная проверка worst-case backlog.

codec, сохранение типов/точности, plain/packed настоящих репозиториев,

## Что остаётся вне точного прогноза

- При 64 группах с каждой стороны дополнительный пик памяти PHP на десятом
  раунде составил 665 816 байт при расчёте и 2 136 352 байта при принятии
  результата. Для пересчёта на весь сервер потребуются распределение размеров
  боёв и число одновременно занятых процессов. [Методика и замеры](capacity-hardening-plan.md#4е4л--передача-одного-боевого-раунда-вычислителю).
- Координатор боёв держит до восьми исходных JSON по 262144 байт в PHP heap.
  Суммарный предел содержимого строк составляет 2 МиБ на процесс координатора.
  На заголовки расписания, массивы и временный разбор нужна дополнительная память.
- PHP heap/кэши, производные индексы и copy-on-write процессов. Для ориентира:
  отдельная модель B076 на262144 закладки добавила≈29,78 MiB PHP heap;
  это не универсальный расход на аккаунт и не сумма PSS процессов.
- Пик всего target-снимка и живой памяти saver. В4Д добавлены packed-строки и
  контроль peak-delta128MiB на границах; это не строгий лимит каждой аллокации,
  суммарного PHP heap/COW/RSS. Полный worst-case backlog не измерен.
- Реальная скорость TTL-уборки, накопление accepted/tombstones и ACK. В4В
  идеальный круг уменьшен с8192 до300 вызовов, но временные ограничения/lag
  и SQL-down могут его удлинить. Запас сценария не является доказательством
  устойчивой очистки при длительной нагрузке; нужен дальнейший аудит admission.
  При одновременном истечении 128 квитанций QA на dev последняя была помечена
  через 31,3 с, а все слоты и внешние блоки освободились к 50,5 с после TTL.
  [Положение курсора, размеры порций и подтверждение снимка](capacity-hardening-plan.md#4е4н--одновременное-истечение-срока-квитанций-команд).
- Сокеты, ОС, MySQL, кабинет и другие процессы хоста. Их резерв нельзя выдавать
  за измеренную линейную стоимость одного игрока.
- Время тика, p95/p99 команд, боевой расчёт и восстановление. Таблица памяти
  не проверяет CPU/задержки; точечные проверки на основном dev сохраняются.

Прогресс фиксируется конкретно: выделенные байты, процент заполнения, запас
до бюджета и закрытые дефекты. Произвольный «процент готовности сервера»
не вычисляется. RAM-first не меняется: игра работает в памяти; MySQL содержит
периодические/финальные снимки для восстановления, не обслуживает игровой hot path.

Порядок рабочих изменений и GitHub описан в [workflow](development-workflow.md).
