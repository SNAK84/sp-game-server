## Этап1 — целостность и первые ограничения

Внесено в backend; клиентский контракт не менялся:

- Очередь отменяется только владельцем; проверяются существование, тип,
  владелец планеты и выбранная база **до** смены WorkPlanet/возврата ресурсов.
  Глобальное исследование по-прежнему можно отменить с другой своей базы.
  Проверка выполняется при публикации и повторяется при исполнении.
- read/delete сообщений и cancel/complete очередей не создают строку при
  неизвестном ID. Убрано такое же создание пользователей при заявке в друзья
  и чтении отсутствующего отправителя. Lazy Builds/Techs/Ships не изменены.
- Перенос кораблей: обе стороны свои, IDLE, без команд, фактически у выбранной
  своей планеты/луны. Нет переноса из полёта, между разными базами, в себя,
  из несуществующей группы. Опустевший удалённый донор не сохраняется повторно.
  Распределение опыта сохранено.
- GalaxyPage принимает целые координаты; getSystem/generateSystem проверяют
  MaxGalaxy/MaxSystem до генерации. Поиск домашней/свободной позиции ограничен
  одним обходом мира: continue не пропускает wrap. У Homeworld сохраняется
  позиция поиска. Физика звёзд/орбит и существующие объекты не менялись.
- Исключение при обработке состояния одного аккаунта не прерывает обработку
  остальных игроков. Повторяющаяся ошибка логируется не чаще раза в минуту
  с количеством повторов. Это не транзакция всех экономических эффектов;
  отказ глобальных боевых/mining-фаз требует отдельной обработки.
- Выбор планет игрока использует существующий owner_id-индекс вместо
  полного прохода по всем планетам мира на каждом аккаунте/запросе.
- Connect:2 048 соединений, collision pool1.0; отказ регистрации закрывает
  новое соединение1013/server_busy, без незарегистрированного сокета.
- Подписки:8 192 строки, максимум8 на соединение, collision pool1.0.
  Поиск/dirty/remove/delivered одного клиента читает не более8 адресуемых
  слотов вместо полной таблицы. pending пока проходит весь реестр один раз
  за flush. Отказ set не игнорируется. При глобальном лимите новые подписки
  отклоняются; действующие не вытесняются.
- Кэш revisions:16 384 строки, collision pool1.0. При заполнении вытесняется
  старейшая запись из ограниченной выборки64, а не выполняется полный LRU-scan.
  Новые версии берутся из общей монотонной sequence; обновление существующей
  записи не вытесняет другую. Это ограниченный кэш, не хранилище всех аккаунтов.
- Перед проверкой размера WebSocket-пакета больше нет лишнего json_decode;
  внешний callback перехватывает Throwable.

### 2А — компактные индексы и вместимость журнала

Внедрено в `src/Game/Repositories/BaseRepository.php`, без изменения клиентского
контракта, числовых ID и SQL-форматов игровых данных:

- Вместо сериализованной колонки2048B — двоичный блок130B: версия, число ID,
  до16 точных64-битных ID. Проверены нулевые байты, ID выше2^53 и предельный
  PHP_INT_MAX. Длинные группы по-прежнему разбиты на части.
  Индексы полностью восстанавливаются из SQL при старте. Чтение старых
  сериализованных блоков оставлено только для диагностических runtime-снимков.
- `runtimeLayout()` задаёт отдельные параметры main/index/sync. Main и индексы
  используют полный collision pool1.0. Новый объект сверх объявленного
  main-бюджета отклоняется до изменения строки/индексов/marker.
- Журнал вместо фиксированных2048 имеет2×main buckets и collision pool1.0:
  для типичного main16384 —32768 buckets. Это запас под живые dirty, чистые
  отметки существующих строк и ожидающие DELETE. Запись при исчерпании журнала
  по-прежнему откатывается, бесконечный рост при SQL-down не разрешён.
  Временный PlayerQueue без SQL получает64 buckets только для meta/ID.
- Уже сохранённые чистые markers пока остаются в журнале. Их удаление и
  generation-aware ACK требуют отдельной проверки параллельной записи;
  этот подэтап не объявляется исправлением всех возможных гонок saver.
- SQL count сверяется с main-бюджетом до загрузки строк конкретного репозитория.
  При превышении запуск не доходит до открытия игрового WebSocket.
  Загрузка идёт keyset-пачками512 по настоящему PRIMARY, включая составной
  ключ EntitySettings. В PHP больше не хранится весь SQL result set.
- При холодной загрузке индекс дополняется только последним блоком; growing
  группа не копируется заново на каждой строке. При обычных runtime-изменениях
  большой группы полное чтение/перезапись ещё остаётся — требуется следующий
  подэтап оптимизации membership. Повторный loadAll не дублирует существующие ID.
- Строгие проверки set/readback, before-image rollback и DELETE/restore сохранены.

физическая раскладка Messages сохраняет прежние логические SQL/wire-поля:

- Метаданные и256B inline-тело; более длинные тела — в ограниченном общем
  пуле блоков1024B. JSON с пятью строковыми полями сжимается deflate только
  если это уменьшает размер. Ограничения text1024/data8192B не увеличены.
- При исчерпании пула операция отклоняется с rollback, без усечения данных.
  Лимит строк не гарантирует вместимость такого же числа тел максимального
  размера: распределение payload и переполнение пула ещё надо нагрузочно проверить.
- Чтение/пагинация выполняются из RAM; SQL cold fallback нет. Счётчики читают
  метаданные, только показанная страница декодирует тела. Read-status не
  перевыделяет неизменённое тело. Замена тела публикуется до освобождения старого.
- Короткий межпроцессный guard защищает публикацию тела/строки/индекса и удаление.
  Сохранены non-creating lookup, checkpoint prepare/apply/rollback и SQL saver.
- При старте загружаются сообщения моложе7 дней; MAX(id) берётся из всей SQL
  таблицы. Runtime cleanup использует минутные buckets: до256 сообщений,
  64 buckets или20мс за проход. SQL удаляет до1024 истёкших строк раз в30с.
  Возможна минутная погрешность плюс очередь уборки, это не жёсткий deadline.
- Сохранённые боевые доклады остаются отдельными записями BattleReports и
  не удаляются вместе с истёкшим письмом.

### 2В — saver, membership и бюджеты

- Счётчик поколений общий до fork. Любое изменение, в том числе уже dirty,
  получает новую generation. ACK SQL снимает marker только при совпадении
  поколения и before-image; старый ACK не стирает новую запись. Чистые markers
  теперь удаляются. DELETE подтверждается только при отсутствии runtime-строки.
- Runtime и saver имеют разные короткие guards; SQL идёт вне runtime guard,
  saver сериализован. Checkpoint сохраняет существующий world barrier.
  Обычный saver всё ещё синхронный, не crash-атомарная транзакция всех эффектов мира.
- Membership записывает только изменённые блоки. Удаление заменяет ID последним
  элементом, поэтому меняются максимум затронутый блок и хвост. Порядок индекса
  не является контрактом; страницы/очереди сортируются явно. Чтение всей группы
  и before-images ещё остаются: нельзя называть весь путь O(1).
- Ограниченная storage-проба:20K dirty,12K DELETE, группа20K ID, uint64,
  rollback и старый/новый ACK — PASS(7,535с на одном запуске вместо26,668с).
  Это проверка структур, не20K аккаунтов работающего мира.
- Введены development/target. До первой Table проверяются SQL count всех
  репозиториев и модель выделения против70% физической/cgroup RAM. Это
  консервативный предохранитель, не измерение RSS и не гарантия отсутствия OOM.
- Development: модель1305,32MiB вместо1489,428MiB. Target-кандидат:
  Accounts32768, основные базы/флоты131072, Commands65536, Messages1048576,
  Orbits262144; точные значения в RuntimeCapacity. Баланс технологий и размеры
  текущего мира1×128 не менялись. Это не утверждённые пределы игрового развития.
- Target-модель8,472GiB на хосте3,76GiB: старт target корректно запрещён
  до выделения Table. На действующей игре оставлен development. Модель не

## Этап3 — планировщик и runtime

Уточнение пользователя04.11.2026: **игровой runtime работает только в RAM;
MySQL используется для сохранения состояния и загрузки при старте**. Прежние
SQL-пути ProtocolCommands, MiningCheckpoints и BattleReports перенесены в3Б2,
а не только ускорены.
Взаимодействие с кабинетом авторизации — отдельный сервис, не прямой доступ
игрового мира к БД кабинета. Политика потерь между последним снимком и аварией
согласована пользователем: **при аварии допустим откат к последнему успешному
снимку, сейчас интервал30с; в будущем интервал может быть увеличен**.
Новый дисковый WAL/синхронный SQL-журнал каждой игровой команды не требуется.
Настройка `GAME_SAVE_INTERVAL_SECONDS`(по умолчанию30, диапазон1–86400) позволяет
увеличить интервал без изменения кода; применяется при следующем запуске.
Deadline следующего снимка считается от начала предыдущей попытки, не от
завершения SQL плюс дополнительный интервал. При ошибке сохранения dirty
остаются и повторяются; во время недоступности MySQL возраст последнего снимка
может превысить настройку, поэтому это не безусловная гарантия RPO при отказе БД.
При штатной остановке нужен финальный согласованный снимок без намеренной
потери последних30с. Очередь принятых команд и их квитанции должны сохраняться
в одной транзакции с игровыми изменениями, иначе авария создаёт риск replay.

### 3Б2 — RAM-журналы и согласованная очередь при аварии

Применено04.11.2026 на основном dev. `RuntimeRecords` хранит записи со строковыми
ключами в ограниченных shared Table: ключ/версия/expiry, inline256B, сжатое тело
в блоках1024B, отдельный dirty-индекс. Все записи проверяются, переполнение
возвращает ошибку, а не усечённый JSON. SQL используется при bootstrap и в saver.

- ProtocolCommands: чтение/приём/завершение/TTL из RAM. Accepted не удаляется
  независимо от ещё ожидающей команды. Очередь PlayerQueue, её внешние payload,
  квитанции и изменения всех зарегистрированных репозиториев снимаются под
  одним world EX и коммитятся одной SQL-транзакцией. Восстановление очереди
  не стирает её SQL-снимок до следующего общего COMMIT. Старая epoch по-прежнему
  даёт unknown/runtime_changed; это не разрешение повторить команду.
- MiningCheckpoints: полный manifest и before/after публикуются в RAM до
  применения экономики. Pending блокирует снимок до roll-forward. Удалены
  принудительные SQL flush из добычи/обследования/слияния/сообщений добычи;
  проверка representability и точных before/after сохранена. Старые prepared
  SQL-журналы умеет читать bootstrap, но отдельный fault-прогон legacy prepared
  в этом этапе не выполнен.
- BattleReports и закладки читаются/сохраняются в RAM; периодический снимок
  пишет доклады перед закладками и удаления после них. Несохранённые доклады
  доступны7 дней; сохранённые не удаляются TTL. Runtime sweep и SQL-janitor
  ограничены порциями. Список закладок пока сканирует глобальные маленькие
  записи закладок: нужен owner-индекс перед целевой нагрузкой.
- Снимок копирует упакованные тела, не распаковывает всю историю докладов
  под world lock. В SQL-процессе распаковывается одна запись за раз.
  `GAME_SAVE_SNAPSHOT_MAX_MIB=128` ограничивает рост PHP heap при capture
  (настройка8–1024MiB). При превышении нет частичного COMMIT/ACK; dirty остаются.
  Это защитный отказ, не доказательство достаточности128MiB для целевого мира;
  рабочий набор/пики аллокации/время захвата ещё нужно измерить.
- ID выдаются из заранее подтверждённого резерва16384; отдельный persistence
  процесс пополняет его при остатке<8192. next()/advanceTo() SQL не вызывают.
  При длительном отказе БД исчерпание резерва отклоняет новую запись явно,

### 3К — ограниченная подготовка сенсорных снимков (B066)

10.11.2026 producer больше не собирает Fleet/позиции/составы всех целей мира,
общий route-cache и большой результат одного наблюдателя до проверки размера.

ID и ограничен ёмкостью runtime-репозиториев, не декартовым произведением DTO.

### 3О — адресные индексные блоки и их undo (B071)

Реализовано12.11.2026 в `src/Game/Repositories/BaseRepository.php`, без смены
игровых ID, SQL-схемы, клиентского протокола или механики. Вся игра остаётся
в RAM; MySQL — загрузка и существующий периодический/финальный снимок30с.

Вместо before-image всей неуникальной группы:

- Головной блок хранит общий count в своей служебной колонке id. Бинарная
  версия2 сохраняет прежний формат тела: header2B + до16 точных uint64 ID,
  размер колонки130B. Это версия внутреннего индекса, не новый протокол игры.
- Одна служебная shared Table на репозиторий с неуникальными индексами:
  строка на ID, на каждый такой индекс24B (hash группы16B, позиция8B).
  Это не dirty-marker и не SQL-таблица. Пустая строка позиций удаляется.
  Все позиции строятся из SQL-образа при штатной загрузке, до fork/клиентов.
- add читает/пишет только head и хвост; remove ID — head, его блок и хвост,
  переносит последний ID на освободившееся место и исправляет две позиции.
  Дубликат проверяется по точной позиции. Группу целиком не декодируем.
- add/update/delete/discard/restore используют общий ограниченный journal
  изменяемых native-строк: блоки индекса и позиции. Каждый before-image сохраняется
  один раз, компенсация reverse-order; main и dirty-marker возвращаются точно.
  Самостоятельные protected операции тоже имеют локальную компенсацию.
- Удаление всей группы действительно меняет все её записи и имеет undo O(H).
  Последовательные отдельные удаления больше не пересобирают уменьшающийся
  список H раз. Подготовка отсортированного ID-view по-прежнему O(H log H).
- Старые диагностические binary-v1/serialize списки читаются и однократно
  переводятся в новый формат при первой записи. Этот compatibility upgrade

### 3Т — owner-индекс сохранённых боевых докладов (B076)

Реализовано13.11.2026 в BattleReports. Прежний savedFor читал и распаковывал
весь RuntimeRecords BattleReportSaves, затем фильтровал игрока. Новый
производный PHP-индекс `user_id → report_id → saved_at` строится во время
той же стартовой загрузки, без дополнительного runtime SQL. При save/unsave
metadata публикуется только после успешной записи закладки и saved_count;
ошибка/повторный save не меняют индекс, пустая owner-группа удаляется.

В текущем явно заданном SWOOLE_BASE/worker_num1 запросы, команды и gameplay
выполняются одним authority-worker. Saver/task workers не используют owner-
индекс; ACK не меняет состав живых закладок. Индекс не объявлен пригодным для
произвольного multi-writer режима. После рестарта он заново выводится из
согласованного снимка, отдельно не сохраняется. Форматы SQL/снимков/DTO,
права, TTL, порядок saved_at DESC/report_id DESC и страница30 прежние.

Запрос больше не зависит от чужих N: выбирает и сортирует только свои K,
CPU O(K log K), scratch O(K), затем читает не более30 докладов. Это не O(1)
для большого собственного архива. Постоянная metadata O(N), не более числа
живых RuntimeRecords-закладок; пустые owner-группы не накапливаются.
На отдельном чистом PHP8.2.33 расчёте262144/20000 индекс занял31226032B
дополнительного heap (пик CLI33140872B). Нет создания мира/Table/SQL в этом
измерении; это не RSS всех процессов, не изменение модели native Table и
не доказательство target/SLO. Новое выделение учитывается сверх shared-модели.

### 4Е1 — резерв результата боевых TaskWorkers(15.11.2026)

Подтверждён риск старой записи: worker делал Table::set(token) без проверки
жизненного цикла задания. После timeout/cleanup поздний ответ мог заново
создать строку и занять место, хотя координатор больше не ждал этот token.
Очистка на следующем tick не гарантировала место для уже принятого результата.

Теперь общий `WorkerMailbox` используется обычными и экспедиционными боями:

- Координатор физически резервирует пустую строку до checkpoint/dispatch.
  При полном буфере не создаёт job и не расходует попытку; раунд ждёт места.
- Worker под общим mutex обновляет только существующий резерв. После закрытия
  token поздний ответ игнорируется, не создаёт строку и не замещает новый job.
  Точный дубликат идемпотентен, другой ответ того же token отклоняется.
- Размер результата проверяется до Table::set; чтение проверяет полные байты.
  Timeout, приём результата и отказ dispatch освобождают резерв. В экспедиции

### 4Е4И — проверка участия флотов в бою за один проход

Планировщик использует один поиск участников SpaceBattles при выборе очередной
команды из due heap. После исполнения команды следующий выбор заново видит состав
боёв. Свои проходы используют пересчёт дружественной охраны и обновление
перехватчиков. Оба могут менять команды флота, а бои меняются за пределами
этих проходов.

Поиск по требованию читает ключи и собирает целочисленные ID участников до
первого совпадения. При ошибке курсор остаётся на повреждённой строке.
Бюджет временного набора составляет 4096 ID. Если следующая запись может
превысить бюджет, проход освобождает набор и использует обычный forFleet.
Это ограничивает память метаданных при произвольном размере боя.

с 456,83 до 17,32 мс. Каждый тестовый checkpoint занимал 262144 байта.
