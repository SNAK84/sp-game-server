# B009 — сохранение отсутствующего токена

29.10.2026. Изменены Accounts и SQL-сериализация BaseRepository. Frontend,
WebSocket-протокол, SQL-схема и uniq_token не изменялись.

## Причина

Logout сразу удаляет старый runtime-индекс и ставит token="" в Swoole.
Swoole не индексирует пустой ключ. SQL-поле nullable, но общий saver передавал
в него строку "": два logout конфликтовали по UNIQUE. InnoDB отклонял batch,
dirty markers оставались, а SQL сохранял прежние значения токенов.

На основном сервере причина воспроизведена29.10 в16:43:09 МСК на существующих
QA15/16: оба вышли обычными WS-запросами; saver получил1062/uniq_token.
В SQL по-прежнему были их прежние128-символьные токены. Для безопасного restart
оба QA снова вошли и дождались обычного сохранения. Значения секретов нигде
в диагностический вывод/артефакты не копировались; существующая проблема
auth-логирования B017 этим этапом не исправляется.

## Исправление

В описании Accounts.token добавлен только флаг sql_empty_as_null=true.
Swoole и API по-прежнему используют пустую строку. При SQL-записи saver и
точечный flush преобразуют ровно '' в NULL только для явно помеченного поля.
Другие поля/репозитории и непустые токены не меняют представление.
Логика авторизации, формат ACK и проверка UNIQUE сохранены.

Миграция/ручная SQL-запись не выполнялись. Фактическая существующая колонка —
nullable varchar(255), uniq_token — уникальный индекс по token. Одиночная
историческая SQL-строка с token='' не мигрировалась: при следующем обычном
сохранении получит NULL; записи новых NULL она не мешает.

## Проверки на основном dev-сервере

```bash
python3 tests/AccountsTokenLiveTest.py --dev restart
```

Тест использует настоящие WS login/logout двух существующих QA и SELECT
основной БД; SQL-записи, второго мира и второго игрового сервера нет.
В режиме restart ждёт Enter после штатного перезапуска внешним менеджером.
Пароли/токены остаются в памяти процесса, вывод содержит только ID/длины/булевы проверки.

- После двух logout saver сохранил оба token как SQL NULL без1062.
- Старые и пустой token не дали доступ к overview.
- Штатный restart: финальное сохранение16:48:30 МСК, контейнер16:48:32,
  WebSocket готов16:48:58. Оба NULL сохранились; старый/пустой token отвергнуты
  уже новым worker после загрузки мира.
- Каждый QA вошёл дважды: токены ротировались, предыдущие отвергнуты,
  актуальные различаются между аккаунтами и совпали с сохранёнными SQL-значениями.
- В настоящем SPA QA15 вошёл и нажал «Выход» реальным WebDriver-кликом:
  получен login/login ACK без token, показан LoginPage, JS errors отсутствуют.
  После обычного saver QA15.token IS NULL; после reload осталась LoginPage.
- Число аккаунтов11 и уникальность индекса сохранились. С момента установки
  исправления не зарегистрированы Accounts sync errors/ERROR/CRITICAL/Fatal.
- PHP lint обоих изменённых файлов и Python syntax пройдены. Отдельный
  изолированный suite не запускался; checkpoint flush Accounts не вызывался.

В SPA выявлен B040: старый token остаётся в sessionStorage после logout.
Доступ он не даёт. Протокол и клиент будут исправляться отдельным этапом.
Периодический saver не заменён немедленной durable-записью каждого auth-события.

Файлы: `src/Game/Repositories/Accounts.php`, `src/Game/Repositories/BaseRepository.php`,
`tests/AccountsTokenLiveTest.py`, `docs/found-bugs.md`, этот отчёт.
