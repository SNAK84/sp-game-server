# B044: раунды боя через существующий ActualData

Исправлено01.11.2026. Изменён только текущий backend `/opt/sp-game`;
производственные файлы SPA и старые версии игры не менялись.

## Причина и исправление

FleetBattleService::tick передавал раунд TaskWorker и сохранял checkpoint,
но возвращал void. EventLoop получал получателей battleAccounts от адаптеров
FleetAttackService/FleetSpaceBattleService при завершении боя. Само изменение
раунда не инициировало push. Клиент корректно рисовал имеющийся snapshot,
но мог видеть только round0 → battle=null после реальных10 раундов.

Публичный round вычисляется как число готовых раундов плюс1 при активном job.
Поэтому изменение отмечается после успешной передачи job: round1 и round10
видны во время вычисления, а не только после готового результата. Завершение,
сохранённый timeout/retry/failure также отмечаются. На неизменившемся tick
новая рассылка не добавляется.

tick теперь возвращает account IDs. Владельцы берутся из attackerId,
defenderId, participants и waiting; положительные ID дедуплицируются.
Преобразование owner→account выполняется после боевого try/catch, чтобы
ошибка поиска получателя не переводила успешный расчёт в failed.
EventLoop объединяет список с существующими battleAccounts и отправляет
онлайн-участникам обычный ActualData через прежний PageBuilder/WS-путь.

Публичный battle по-прежнему содержит только phase/round/rounds_max.
Ни новый тип сообщения, ни polling, ни изменение клиентского state management
не вводились. Правила боя, RNG, урон, опыт, раунды, TaskWorker и применение
результата не менялись.

## Производительность и индекс команд

Первый функционально правильный вариант выявил задержку: полный fleets Page
на QA9 с37 базирующимися и12 летящими флотами занимал1,69–2,28с.
Промежуточные бои после добавления push длились30–50с вместо исходных11с.
Этот вариант не был оставлен конечным результатом.

Временный профиль Page показал FleetList1,205с, FlyingFleets0,528с,
FleetTargets0,227с; остальные три компонента суммарно около0,011с.
Частые выборки команд каждого флота обходили всю общую Table, хотя runtime
индекс fleet_id уже существовал и поддерживался BaseRepository.

getActiveCommands/getNextPendingCommand/getFleetQueue/getFleetCommandChain
теперь читают этот индекс. Предикаты и сортировка по id остались прежними;
последний метод по-прежнему включает выполненную/отменённую историю.
Для read-only копий без инициализированного индекса остаётся прежний полный
проход. Схема, ёмкость, числовые ID и глобальная due-выборка не менялись.

Профилирование FleetsPage удалено полностью; файл совпал с побайтовой
копией начала B044. Эта оптимизация нужна для новой частоты обновлений,
а не является отдельным переписыванием репозитория или новым B045.

## Границы и воспроизведение

Массовые одновременные бои/1000 онлайн, аварии TaskWorker и timeout/retry
специально не вызывались. Для waiting-подкреплений проверен общий путь
формирования получателей в коде, но новый живой подкрепляющийся флот здесь
не отправлялся. Полный перезапуск с активным боем в этом этапе не проверялся;
подтверждено обычное сохранение законченных результатов в MySQL.

Это stateful QA-сцены: повтор использованной фазы запрещён. Для новой проверки
нужны свежая ограниченная сцена/фаза и подключение до startAt, без удаления
старых флотов и докладов. Команды и условия — в [tests/README.md](../tests/README.md).
Штатные остановки/запуски выполняются manager, основной сервер запускается
в finally даже при отказе подготовки. Общий baseline не запускался.
B040 и пересмотр клиент-серверного протокола этим исправлением не затронуты.
