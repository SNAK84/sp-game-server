## Представление базы

| Вид приписки | home_planet_id | home_site_id | fallback_planet_id |
| --- | --- | --- | --- |
| Старый планетарный флот | ID своей планеты/луны | 0, при чтении старой схемы отсутствует | 0 означает прежнюю домашнюю планету/луну |
| Планетарная приписка после штатного изменения | ID своей планеты/луны | 0 | тот же ID |
| Ресурсная приписка | 0 | ID объекта/сектора | ID своей резервной планеты/луны |

siteId никогда не передаётся как Planet ID. Виртуальная планета и пустые
планетарные ресурсы не создаются. Нельзя одновременно хранить две домашние
базы; у ресурсной приписки обязателен положительный резервный адрес.

`ResourceBases` — отдельный разреженный реестр **занятых** баз:
первичный id=siteId, owner_id, created_at, updated_at. Он не содержит
копию G/K, трюмов, ангаров, складов или список слитых в один флотов.
Владелец базы не выводится из единственного controller_fleet_id:
это поле OrbitalResourceSites остаётся прежней неиспользуемой заготовкой.
Уход одного флота в будущем не должен удалять реестр, если осталась охрана.

У реестра индекс владельца содержит только занятые базы. Индекс owner_id=0
на всех свободных объектах не вводится. Во Fleet также не добавляется
runtime-индекс home_site_id=0 со всеми старыми флотами: для лимитов достаточно
существующего индекса owner_id и проверки своих немногочисленных строк.

Чтение неизвестного ResourceBases::findById не создаёт default-строку.
До инициализации реестра безопасное чтение возвращает null/пустой список;
изменение приписки отклоняется до любых мутаций.

## Service

`ResourceBaseService` предоставляет:

- Разрешение домашней координаты планеты/луны либо занятого своего siteId.
  Потеря владельца не превращает чужую базу в допустимую домашнюю цель.
- Выбор резерва: сохранённая собственная планета/луна; если она недоступна,
  первая собственная планета по ID, затем луна. Если своих объектов нет —
  явная ошибка для будущего обработчика паузы/эвакуации, не удаление флота.
- Согласованные лимиты: T0→0 баз, при T>=1 —1+floor(T/2); собственных
  приписанных флотов2+Логистика; дружественной охраны — уровень Логистики.
- Подсчёт места на конкретной базе: приписанные флоты, включая находящиеся
  в рейсе, плюс входящая передислокация с конечной STAY на тот же siteId.
  Не смешиваются разные сектора одной орбиты и планетарные места.
- `prepareRebase`: готовность runtime-схемы, владелец, непустой состав,
  отсутствие боя, фактическая OBJECT-координата объекта, отсутствие другой
  текущей команды (кроме STAY), принадлежность базы, свободное место и резерв.
  Чужая/удалённая/неизвестная база не становится своей из-за одного siteId.
- `rebase`: повтор prepare перед записью, существующий FleetControl commit,
  установка трёх полей и проверка сохранённого runtime. При исключении
  действует прежний rollback снимка Fleet/команд; сама база, G/K и ресурсы
  планеты этой операцией не меняются. SQL-транзакций и нового saver нет.

`prepareRebase` не занимается захватом, активацией STAY, превращением статуса
флота в IDLE или запуском полёта. Оно не вызывается из текущего API. Именно
поэтому неподключённые пути, ещё предполагающие home_planet_id>0, пока не
могут получить новый ресурсный флот через игровую команду.

## Совместимость с работающим мастером

Новые getters считают отсутствующие поля нулевыми. Планетарный setter не
пишет новые поля в строку старой схемы; ресурсный setter явно отказывается
работать без обеих колонок. Это защита подготовительного состояния, а не
обещание полноценного hot upgrade Swoole Tables.

Новый реестр зарегистрирован в штатном main/init. После будущего полного
restart стандартный Repository init создаст SQL-таблицу и две колонки,
загрузит Tables и подключит прежний RepositorySaver. На этом шаге restart
и DDL не выполнялись. Даже появление схемы само по себе не включает занятие,
приписку, добычу, захват или новый интерфейс.

Новые числовые значения: миссия CAPTURE=45, команда CAPTURE=60. Старые

Условия контроля — непустой состав с хотя бы одним кораблём с базовой
атакой>0, Внеземная добыча>=1, лимит баз, место приписки и собственный резерв.

Подготовлены цепочки:

```text
Захватить свободный объект:
LOAD на своей планете/луне → прежний MOVE-путь → CAPTURE → STAY у объекта

Передислокация на свою ресурсную базу:
LOAD на своей планете/луне → прежний MOVE-путь → STAY у объекта

Прежняя передислокация на планету/луну:
LOAD → MOVE → UNLOAD → STAY (без изменения)
```

Входящие занятия резервируют лимит разных баз по siteId; несколько рейсов
на один объект не считаются разными базами. Места учитывают также входящие
передислокации/занятия с конечной STAY на тот же siteId. При прибытии заново
проверяются фактическое владение и приписанные флоты: если во время рейса
уровень уменьшился, старые входящие заявки не блокируют друг друга навечно.
Существующие сверхлимитные базы/флоты не удаляются.

Для нового занятия проверяется свободный объект. Если ко времени прибытия
его уже занял тот же владелец другим флотом — возможно обычное добавление
приписки при свободном месте, без второй записи базы. Если объект чужой —
бой не начинается: команда получает pause=plan и planError, флот остаётся
физически у цели с прежней домашней планетой. Для этих новых состояний
CAPTURE/ресурсной STAY разрешён отзыв; пауза execute_time=0 не возвращает
время в прошлое и не превращает стоянку в межсистемный переход. SpeedFactor
сохраняется в обеих командах. Прежнее ограничение отзыва OBSERVE не менялось.
Отзыв не выдаёт бесплатное топливо: прежняя проверка достаточности остаётся.

### Точка commit

CAPTURE и ресурсная STAY активируются как отдельное due-событие существующего
EventLoop, подобно RESEARCH/MERGE. Они не выполняются внутри внешнего commit
запуска или завершения MOVE. Только при обработке прибытия:

1. Повтор проверки фактической OBJECT-координаты с siteId, команды и условий.
2. Для свободного объекта — запись ResourceBases id=siteId/owner/time.
3. Приписка Fleet home_planet_id=0 / home_site_id / fallback_planet_id.
4. Окончание CAPTURE+конечной STAY либо ресурсной STAY: IDLE, mission=0,
   очистка start/target и завершённой цепочки штатным репозиторием.

Это один локальный FleetControl commit. CAPTURE и следующая за ней STAY
завершаются совместно: между ними не остаётся отдельного event со владением
без завершения приписки. Ресурсная STAY допускается только как последняя
команда передислокации либо возвращение на уже свою текущую базу; произвольная
STAY не даёт право переприписать флот. Передача домой на ресурсную базу ещё
не подключена к построителю обычных возвратов.

В операции нет UNLOAD/выдачи ресурсов/фиктивного Planet: груз, бак, состав,
имя и опыт остаются на борту. G/K и геологоразведка не меняются. Показанный
расход до объекта включает резерв обратного пути; можно загрузить больше
для будущей стоянки до предела трюма с учётом груза. Это ещё не обработчик
расхода стоянки и не гарантия бессрочного удержания.

При исключении FleetControl восстанавливает Fleet и цепочку. Новая запись
базы дополнительно компенсируется, существующая своя база не удаляется.
Сначала проверяется восстановление Fleet: при отказе rollback нельзя удалять
базу из-под уже сохранённой ресурсной приписки. Такой отказ логируется как
critical и требует восстановления согласованности. Владелец, изменившийся
после записи, также не затирается компенсацией.

Это **не** межрепозиторная crash-транзакция: авария процесса/несогласованный
SQL-flush/отказ компенсации остаются рисками. Повтор старого due snapshot
после успешного окончания не применяет занятие снова — его команды уже нет.
Межпроцессный CAS/lock не добавлялся; при подключении других писателей
владения нужна отдельная проверка гонок. Общий B006 не исправлялся.

## Этап5А.4 — топливо стоянки, потеря базы и резервный дом

### Расход и резерв

- В Fleets добавлены четыре численных поля: `base_fuel_time`,
  `base_fuel_rate`, `base_fuel_reserve`, `base_fuel_speed`, default0.
  Это checkpoint в той же строке флота, не длинный JSON в PlayerQueue.
  Скорость расхода сохраняется DOUBLE без фиксированного округления.
- При завершении CAPTURE/ресурсной STAY внутри commit задаются время,
  10% базового расхода кораблей/ч (существующий настраиваемый
  FleetHoldFuelPerHourFactor), резерв перелёта к запасной собственной
  планете/луне и выбранный speedFactor. Стоянка оплачивается **из бака**.
  Запасы объекта, планетарный дейтерий и трюм не используются.
- Резерв рассчитан по максимальной стоимости эвакуации при той же
  скорости; автоматический возврат не повышает её до100%.
  Резерв не добавляется в бак: при исходной нехватке топлива работает
  обычная остановка, а не бесплатная дозаправка.
- standingProjection вычитает rate×прошедший интервал, но не резерв;
  checkpoint останавливается на моменте его достижения. Повтор времени
  не оплачивается повторно. Готовность эвакуации включена в существующий
  chronological FleetEventScheduler как неперсистентное событие с
  отрицательным служебным ID site, не новая FleetCommands/миссия.
- settleWorld начисляет оплаченные интервалы и offline-флотам.
  Нельзя сначала начислить простой до now и затем исполнить более ранний
  прилёт: due события базы выбираются вместе с существующими событиями.
- Preview/старт вылета учитывают начисленный расход, при старте clock
  снимается. Rollback старта возвращает clock вместе с баком/очередью.

### Уход охраны и потеря базы

- Уход одного стоящего боеспособного своего флота не освобождает базу,
  если остался другой. При уходе последнего владельческая строка удаляется.
  Груз/корабли не списываются и запас ресурса не увеличивается.
- При потере дома своим приписанным флотам выбирается существующая
  собственная резервная планета/луна. Стоящие начинают обычный возврат;
  улетевшие получают новый дом. Явная внешняя цель транспорта сохраняется,
  а неявный помеченный home-tail перенаправляется после доставки.
- Уже возвращающийся внутрисистемный флот разворачивается из физической
  позиции существующим recall-path, с возвратом неиспользованной части
  оплаченного участка. Межсистемный/межгалактический переход не обрывается:
  перенаправление выполняется после входа. Телепортации к резерву нет.
- Preview транспорта, вылетающего последней охраной, считает обратное
  топливо уже до резервной планеты, не до будущей пустой базы.
  При ресурсной передислокации с ресурсного дома резерв тоже рассчитывается
  до запасной планеты, а не до исходного объекта.
- Если собственных планет/лун вообще не осталось, флот не удаляется и
  Planet0 не создаётся. Он паркуется с явным pause=base/lostBase;
  незавершённый переход сначала доходит до физического входа. Исторический
  siteId не считается действующим владением. Обычный Resume эту проблему
  не обходит; UI назначения нового дома ещё нужен.
- Изменения своих Fleet/команд выполняются совместным FleetControl commit;
  удаление ResourceBases компенсируется при ошибке. Ошибка компенсации
  отдельно логируется CRITICAL. Это runtime compensation, не гарантия
  единой SQL-транзакции всех RepositorySaver flush.
- Сообщение через существующую Notification/Messages содержит имя флота,
  причину, ресурсный объект, новый дом, остаток бака и факт топливной паузы.
