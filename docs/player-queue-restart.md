# B036: ожидающая PlayerQueue при штатном restart

27.10.2026, основной dev `/opt/sp-game`; настоящий SPA `https://sp-game.ru/`.
Другой игровой сервер и изолированные Swoole-тесты не запускались.

## Причина и исправление

Раньше immediate ACK означал только публикацию ready=1 в Swoole Table.
Короткий payload и внешний PlayerQueuePayloads не входили в RepositorySaver.
B032 сохранял уже применённый мир, но не ожидающие события.

Теперь после успешного strict save мира Shutdown сохраняет только ready=1
события в отдельную `player_queue_restart` (InnoDB, ID + ограниченный blob).
В снимке полный payload, ID, владелец, планета, priority/added_at и остаток TTL
большого payload. Размер runtime-колонки остаётся512байт, квоты1024/4 и
максимум16384байта payload сохранены; постоянно увеличенного резерва RAM нет.

До запуска WSocket очередь восстанавливается через обычную публикацию:
проверяются строка, индексы и внешний payload, восстанавливается last_id.
Порядок полей JSON нормализуется перед строгим сравнением с Table::get.
SQL-снимок потребляется транзакционно только после успешной загрузки всех
строк. Ошибка запрещает startup; SQL-снимок остаётся для исправления/повтора.

После старта события выполняет обычный EventLoop. Shutdown не запускает
игровой цикл, бой, новые TaskWorker-задачи или сетевые push. Периодический
saver не записывает очередь: старый журнал иначе мог бы повторить уже
применённую команду. Ошибка финального снимка запрещает успешный marker
финального сохранения и даёт ненулевой выход существующим путём B032.

Это передача между **штатными** запусками, не WAL/полный exactly-once протокол.
Не заявлена защита от SIGKILL, отказа SQL, crash посреди межрепозиторного
flush или между потреблением снимка и запуском игрового цикла. Игровая
доступность команды после простоя проверяется повторно, как и раньше.
Уже истёкший в runtime payload не возрождается; выключенное время сервера
не расходует сохранённый остаток TTL.

## Что действительно проверено

### Обычные публичные ACK + stop

Через основной WebSocket выполнялись RenameFleet и SetFleetCommands на
QA120/121 аккаунта qafor_260924. ACK получены, штатные остановки ExitCode0,
но в этих прогонах события успевали примениться до финального snapshot,
его count был0. Это положительная проверка обычного пути, **не воспроизведение
исчезновения ещё не применённого ACK** и не доказательство непустой очереди.
Пробовался контролируемый SIGSTOP/SIGCONT с обязательным finally-resume;
SIGKILL/удаление логов не применялись. Постоянных тестовых hooks в runtime нет.

Установлен Swoole5.1.6; Reflection конструктора показывает mode1, BASE.
PID контейнера в do_wait не является event-worker с игровым tick. Не добавлено
искусственное управление таймерами/новый механизм отправки ради этого теста.
Исходники lifecycle: [server master](https://github.com/swoole/swoole-src/blob/v5.1.6/src/server/master.cc),
[PHP Shutdown callback](https://github.com/swoole/swoole-src/blob/v5.1.6/ext-src/swoole_server.cc).

Offline fixture `migrations/20261027_player_queue_restart_qa.php` использует
только SQL, без создания игровых Tables/второго сервера. QA120 уже существовал:
1 малый транспорт, XP40, своя база27[1:10:5].

- Подготовлены события1001/1002 с временно недоступным тестовым account_id65535
  (сам такой аккаунт не создавался): RenameFleet64байта и SetFleetCommands654байта.
  Большой payload имеет TTL90с, настоящий план из двух точек и возврата,
  погрузка71M/37C/19D и100 топлива. Игровых эффектов на этой фазе нет.

  те же ID, данные64/654байта; остаток большого TTL52.181946992874146с.
- Offline `--activate` меняет только fixture-владельца на настоящий QA16/user10.
  Первая попытка честно отклонила маршрут по лимиту11/11, короткая команда
  выполнилась. Это подтвердило, что recovery не обходит игровую валидацию.
- Только QA user10 получил computer_tech12 вместо10 для параллельных миссий.
  Повторный fixture восстановлен16:04:25.638 и исполнен обычным tick16:04:27:
  имя `QA Restart restored`, одна LOAD454, MOVE455, бак97, груз71/37/19.
  Видимая карточка и raw Page в реальном SPA совпали.
- Штатный повторный stop16:05:16.502 сохранил count0. SELECT-only `--verify`:
  одна LOAD454, бак97, груз71/37/19, pending0. Последующий старт16:05:30.878
  восстановил0 событий — повторной LOAD нет.
- В16:06:10.726476 естественно окончился MOVE455 и начался уже имевшийся
  MOVE456 до16:09:49.726476. После restart SPA показал бак95 и прежний груз,
  SELECT-only16:07 подтвердил **ту же единственную LOAD454**, состав1/XP40.
  Изменение MOVE/расхода здесь — нормальное продолжение времени, не replay.
- После полного reload SPA карточка120 также видна: MOVE456, бак95,

  фиксирует все71/37/19 ресурсов и92D возвращённого топлива.

`--verify` следует запускать после periodic/final flush, пока рейс продолжается:
сам immediate ACK или raw SPA ещё не гарантирует актуальный SQL snapshot.
После естественного окончания команды очищаются обычным движком, поэтому
исторический `--verify` не предназначен для произвольного более позднего запуска.

### Статические проверки

Пять новых чистых контрактов: типы/идентичность, отбраковка ready/полей,
TTL/размер, порядок JSON-колонок, точная граница16384байта. Baseline обновлён
до **CoreContracts178/0**. PHP lint — для каждого изменённого PHP-файла.

Дополнительная живая регрессия добычи: старый `--verify-complete` сначала
остановился на устаревшем требовании текущего владения базой6. К этому времени
QA116 уже вернулся, записи resource_bases6 не было. Только у финального режима
снята эта временная привязка (T004); все экономические проверки оставлены.
Повторный SELECT-only прогон положительный:117 доставил271.2801972495185D
и4936.304498767187D топлива;118/119 сохраняют1600D, XP240/360 и корректный
расход стоянки. Это правка теста, не изменение контроля ресурсных объектов.

Финальный health-check: main running, startup16:05:30.878, после него0 новых
ERROR/CRITICAL, PlayerQueue0. Собственная Selenium-сессия закрыта, чужие
подключения не трогались. QA120/121 завершили обычные маршруты с возвратом;
основные аккаунты не менялись. Только QA user10 получил computer_tech12.
