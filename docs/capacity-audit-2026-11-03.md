# Аудит сервера: 20 000 аккаунтов / 1 000 онлайн

Дата: 03.11.2026. Проверена текущая рабочая версия после полного перехода на v2,
а не только Git HEAD. Отчёт Claude от01.11.2026 13:46 использован как checklist,
но его выводы не перенесены автоматически. Кабинет читался только в части
актуальной авторизации. Исторические проекты не менялись.

После согласования начаты исправления: текущие изменения и оставшиеся этапы
ведутся в [плане стабилизации](capacity-hardening-plan.md). Ниже сохранён
исходный результат аудита; его размеры/статусы не выдаются за состояние после
исправлений. JSON — исходный снимок, `bin/audit-capacity.php` читает текущие схемы.

## Вывод

**Текущий сервер не рассчитан на этот объём.** Ограничение возникает задолго
до доказанной способности обслужить1 000 игроков: вмещаемость runtime-таблиц,
sync markers, реестра соединений и модели хранения истории недостаточна.
Добавлять одинаковый множитель всем Table нельзя: нынешняя модель уже
резервирует примерно **2,02 GiB общей памяти таблиц**.

Переполнение Table обычно означает отказ записи/исключение, а не обязательно
SIGSEGV. Основные последствия — отказ входа/команд, откат отдельной операции,
повторяющийся сбой tick, невозможность startup. OOM может завершить процесс
или контейнер; это другой механизм. Исторический core не исследовался и не
менялся: по этому аудиту нельзя приписать ему конкретную причину.

Ни теста1 000 реальных соединений, ни загрузки20 000 игровых аккаунтов не
выполнялось. Это проверка кода, текущего окружения, агрегатов SQL и ограниченных
проб установленного расширения, а не подтверждение production throughput.

## 2. Версия расширения важнее предположений

Из работающего контейнера: PHP8.2.33, **Swoole5.1.6**, x86-64. Это не OpenSwoole,
несмотря на нынешний Dockerfile с `pecl install openswoole`. Отсюда:

1. `Table(N)` — число hash buckets и дополнительный collision pool, а не
   гарантированная вместимость N произвольных ключей.
2. На этой версии все TYPE_INT занимают sizeof(long)=8 байт. Размер1/2/4
   в declaration сам по себе не доказывает переполнение на127/32767.
   SQL TINYINT/SMALLINT и бизнес-границы проверяются отдельно.
3. У getMemorySize()5.1.6 есть существенная особенность: create() сохраняет
   оставшийся размер collision pool после вычитания основных рядов/указателей.
   Нельзя выдавать это число за всю shared allocation. Аналогично
   memory_get_usage() в игровом логе не показывает весь mmap/Swoole/RSS/swap.
4. Минимальный размер buckets —64: mailbox с new Table(16) или(32) фактически
   округляется до64. Это тоже учтено, а не принято за16/32 доступных задания.

Проверены upstream именно5.1.6:
[TableColumn/sizeof(long)](https://github.com/swoole/swoole-src/blob/v5.1.6/include/swoole_table.h),
[allocation/collision pool](https://github.com/swoole/swoole-src/blob/v5.1.6/src/memory/table.cc),
[PHP-обёртка](https://github.com/swoole/swoole-src/blob/v5.1.6/ext-src/swoole_table.cc).
Собственная численная модель и пробы не заменены документацией другой версии.

### Ограниченные пробы

Первый отказ на этих **конкретных** наборах ключей:

| Buckets | Ключи | Успешно вставлено | Следующая вставка отказала |
| ---: | --- | ---: | ---: |
|1 024|decimal1,2,…, аналог FD|454|455|
|2 048|decimal1,2,…|1 076|1 077|
|8 192|decimal1,2,…|5 143|5 144|
|16 384|decimal1,2,…|9 257|9 258|
|4 096|sha256-prefix32, детерминированный набор|2 858|2 859|

Это не универсальные пороги для любых FD/ID. Они доказывают, что запас по
collision pool обязателен. Даже теоретический максимум16 384+3 276=19 660
при default0.2 меньше20 000, а конкретный hash-профиль может отказать раньше.

## 3. Количество записей, а не только игроков

Без дополнительных лимитов технологии не дают конечной верхней границы
планет/флотов. Поэтому целевые20 000/1 000 сами по себе недостаточны для
окончательного выбора размеров. Для проектирования следует закрепить бюджет:

| Сущность | Минимальный сценарий | Рабочий сценарий для расчёта |
| --- | ---: | ---: |
|Аккаунты, игроки, Techs, UserResources|20 000|20 000 плюс запас миграций/QA|
|Планеты/луны и связанные Builds/Ships/Defenses/PlanetResources|20 000|100 000 баз: по5 на аккаунт; луны входят в это число|
|EntitySettings|несколько на базу|700 000 при7 настройках на100 000 баз|
|Постоянные Fleets и FleetsShips|20 000 при1 флоте на аккаунт|100 000 при5; FleetsShips — строка на флот, не на тип корабля|
|Активные маршруты|1 000 флотов|3 000 флотов: по3 на онлайн-игрока|
|FleetCommands|6 000 при6 командах/флот|30 000 при10 командах/флот, без истории/пиков|
|Дружба|10 000 рёбер при среднем1 друге|100 000 рёбер при среднем10 друзьях|
|Сообщения за7 дней|140 000 при1/день/аккаунт|700 000 при5/день/аккаунт|
|Подписки|2 000 при2/онлайн|до8 000 по нынешнему публичному лимиту8|

Это **сценарии**, не утверждённое изменение баланса. В текущем SQL мира
MaxGalaxy=1/MaxSystem=128;28 уже созданных систем имеют196 обычных орбит.
Для20 000 игроков надо отдельно расширить и проверить ёмкость самой вселенной,
а не только Users. Ошибка выхода поиска Homeworld за MaxSystem не является
допустимым способом такого расширения.

## 4. Подтверждённые ограничения и риски

### C01 — P0 для целевого масштаба: основные таблицы не вмещают20 000

`BaseRepository::$tableSize`16 384 применяется к Accounts/Users/Techs,
UserResources, Planets и связанным таблицам; Fleets/FleetsShips/FleetCommands
имеют тот же default. Инициализация делает SELECT * → fetchAll → add каждого
ряда. Нет active working set, архивного SQL-чтения или резидентного eviction
игровых сущностей. Превышение обрывает загрузку/запись; смена php memory_limit
не расширяет Table.

Код: BaseRepository.php:29,78–110,202; Resources.php:PlanetResources/UserResources;
Techs.php:init; Ships.php:init; FleetsShips.php:init.

Нужно: бюджеты по сущностям и механике, headroom по collision pool и памяти,
проверка startup SQL-counts **до** загрузки и диагностика отказа. Для истории
и неактивных данных — отдельная стратегия, а не одинаковое увеличение Table.

### C02 — P0 для1 000 онлайн: Connect(1024) и неотслеживаемый set(false)

Connect.php:46–88 создаёт Table1024 с default conflict0.2; set() не проверяет
результат. При отказе socket физически открыт, но его connectionId/метаданных
нет, hello/auth не могут пройти нормальный контракт. Проба454/455 показывает
реальность отказа до1 000. Неподтверждённые/анонимные соединения тоже занимают
реестр; в WSocket нет отдельного deadline на hello/auth и явной квоты для них.

Нужно: отдельный бюджет физических соединений с запасом reconnect/неавторизованных,
проверка set с явным закрытием при отказе, handshake timeout и admission/rate limit.
Одна игровая сессия на аккаунт не ограничивает анонимные WebSocket.

### C03 — P1: syncTable2048 — bottleneck сохранения

BaseRepository.php:78,420,442; RepositorySaver.php:saveAll; WSocket.php:flush30с.
Размер2048 одинаков для всех репозиториев.1 000 онлайн по5 планет дают5 000
разных Resources/Planets rows между flush, не считая прочих операций. Даже
проба decimal-ID отказала при1 077-м ключе. Повторные изменения одной строки
не добавляют marker, но разные базы добавляют.

Старое «молча всё потеряется» уже неточно: writeRuntimeRow проверяет set/read-back
и компенсирует строку/индексы. Однако отказ marker прерывает операцию/tick;
компенсация одной строки не делает весь AccountData::save атомарным.
Сокращение интервала само по себе не даёт гарантии при пике/медленной MySQL.

Нужно: бюджет distinct dirty rows, backpressure и наблюдаемость; согласовать
порядок/атомарность сохранения нескольких связанных rows, затем размер/механизм.

### C04 — P1: фиксированные индексы уже резервируют слишком много памяти

30 BaseRepository и9 дополнительных Table дают модель **2 165 126 204 байта
(2,016 GiB)** общей allocation. Учтены19 построек,22 технологии,22 типа кораблей,
13 видов обороны/ракет и динамические113 колонок FleetsShips. Это не RSS и
не сумма RSS всех процессов: shared страницы нельзя считать по worker повторно.

| Семейство, основная+индексы+sync | Модель MiB |
| --- | ---: |
|Fleets|295,88|
|Messages|232,30|
|OrbitalResourceSites|178,28|
|FleetCommands|162,93|
|PlayerQueue|134,96|
|Planets|130,13|

Причина: каждый неуникальный индекс резервирует tableSize рядов с ids2048,
даже если реальных групп мало. Например Fleets.status имеет несколько групп,
но резервируется как полноценная большая таблица. Простое×8 для всех основных
таблиц/индексов означает порядок16 GiB общей allocation ещё до heap/SQL/ОС.

На dev наблюдались3,76 GiB RAM, занятый8 GiB swap, container memory около1 GiB
и VmSize PHP около2,1 GiB; поэтому прежний browser timeout нельзя объявить
доказательством падения приложения. Лог memory_get_usage показывал лишь десятки MiB.
Нужны PSS/cgroup+swap метрики и отдельный бюджет индексов/групп/частей.

Модель5.1.6: row header88; INT/FLOAT8; STRING align8(length)+4; buckets округляются
к степени2, минимум64; default collision0.2; учтены указатели/структуры pool.
Не включает PHP objects, SQL, сетевые буферы, стек и страницы allocator.

### C05 — P1: история сообщений не должна целиком жить в Swoole

Messages8192 глобально, не на аккаунт. Нет автоматической очистки Messages
по времени; удаление несохранённых BattleReports через7 дней — другая таблица.
messages.get отдаёт весь inbox, не страницу. При20 000 аккаунтов даже по одному
сообщению на каждого уже превышен теоретический бюджет.

При5 сообщениях/сутки×7 дней —700 000 rows. Одна основная запись резервирует
9540 байт payload, то есть около6,22 GiB raw payload, без header/индексов/heap.
Нужно: SQL-пагинация/retention, ограниченный hot cache, отдельно unread summary;
не наращивать8192 до миллиона при неизменной архитектуре.

### C06 — P1: клиентские ID ещё создают фантомные сущности

BaseRepository.php:784 создаёт default row, если findById не нашёл ID.
Notification.php:633/670 вызывает его для read/delete; QueuesServices.php:455/549
для cancel. Проверка владельца происходит после создания. Отказ запроса
не гарантирует отсутствия уже созданной строки. Это загрязнение SQL/runtime
и способ исчерпать ограниченные Table/sync/ID, а не корректное чтение.

Нужно: non-creating lookup на пользовательских ID, проверка existence/owner
до смены WorkPlanet/публикации и при исполнении. Автосоздание оставить только
в явно предназначенных для этого таблицах/операциях. Массовый exploit на dev
не выполнялся; цепочка подтверждена исходниками.

### C07 — P1: незакрытые проверки прав и состояния

- CancelToQueueHangar, QueuesServices.php:549: нет owner check. getCurrentQueue
  для hangar ищет **по planet/type**, не user, поэтому переданный userId
  не является защитой. WorkPlanet меняется на планету чужой очереди.
  FleetBattleService::assertQueueAction проверяет бой, не владельца;
  v2 проверяет owned context, но не принадлежность вложенного QueueId.
  Resources::updateByPlanetId берёт userId из владельца планеты, но не принимает
  actorId: при чужом WorkPlanet это также риск записи валют из контекста другого
  пользователя. Чужие очереди/балансы при аудите не менялись.
- MoveShip: owner обеих сторон уже проверяется, но нет общей проверки IDLE,
  совпадения фактического места и допустимости изменения состава у обеих сторон.
  DisbandFleet уже защищён getManageableFleet(...,true). Поэтому A1 Claude
  нельзя целиком считать ни открытым, ни исправленным.
- GalaxyPage.php:40 и Galaxy::getSystem:122: запрос системы вызывает сохранение
  генерации, но здесь нет проверки MaxGalaxy/MaxSystem. В результате query

  также не является корректной валидацией типа. За пределы мира в аудите не ходили.

Нужно: права и domain bounds перед побочными эффектами. Не добавлять owner
ограничение в общий FleetsData::get: внутренним боям нужны чужие флоты;
защищать конкретные операции/контексты.

### C08 — P1: v2 capacity и уборка receipts

- ProtocolResources16384 начинает eviction только при count>=15000.
  На hash-пробе запись отказала при11 592. Cache может исчерпать collision pool
  раньше порога уборки и выдавать ошибки чтения до освобождения/рестарта.
- ProtocolSubscriptions4096: штатные2×1 000=2 000 подписок меньше номинала,
  но объявленные8×1 000=8 000 уже не помещаются; пробный hash-профиль отказал
  при2 859. Нужны общий budget и резерв на смену view/reconnect, не только
  индивидуальный лимит. Delivered/dirty set тоже следует проверять.
- ProtocolCommands::cleanup удаляет до1 000 receipts раз в60с: средний потолок
 16,7/с.1 000 игроков с одной командой в30с создают33,3/с; после retention
  очередь удаления будет расти примерно на1,44 млн/сутки. Accepted автоматически
  не чистятся; для старого epoch нужен отдельный reconciliation, не слепой replay.

Дедупликация и runtime-boundary протокола сохраняются; это не основание
выкинуть receipts или автоматически повторять неизвестные команды.

Дополнение05.11.2026: reconciliation orphan accepted исправлена и проверена
на основном dev(B061, этап3Д плана). После restore очередь защищает только
точно совпадающую квитанцию; orphan сохраняется как unknown без replay.
Проверены23 случая startup/restart и9 проверок потери payload в той же epoch.
Это не закрывает целевую нагрузочную приёмку бюджетов C08.

### C09 — P1: горячие полные сканы и синхронная работа

- EventLoop.php:465 → Planets::getAllPlanets:137 сканирует все планеты для
  каждого онлайн-аккаунта.1 000×100 000=100 млн проверок рядов на tick,
  до расчёта ресурсов. getPlanetsList:147 добавляет похожие сканы в проекциях.
- FleetCommands::getPendingTimeCommands:219 сканирует/сортирует все команды
  при очередном поиске scheduler. Извлечение rows конкретного флота уже
  использует индекс; старый вывод «все методы всё сканируют» больше неверен.
- ProtocolSubscriptions::all/dirty проходят реестр подписок; для1 000 dirty
  accounts и2 000 subscriptions это миллионы проверок. Пересчёт полных DTO,
  JSON и digest выполняется даже для неизменившейся проекции.
- Query/command/flushPending используют world EX. Saver и обычный tick проходят
  под world barrier; синхронные PDO/JSON/сжатие/логирование удерживают event loop
  или задерживают доступ. Database дополнительно делает SELECT1 перед запросом.

Нужно: owner/time indexes, bounded scheduler, budgets работы на tick, coalescing
проекций, профилирование/кэширование формул; сначала обеспечить согласованность,
а не снимать блокировки для ускорения. Измерить p95/p99 tick/command/push/flush
на целевом dataset; текущие малые тесты этого не доказывают.

### C10 — P1/P2: bounded боевые/разведывательные состояния и очереди

PlanetBattles/SpaceBattles/FleetExpeditions: по128 buckets и262144 байта state.
1 000 экспедиций/боёв не помещаются в128/153 theoretical slots. Есть проверки
размера/state и отказа записи — это уже не молчаливое усечение, но нужен
явный общий admission limit и корректное освобождение завершённых checkpoint.

PlayerQueue.data512 сохранён намеренно; большие payload вынесены в буфер
1024×16 KiB, максимум4/account, TTL120с. Это bounded backpressure, а не ошибка
«всем нужен16 KiB в основной строке».1 000×4 одновременных больших команд
не поместятся: требуется ожидаемый отказ/очередность, не бесконечный буфер.

FleetCommands.params теперь2048, Messages.data8192/text1024; старые512/1024
из Claude неактуальны. BaseRepository read-back обнаруживает усечение, а
chunked indexes по64 IDs защищены длиной и rollback. Однако допустимые сложные
планы/бой могут превысить предел: нужны конкретные worst-case JSON tests и
отдельные bounded сущности, не неограниченное увеличение каждой колонки.
