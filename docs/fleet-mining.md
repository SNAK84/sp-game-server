## Реализовано5Б.0

В5Б.0 подготовлены три чистых расчётных метода `FleetMiningService`:

| Метод | Назначение |
| --- | --- |
| `rates(site, ships, level, mode)` | Мощность подходящих корпусов из согласованного конфига; сопровождение её не увеличивает. Смесь — одна суммарная мощность. |
| `baseline(site, knowledge, time)` | Приводит сохранённые G/K к общему моменту с пассивным восполнением и пределами C/qC. Не восстанавливает исчерпанный K до полного запаса при q=1. |
| `phase(state, fleets, until)` | Совместно рассчитывает всех добытчиков до первой границы: G, K, трюм, резерв бака, конец длительности либо запрошенный момент. |

Baseline используется только до первой работы либо поверх уже согласованного
checkpoint. Нельзя применять его пассивное восполнение поверх ещё не учтённой
активной добычи. Личное наблюдение/observed_at и качество q им не изменяются.

У фазы фиксированы мощности по ресурсам. Для каждого ресурса:

```text
X_i = P_i * dt / 3600
G' = min(C, G + (R - sum(P_i)) * dt / 3600)
K' = min(q*C, K + (q*R - sum(P_i)) * dt / 3600)
```

dt ограничивается первым исчерпанием, поэтому положительная добыча не берёт
восполнение из будущего. Все флоты получают один фактически отработанный
интервал; малый общий запас делится пропорционально их мощностям, а не порядку
перебора. Расчёт по группам и ресурсам, не по каждому кораблю/прошедшей секунде.

Вместимость считается после груза И бака. Сожжённое топливо освобождает место,
но не прибавляется к добыче; работа не тратит резерв возврата. При исходной
нехватке резерва топливо не создаётся. Нулевой расход не требует фиктивного
топлива. Входные серверные массивы не мутируются; возвращаются новые balances,
приращения груза, остатки трюмов/баков и события границы.

**Фаза не является обработчиком всей миссии.** После первой границы будущий
координатор должен сначала совместно сохранить результаты, закончить только
нужные флоты/действия, перераспределить смесь и продолжить расчёт. Полный трюм
одного флота не передаёт его производительность другим. Такая последовательность
проверена расчётно двумя фазами, но автоматический runtime-переход ещё не подключён.

## 5Б.1а — ограниченный долговечный журнал,25.10.2026

### Хранение и публикация

`MiningCheckpoints` — отдельный Repository для управляющего журнала MySQL,
как у durable receipt, не замена Swoole Tables игрового мира. Нет новой
Swoole Table с крупным payload на каждого игрока/флот. Две новые InnoDB-таблицы:

- `mining_checkpoints`: один заголовок на siteId, revision/token/owner,
  checkpoint_time, phase prepared/applied, число частей и общий SHA-256 manifest.
- `mining_checkpoint_rows`: отдельные before/after/guard для объекта,
  личного обследования, каждого флота/команды. Изменять можно только узкий
  whitelist экономических полей, не владельцев/приписки/индексные идентификаторы.

Подготовка принимает ожидаемую revision и уникальный token. Все размеры/
поля проверяются до SQL. Новые части сначала записываются отдельно от
действующего заголовка, затем сверяются и одной SQL-операцией публикуется
новый prepared-заголовок. До публикации effects запрещены. Обрыв во время
записи частей оставляет старый applied-заголовок и неиспользуемые части;
новая подготовка удаляет только такие служебные поколения.

После публикации новый token запрещён до подтверждения текущего.
Тот же token с тем же manifest возвращает ту же операцию; изменённый payload,
устаревшая revision или конфликт времени отклоняются. Чтение сверяет число
частей, их SHA-256 и общий manifest; неполные/неизвестные состояния — отказ,
не попытка «починить» экономику. Предохранители:1024 сущности/операцию,
8192 байта/сущность,2048 байт metadata. Это технические пределы журнала,
не новые игровые лимиты. Заранее в Swoole эти объёмы не выделяются.

`acknowledge()` — внутренний метод, который будущий commit-адаптер обязан
вызывать только после durable проверки after всех игровых строк. Сам
Repository экономику НЕ сохраняет. После applied остаются текущий marker и
текущие части; старые поколения удаляются, история каждого тика не растёт.

### Сериализация и восстановление

`locked(siteId, callback)` использует неблокирующий `flock` в общем logs
bind-mount.64 шарда, не отдельный lock-файл на каждого игрока. Блокировка
реально разделяется независимыми процессами и освобождается ОС при их выходе;
PID/coroutine owner дополнительно проверяется перед записью. Все писатели
обязаны видеть тот же каталог, это не распределённый lock для несвязанных томов.
Будущий адаптер должен держать блокировку на всей операции до подтверждения.

`FleetMiningService::recoveryPatch()` — чистое решение одной строки:

- текущий guard + before → абсолютный after patch, не повторный delta;
- текущий guard + after → ничего повторно не начислять;
- другой владелец/контекст/ID или неизвестные значения → остановка/диагностика.

Разные сущности одной операции могут быть before/after после частичного
flush. Их решение проверено расчётно; записи в настоящие игровые репозитории
и блокировка параллельных игровых действий пока не подключены.
Сравнение точное, без относительного epsilon: иначе при большом грузе можно
пропустить реальные потери. Будущему адаптеру ещё нужны канонические числа
с точностью SQL-полей, дробные остатки и проверенный read-back.

## 5Б.1б — применение и восстановление на основном dev-сервере

### Реализация

`FleetMiningCheckpointService::commit` принимает серверные before/after/guard,
не пользовательские дельты. Проверяет схему, состав объекта/обследования/флотов,
принадлежность команд и все runtime before; точечно сохраняет durable before.
Только затем публикует journal. После публикации разрешён лишь roll-forward
того же результата. Повтор уже applied-token не откатывает последующую жизнь флота.

Общий путь применения/recovery сначала проверяет ВСЕ runtime и SQL-строки.
Для каждой допустимы before или after независимо от других сущностей;
неизвестное состояние отклоняется до первого эффекта. Затем выставляются
абсолютные after, обновляется runtime-кэш Fleet, выполняется точечный flush
и read-back guard/after. Только после этого ACK. Существующий общий saver
не используется как доказательство успешного сохранения.

Новые методы BaseRepository читают/сохраняют только существующие строки:
не создают default-объекты и не воскрешают удалённые. Float-параметры точечного
flush передаются round-trip строками, а не через PHP precision=14. Общий saver
не переписан. Непредставимые DOUBLE(p,s), неверные типы и длинные runtime-строки
отклоняются заранее. Адаптер НЕ прячет потерю точности epsilon/округлением:
расчётному обработчику ещё предстоит явно сохранять дробный carry.

### Барьеры

- На общем logs bind-mount: SH для обычного PageBuilder/tick/saver, EX для
  commit/recovery. Обычные обработчики не блокируют друг друга; checkpoint
  не публикуется/не применяется посреди другого обработчика.
- `main.php` восстанавливает prepared до запуска WebSocket. Tick, страницы
  и saver также проверяют recovery перед допуском операций.
- После ошибки внутри уже начатого тика строки участников защищены локальным
  fence: update/delete и общая проверка доступности флота отказывают, saver
  пропускает защищённые dirty-записи, не сбрасывая маркеры. Сам roll-forward
  имеет узкий допуск под EX. Успешный ACK снимает защиту.
- Если ACK записался, а последующее чтение/cleanup оборвалось, следующий допуск
  снимает оставшийся локальный fence по applied-журналу, НЕ переигрывая старые after.
- Занятый world-lock имеет отдельный код423: tick повторяется позднее. Неизвестное
  состояние/ошибка SQL — fail-closed, а не допуск мира с частичной экономикой.
- Новых Swoole Tables и увеличения payload-колонок нет. Static fence не заменяет
  межпроцессный flock и журнал; он закрывает продолжение того же тика после catch.

### Расчётная связка

`FleetMiningPhaseService::build(snapshot, workers, from, until, previous)`:

- Берёт общий серверный site/knowledge, все строки участников и их команды;
  не принимает подменённые free/fuel из конфигурации. Вместимость вычисляется
  за вычетом реального груза и логического бака с ещё не материализованным остатком.
- Вызывает общий phase до первой границы. Создаёт site+knowledge и по две
  записи fleet/command на участника. Поэтому максимум511 участников при
  прежнем MAX_ENTRIES1024. Размер params по-прежнему2048, metadata2048;
  переполнение отклоняется до подготовки журнала, колонки не увеличены.
- Груз и личный K сохраняются полными DOUBLE/JSON-значениями. Общий G и бак
  записываются вниз до микроресурса; положительная разница сохраняется.
- `metadata.miningCheckpoint.stockCarry` — три дробных остатка G, связанные
  с физическим after предыдущей site-строки. Изменённый запас не «почти равен»:
  такой контекст отклоняется, а остаток не накладывается на чужое состояние.
- `command.params.miningCheckpoint` — точный at, storedFuel/fuelCarry,
  конфигурация фазы и локальные события границы. Обычные параметры команды
  не заменяются. Применение fuelCarry требует того же владельца/объекта,
  неизменного storedFuel и согласованных часов команды/K/общего checkpoint.
- Временная точка at хранится полностью в журнале/JSON, а SQL-маркеры
  resource_update_time/current_position_time получают представимый образ.
  При восстановлении baseline использует точный at, а не повторное пассивное
  восполнение за уже учтённую дробь времени.
- События stock/reserve остаются в общей metadata, cargo/fuel/duration —
  в ledger соответствующего флота. Завершение/возврат/перераспределение смеси
  пока не выполняются автоматически, это задача следующего обработчика.

`FleetMiningCheckpointService::commitPhase` подготовлен как внутренний вход
обработчика: под EX читает runtime и проверенный прошлый journal, строит фазу,
передаёт её существующему commit. Fingerprint исходного запроса запрещает менять
содержимое того же token. Applied retry возвращает прежний результат, не строит
новую фазу поверх изменившегося флота. Публичного WebSocket test-backdoor нет.
Этот вход пока не вызван обычной игровой командой и не проверен ненулевым рейсом.

### Явный SQL-образ before

Первый runtime before может содержать больше дробных знаков, чем DOUBLE(p,s).
Теперь before/guard сохраняют raw-значения, но дополнительно имеют ровно один
определённый по схеме SQL-образ. Initial commit всё ещё требует строгого raw
runtime before; после flush durable сверяется с явным SQL-образом. Recovery
допускает raw либо этот известный образ после restart. Это не нормализация
произвольного current и не epsilon: третье значение по-прежнему отклоняется.
After обязан быть представимым; его дробные остатки уже входят в тот же batch.
Точечный flush также явно приводит fixed-scale поля перед SQL-binding, поэтому
пограничное округление PHP/MySQL не выбирает неизвестный третий before.

При проверке найден дефект новой реализации числовой проверки: PHP round(x,6)
для1792916730.1234567 оставляет исходное семизначное представление. Fixed-scale
образ строится через locale-independent sprintf('%.*F', scale, value), а не round.
На настоящем MariaDB SELECT CAST(? AS DOUBLE(17,6)) совпал с PHP-образом для
большого timestamp, обычной дроби и двух граничных значений; игровых записей
этот диагностический SELECT не менял.

## 5Б.2б.1 — экономическое закрытие фазы без потери дробного бака

Это необходимая часть выхода, **не весь обработчик миссии**. Begin, выбор
следующей границы scheduler, формирование возврата/стоянки и UI не подключены.
Корпуса223/224 по-прежнему не выдавались, enum/API не менялись.

### Закрытие

- `FleetMiningPhaseService::close(batch, rows, fleetIds, reason)` требует
  проверенный applied checkpoint и точное совпадение всех текущих after/guard.
  Не пересчитывает время/добычу, не меняет груз, G/K или физическую позицию.
- Для выходящих участников `storedFuel + fuelCarry` переносится в fuel_current,
  `miningCheckpoint` убирается и сохраняется короткий `miningClosed` receipt.
  Общий stockCarry сохраняется. Не выходящие участники остаются неизменными.
  Начало новой расчётной работы убирает старый receipt, не прибавляя его бак ещё раз.
- Размеры journal/params не увеличены. Неверный контекст, ID, причина выхода,
  повреждённый остаток/превышение загруженного топлива отклоняются до prepare.
- `FleetMiningCheckpointService::closePhase` — внутренний EX/recover/read/commit
  вход с fingerprint запроса. Applied retry того же token возвращает receipt;
  изменение участников/причины для этого token запрещено.
- Закрытие НЕ помечает игровую команду выполненной и не активирует следующую.
  Это экономическая часть, которую координатор должен включить в свой переход.
  После изменения общего состава сначала нужен совместный settle всех участников.

### Представимость и обычный saver

`fleets.fuel_current` расширено с DOUBLE(17,6) до DOUBLE при штатном init.
Так остаток после закрытия остаётся топливом, не превращается в груз и не теряется
при последующем удалении команды. Новых колонок/байтов Swoole нет. Ранее
сохранённые значения остаются теми же; нестандартные nullable/default constraints
не меняются автоматически. В текущей dev-БД старые constraints проверены.

Для параметров всех float в обычном `BaseRepository::syncToDatabase` используется
тот же явный SQL-образ и roundtrip-строка, что у точечного checkpoint flush:
unscaled DOUBLE сохраняет весь баланс, fixed-scale DOUBLE получает ровно свой
известный образ. Никаких epsilon-сравнений/маскирования третьего состояния.

Живой тест обычного saver через RenameFleet выявил, что прежний PDO precision=14
переписывал current_position_time1792927000.541368 в1792927000.5414. Попытка новой
фазы штатно отказала до prepare. Только у QA Fleet42, при остановленном сервере,
clock восстановлен из совпавших последнего WS и проверенного journal; все остальные
поля сверены с after, чужие строки не исправлялись. После изменения saver повторный
RenameFleet→возврат исходного имени→обычный flush сохранил точные бак И clock.

### Жизненный цикл

- begin проверяет реальное прибытие на собственную ресурсную базу, обследование,
  подходящие корпуса, завершённую технологию, режим/длительность/продолжение.
  Мощности, вместимость и расход вычисляются сервером, не берутся из запроса.
- До входа нового участника все прежние доводятся до общего времени события.
  Zero-elapsed checkpoint присоединяет новый флот. Его стоянка оплачивается
  до этого момента, затем base_fuel_* обнуляются: второго параллельного расхода нет.
- Общий phase применяется через прежний durable journal, учитывает G/K, трюм,
  бак, резерв возврата и срок. Следующая команда назначается на ПЕРВУЮ границу,
  отдельный таймер или новый scheduler не создаётся.
- Смесь сохраняет общую мощность, делит её по metal/crystal regeneration и
  переключает на оставшийся ресурс при исчерпании первого. Исчерпанный компонент
  не переоткрывается в рамках того же запуска: это исключает Zeno-цикл регенерации.
  Новый запуск заново проверит запас. Мощность ушедшего флота другим не передаётся.
- closePending вызывает первичную runtime-ветку closePhase; она материализует
  дробный бак и делает MINING терминально due, но не ставит executed=1.
  finish затем передаёт управление обычным STAY либо заранее подготовленному
  возврату. Отзыв сначала settle/close, затем обычный commitRecallReturn.
- До фактического перехода к продолжению даже finished MINING остаётся физической
  охраной объекта: экономическое закрытие не означает уход кораблей.
- В FleetsPage добыча — стоянка, а не перелёт. Время следующего общего события
  не выдаётся за точный ETA всей миссии. Отдельной клиентской интерполяции добычи
  пока нет; authoritative груз обновляется при server checkpoint.

## 5Б.2в.1 — доставка своему работающему добытчику

Подключается один вид внешней мутации, не все сразу: TRANSPORT → свой Fleet,
выполняющий MINING. Добыча, слияние, бой и изменение обследования не объединяются
в универсальный небезопасный callback. Публичная отправка MINING ещё закрыта.

- Существующий receiver разрешает MINING только своему отправителю, сохраняя
  проверки видимости/экспедиции/боя. Чужой добытчик не становится разрешённой целью.
- Встреча проверяется до передачи и повторно под EX world barrier. Общий settle
  приводит ВСЕХ работающих добытчиков объекта ко времени прибытия доставщика.
- Расчётный transfer строит zero-elapsed baseline: старый fuelCarry материализуется
  на копии, добавляется доставка, заново строятся ledger/свободный трюм/следующая
  граница. Производительность, срок и накопленные показатели работы не сбрасываются.
- Режим refuel отправляет только доставленный903 в бак, иначе903 остаётся грузом.
  Три ресурса передаются пропорционально percent в пределах свободного трюма,
  учитывающего логический бак. Исторический fuel_total расширяется явно вверх
  до SQL-точности, а не теряет дробь при обычном saver.
- Изменения донора, добытчиков, G/K и receipt команды донора входят в один batch
  существующего журнала. В whitelist разрешён существующий fuel_total; схема,

- Если к моменту обработки цель уже вышла из MINING, используется прежний обычный

## 5Б.2в.2 — слияние своего донора с работающим добытчиком

Входящий обычный флот может присоединиться к своему работающему MINING.
Сам добытчик не становится отправляемым донором: для этого по-прежнему нужен
выход из добычи. Бой/САБ/оборона/экспедиция/межсистемный переход сохраняют
предыдущие ограничения. Публичная отправка MINING пока не включается.

Порядок: физическая встреча → общий settle объекта старым составом → нулевой
rebase с объединённым составом → durable after → удаление пустого донора.
Начало/конец работы, накопленная добыча, оплаченный расход, имя, домашняя база
и следующая команда получателя сохраняются. С момента встречи пересчитываются
производительность, вместимость, расход и резерв возврата. Расчёт preview
состава не меняет зарегистрированный Fleet/dirty-маркеры.

В один manifest входят оба бака и весь груз (включая кредиты/дублоны), группы

не повторной передачи. Close следующей фазы не

## 5Б.2в.3 — дообследование при работающей добыче,26.10.2026

Подэтап закрывает обновление личного знания q/K во время MINING. Бой и смена
контроля самой добычи остаются следующими интеграциями; публичный MINING
по-прежнему не включён. SPA и исторические движки не изменялись.

Порядок завершения RESEARCH:

1. Под существующим EX world-barrier проверить команду и восстановить pending.
2. Сохранить SurveyResults/preparing с token/site/owner/временем ДО первого
   settle. Другие операции добычи и смена контроля этого объекта не обгоняют
   незавершённый результат. Повтор preparing заново подтверждает durable-запись.
3. Совместно довести всех добытчиков до времени обследования. Затем прочитать
   свежие G/K; G берётся с stockCarry, а не только из округлённой SQL-колонки.
4. Старая формула обследования: Knew=min(qnew*C,Ksettled+gain*Gsettled).
   Покрытие не меняет физический G, трюм или бак; полное q=1 не восстанавливает
   уже добытый K повторным обследованием.
5. Если у обследующего игрока продолжаются добытчики, journal одним batch
   меняет q/K/observed_at, все носители carry и miningApplied в SurveyResults.
   Нулевая фаза пересчитывает due-события, не добавляет прошедшее время ещё раз.
6. Доклад и обычное завершение RESEARCH используют существующий receipt-путь.
   После miningApplied знание больше никогда не переписывается из frozen receipt:
   добыча уже могла продолжиться. После recovery helper перечитывает receipt.

Если обследует другой игрок, общий G сначала согласуется с действующими
добытчиками, но результат меняет только знание обследующего. Владелец добычи
не получает чужое покрытие/резерв. Если все добытчики естественно завершились
до этого момента, работает прежний standalone-путь обследования. Закрытые
работы/компоненты смеси автоматически не возобновляются.

Добавлена ограниченная journal-сущность survey/state: используется прежняя
SurveyResults.state4096, общий лимит части8192 и manifest1024 не повышены.
Экономический close не наследует структурную запись survey как зависимость
последующих фаз. Схема БД, ID миссий/команд и система отправки не менялись.

### Изменение lifecycle

После проверок участников, разрешённого наблюдения, фактической встречи и
размера боевой команды общий exclusive-барьер сериализует вход в бой с journal.
`interruptForBattle` сначала актуализирует всех добытчиков объекта до времени
встречи. Затем существующий closePhase(reason=battle) одним durable batch:

- материализует дробный остаток бака, сохраняя уже добытый груз;
- убирает активный miningCheckpoint, сохраняет finished/miningClosed;
- меняет command_type MINING61→OBSERVE43, execute_time=0, pause=battle;
- снимает miningRequest/planStep/hold, не создаёт маршрут и не включает расход
  удержания во время боя.

Только после этого боевой адаптер снимает rollback/start snapshot и замораживает
флоты. Неудачная подготовка боя не может воскресить working MINING: baseline
уже paused OBSERVE. Обычный surviving defender остаётся на ручной паузе,
attacker продолжает свой штатный возврат. Корабли, урон, XP и потери топлива
по вместимости рассчитывает прежний battle pipeline, не экономический journal.
Новая whitelist-часть command_type не увеличивает лимиты записей/таблиц; применение
подтверждает новый индекс типа, отсутствие старого и существующий индекс времени.
Естественное закрытие добычи на той же/более ранней границе имеет приоритет:
после settle повторно проверяется working, бой требует актуальной встречи.
