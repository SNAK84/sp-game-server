## Уточнение старой границы «активный hold»

В актуальной игре OBSERVE отправляется только к POINT:
`FleetMissionService::getAvailableMissions` и `FleetCommandsService` проверяют
тип координаты. Ручная остановка через `holdBefore`/`beginHold` тоже вычисляет
физическую POINT, а не продолжает движение вместе с OBJECT.
Следовательно, такой флот не становится охраной соседнего гиганта/сектора
из-за совпадения приписки или близости. Его POINT нельзя автоматически
превратить в привязку к объекту ради снятия старой записи плана.

Фактическая стоянка у ресурсной базы уже поддержана: IDLE, MINING,
послебоевая платная siteGuard и явная дружественная DEFEND; собственное
обследование прерывается с автоматическим возвратом. Подкрепления CAPTURE,
DEFEND и RELOCATE подключены в5В.4а/6/7. Запрет произвольного импортированного
OBSERVE/hold при OBJECT остаётся защитной проверкой, не новой публичной миссией.

## Повторяемая проверка сохранённого QA-контекста

```bash
docker exec swoole_app php migrations/20261027_resource_combined_battle_qa.php --verify
```

Это SELECT-only проверка текущего MySQL, без второго Swoole и без инициализации
локальных репозиториев. Проверяет точных участников/результат, общую revision,
закрытие обеих MINING, арифметику груза, раздельные корабли/XP, единственность
сообщений и отсутствие списания топлива за бой. Топливо сверяется по frozen
баку из сообщения и реально сохранённому послебоевому clock, а не по времени
снимка. Также проверяются восстановленная DEFEND и контроль объекта.
Проверка привязана к этой QA-сцене до последующего Resume/Recall/истечения
DEFEND; это не постоянно применимый baseline всей игры. CoreContracts остаётся166/0.

Проверка пройдена до restart и после него на сохранённых строках, затем
повторена после загрузки мира. Финальный main StartedAt:
`2026-10-27T08:54:43.988544759Z` (11:54:43 МСК).
Полный reload SPA показал те же152.36775282768156/93.0608957236236 у104 и
111.77565786894081/68.26866346939487 у105. MINING=null, оплачиваемая пауза и
20D/ч/резерв25 сохраняются. Бак уменьшается только по послебоевому clock.
В отдельном preview SPA для OBJECT/sector3 после загрузки доступны11/40,
OBSERVE30 отсутствует; новая миссия hold у объекта не включалась.

CoreContracts166/0 повторены в основном контейнере. PHP lint новой fixture и
diff --check пройдены. Клиентский и backend production-код менять не потребовалось.
После финального restart четыре публичных WS ActualData другого QA9 — fleets,
overview,galaxy,messages — вернули status=ok. В просмотренном свежем startup/
QA-интервале ERROR/CRITICAL нет.

## Что осталось

- Отдельный живой сценарий FLEET-цели, которая прибывает к защищённому объекту
  во время полёта атакующего, ещё не заявлен PASS этим прогоном.
- Потеря базы при приписанном добытчике, работающем у другого объекта, остаётся
  явно закрытым случаем в prepareDestination; этот слой ещё нужно подключить.
- B030/B033 и другие отложенные баги не исправлялись. Полный5В пока не закрыт.
- Проверка10 раундов без потерь не доказывает произвольный crash между любыми
  строками result-plan; намеренный crash-injection в этом подэтапе не выполнялся.

Изменены только этот отчёт, `docs/fleet-roadmap.md` и
`migrations/20261027_resource_combined_battle_qa.php`. Последняя также содержит
SELECT-only `--verify`; её prepare/attack требуют остановленного main.
Основной сервер оставлен работающим; старые версии не менялись.
