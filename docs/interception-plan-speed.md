# B034: скорость перехвата в редакторе маршрута

Исправление01.11.2026, текущий backend. SPA/протокол/схема SQL не менялись.

## Причина

Окно отправки правильно передавало speedFactor5. Обычный command pipeline
писал5 в MOVE и возврат, но у ATTACK перехвата оставлял только interception.
FleetPlanService::steps пропускал активную MOVE, не сохранял скорость
предшествующей MOVE и брал из ATTACK отсутствующий speedFactor как10.
Отдельная ветка возврата выдавала только kind=return, тоже без скорости.
Клиент штатно восстанавливал оба слайдера на100%; сохранение такого редактора
могло незаметно заменить скорость будущих этапов. Уже летящая MOVE при этом
не переписывается механизмом редактора, её расчёт сам по себе был правильным.

## Изменение

- Новые ATTACK перехвата явно получают выбранный speedFactor вместе с MOVE.
- Для старых цепочек reader рассматривает полную историю, но не возвращает
  выполненные этапы в редактор. Она нужна только для наследования скорости
  ближайшего MOVE: ожидающего, активного или выполненного перед ещё
  ожидающим действием. После отдельного действия контекст скорости очищается.
- Отменённые строки не задают скорость/границы новой цепочки. Явные
  params.speedFactor и авторский planStep имеют приоритет над наследованием;
  отсутствие обоих источников сохраняет прежний default10. Округления нет.
- Восстановленные return/move/relocate также сохраняют свою скорость,
  а не теряют её в отдельных ветках reader. Состав этапов не меняется.
- Чтение не записывает команды, не активирует их, не меняет версии, топливо,
  текущую геометрию/время MOVE. Перезапись старых миссий миграцией не нужна.
