## Краткий вывод

Транспорт WSS + JSON подходит для SPA и Android. Основная проблема — не
транспорт, а смешение разных назначений пакета и контекста клиента:

1. Ответ на запрос, приём команды, результат её применения и фоновый snapshot
   выглядят почти одинаково; `mode` одновременно является маршрутом API и
   указанием открыть страницу.
2. Приём не равен применению, а применение не равно завершению игрового
   действия. Добавить строительство в очередь — не закончить постройку.
3. `requestId` связывает только прямой ответ. Внутренний PlayerQueue не
   сохраняет его для последующего результата; ActualData имеет новый UUID.
4. Один активный игровой клиент — намеренная модель. Однако переключение
   account.frame последним запросом само по себе не является явным контролем
   единственной сессии. Push-получатели браузера/Android не должны занимать этот FD.
5. Для личных диалогов нужны собственные история, порядок, права и состояния
   доставки/прочтения, которые нельзя приравнивать к обычному обновлению Page.

## Текущий lifecycle

```text
SPA: GameEvents.SendServer → Overlay → WS.Submit → Message → WebSocket
                                                │
Сервер: Connect/auth → PageBuilder → PageActionService → PlayerQueue
                                                │
          прямой response с исходным requestId ───┘
                                                │
                       EventLoop применяет очередь
                                                │
                  sendActualData(account.frame, account.mode)
                                                │
SPA: Message → callbacks → общий обработчик → ShowPage → render/reconciliation
```

Публикация события предшествует прямому ответу; общий контракт не устанавливает
барьер «ACK всегда раньше фонового обновления». В живой проверке ACK пришёл
раньше, но считать это универсальной гарантией нельзя.

### Прямые ответы не имеют единой семантики

| Случай | Сейчас |
| --- | --- |
| Обычное чтение страницы | `status=ok`, Page/TopNav/PlanetList |
| Большинство обработанных действий, включая cancel | `status=ok`, `mode=none`, обычно `data=[]` |
| Hangar build | Событие поставлено в PlayerQueue, но сразу возвращается Page; он может ещё не содержать новую очередь |
| Ошибка входной проверки | Прямой `status=error`, исходный requestId |
| Отказ/ошибка после приёма | Часто лог и новый snapshot; общего коррелированного terminal result нет |
| Фоновый ActualData | Новый server UUID, текущая страница аккаунта |

Нельзя выводить «применено» только из `ok` или присутствия Page. Также нельзя
объявлять команду успешной по первому следующему ActualData: он может объединять
несколько изменений или относиться к другому событию мира.

Проверено в `src/Game/Services/PageActionService.php:143`,
`src/Game/PageBuilder.php:75`, `src/Game/Services/EventLoop.php:551`,
`src/Game/Services/EventLoop.php:913`.

### Request lifecycle SPA

- `Submit` регистрирует request до отправки, timeout по умолчанию 15 секунд.
  Сам метод не возвращает Promise/requestId.
- `onSuccess`, `onError` или `latestKey` делают ответ локально обработанным.
  Такой ответ после callback не маршрутизируется как страница.
- Обычный ответ завершает bookkeeping и затем идёт в общий page router.
- `latestKey`/закрытие scope отменяют наблюдение клиента, не выполнение сервера.
- `kind` и локальный sequence существуют, но не задают серверную семантику
  команд и не обеспечивают идемпотентность.
- После первого ответа запрос считается завершённым. Добавить второй ответ
  «результат» с тем же requestId без изменения lifecycle нельзя: локально
  обработанный ID уже может находиться в ignoredRequestIds.
- Системные connect/lang ответы обходят обычное завершение запросов.
- Входящий token/time/lang применяются до фильтра ignoredRequestIds. Поэтому
  этот фильтр не является защитой от устаревшего изменения сессии.

Источники: `js/base.js:943`, `1017`, `1109`, `1151`, `1221`.

## Живая проверка B002

Настоящий SPA `https://sp-game.ru/`, headless Chromium через Selenium,
собственная диагностическая сессия. QA `qaown_260924`, планета 26. Только
штатные UI-кнопки заказа/отмены, без подмены ответов сервера.

Заказаны две ракетные установки (401), время одной около 41.14 секунды.
Контрольные партии отменены примерно через две секунды, до завершения единицы.
Изначальное и итоговое серверное количество — **0**, очередь после cancel
пуста. Стоимость фактического прогресса удерживается штатной механикой; ресурсы
не восстанавливались вручную. Старые чужие очереди не отменялись.

Сохранённая трасса успешного повтора:

| Пакет | requestId | Содержимое |
| --- | --- | --- |
| defense/build | `f744df0f-beb8-49df-a795-612261443e9f` | Запрос партии |
| Прямой ответ build | тот же | `ok`, mode=defense, Page.QueueList пуст |
| ActualData | `59393a7a-7510-49ad-adc9-944c3e989ab2` | QueueList содержит 5724 |

**472.5 мс** после запроса (разница около 433.5 мс). Зафиксировано предупреждение

Вывод: warning маршрутизации не означает отказ cancel; реальный hangar pipeline

## Живая проверка B040

1. Нативная кнопка «Выход»: прямой ответ
   `9f8ea706-3341-4e1e-9cda-4a991711ebfe`, `ok`, mode=login/action=login,
   token отсутствует, `data=[]`.
2. LoginPageClass открыт, Data.mode=login, но сохранён **тот же** непустой token.
3. Полный reload: старый token по-прежнему в sessionStorage, снова LoginPageClass.
4. Чтение overview с этим токеном получает `invalid_token`.
5. После закрытия штатного error-диалога и повторного нормального входа QA
   получен новый token, открыт Overview, pending requests=0, JS errors=0.

Токены/пароли в отчёт и диагностический stdout не выводились; проверялись только
наличие и равенство. После проверки QA снова авторизован штатно.

Причина: `Accounts::logout` обнуляет серверный token; `Message::source()`
не сериализует пустой token. Оба обработчика SPA сохраняют только truthy token,
но не удаляют прежний. `Data.clear()` существует, logout его не вызывает.
Отсутствие token у обычного snapshot нормально и не должно означать logout.
Нельзя просто присвоить `Data.token=null`: текущий setter вызывает setItem,
то есть нужен явный контракт удаления credentials.

Источники: `Accounts.php:119`, `Connect.php:240`, `Message.php:151`,
`js/base.js:44`, `87`, `955`, `1195`.

## Два соединения одного аккаунта: диагностика single-client границы

Открыт второй WS с тем же действующим QA token, без повторного login. От него
отправлен `planetselect` **той же** планеты 26, без изменения игрового объекта:

- ACK `17bbe708-3f4f-4427-9480-71b038e70ec7`, mode=none.
- Второй WS получил ActualData `1207b0e9-3667-46ab-a8d5-18f3b03d1917`.
- Первый WS в том же окне наблюдения получил **0 ActualData**.
- Второй WS закрыт; обычное чтение overview из SPA восстановило основной канал.

Source подтверждает модель: `Accounts::authByToken` переписывает account.frame,
`Connect` — account.mode, `sendActualData` использует единственный frame/mode.
Дополнительно `Users.current_planet` общий, а новый login заменяет единственный
token аккаунта. Это **не баг отсутствия fan-out**: пользователь не разрешает
два одновременно открытых игровых клиента. Тест доказывает только существующее
переназначение получателя без явного takeover/close старого соединения.
Будущий контракт должен ограничивать активную игру одной сессией/соединением,
а уведомления отправлять отдельно зарегистрированным push endpoints. Новый
вход должен явно завершать предыдущую сессию. Сам общий selected planet при
одном клиенте больше не рассматривается как требование нескольких независимых
выбранных планет; явный context команд всё равно нужен для гонок навигации.

## Authoritative state и существующая визуальная симуляция

ActualData — полный снимок страницы, а не JSON patch. BasePage заменяет
messageData; пропуск коллекции может трактоваться renderer как пустая коллекция.
При миграции нельзя слать частичный DTO напрямую в существующие renderers.

Существующий same-page incremental UI сохранять:

- DOM по ID, открытый список планет, введённые поля, выделение сообщений,
  раскрытые блоки, scroll, zoom/pan галактики;
- ownership/generation checks и page scopes;
- намеренную симуляцию производства hangar, ресурсов TopNav, топлива и движения;
- атомарную смену authoritative baseline и временных anchors. Результат команды
  не должен ещё раз прибавлять count/возврат ресурсов, уже входящий в snapshot.

Подтверждено чтением `BasePageClass.js`, `HangarPageClass.js`,
`GameBuildElement.js`; в живом cancel DOM-карточка также сохранилась. Это не
заявление, что весь UI уже свободен от любых пересозданий.

## Надёжность и границы доказательства

- Повтор requestId не дедуплицируется общей очередью; нет универсального запроса
  результата старой команды. Узкие guards отдельных миссий это не заменяют.
- PlayerQueue RAM публикация не является crash-durable ACK. Штатный shutdown
  сохраняет мир и передаёт pending events через player_queue_restart. Это не
  общий журнал приёма/результатов после аварийного завершения.
- Saver работает каждые **30 секунд** по коду WSocket, а не раз в минуту,
  указанной в части старых комментариев. Разные repositories сохраняются
  последовательно; запись receipt в SQL сама по себе не делает эффект команды
  атомарным с этим receipt.
- Ошибки выполнения/истечение payload могут закончиться логом и snapshot,
  без terminal error исходной команде.
- `serverTime` — wall clock сериализации, а не revision или causal ID.

Не выполнялись: аварийное завершение сервера, повтор реальных SendMission,
массовая нагрузка, проверка Android, отправка чат-сообщений. Эти гарантии не
объявляются проверенными или уже реализованными.

## Статические риски для отдельной проверки при миграции

Ниже не новые воспроизведённые runtime-баги:

- flushQueue до auth/handshake; истёкший/заменённый запрос может оставаться в
  offline messageQueue и позже уйти на сервер;
- auth ошибки локальных callbacks обходят общий auth handler;
- старый ответ может повлиять на token/lang до stale-response фильтра;
- непрозрачные структуры Page, отличия mode=fleets / Page.page=fleet;
- общий selected planet и неопределённая причинность snapshot;
- закрытие scope не должно уничтожать наблюдение результата принятой команды.

С учётом уточнения multi-device gameplay не является критерием. Проверять надо
новый вход → отзыв старой игровой сессии, отсутствие авто-reconnect борьбы,
сохранение принятых команд и независимую доставку push без второй игровой сессии.
