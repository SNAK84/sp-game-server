# Управление маршрутами и снабжение Fleet

Реализованный контракт текущего SP-Game; числовые ID enum не менялись.

## Возможности

- Компьютерная технология 1: план перед вылетом; 3: замена будущего плана.
- Флотовая логистика 1: добровольная остановка и удержание POINT.
- Редактор принимает 1–12 этапов: `mission`, `move`, `hold`, `return`;
  старый `transfer` совместим с транспортом на флот.
  Доступны все реализованные действия: атака, САБ, оборона, уничтожение луны,
  транспорт, передислокация, переработка, колонизация, шпионаж, удержание,
  экспедиция. Заглушки RESEARCH/MERGE не выдаются как работающие действия.
  Завершение — удержание, возврат на домашнюю базу либо передислокация на новую.
  Внутренние LOAD и execution timestamps команд клиент не назначает;
  общее время САБ проверяется существующим механизмом группы.
- На активном перелёте, обороне или экспедиции текущая команда сохраняется.
  Во время боя редактирование запрещено. Старые будущие команды
  отменяются, но остаются в истории; сохранение плана не снимает паузу.
- Редактор загружает оставшиеся этапы, а не заменяет их возвратом по умолчанию.
  Можно выполнять несколько действий у одной цели без фиктивного перелёта.
- В окне отправки доступны все свои флоты и входящие флоты, видимые в обзоре.
  Проверка видимости повторяется на сервере; свой отправитель исключён.

## Удержание и нехватка топлива

`FleetHoldFuelPerHourFactor = 0.1`: базовый расход кораблей × коэффициент в час,
из бака удерживающегося флота, не с планеты. Runtime хранит топливо на `lastAt`
и расход в секунду; клиент только интерполирует отображение.
Срок удержания не задан, поэтому для OBSERVE можно загрузить дополнительный
запас вплоть до свободной вместимости/наличия дейтерия. Для конечных миссий
сохраняется прежний предел топлива полного маршрута. Удержание может расходовать
и возвратный запас: игрок сам выбирает момент продолжения.

Остановка на MOVE_IN_SYSTEM фиксирует физическую POINT и возвращает в бак
неизрасходованную часть предварительно оплаченного участка. В переходе
остановка назначается после входа в следующую систему, без телепортации.
Оба варианта добровольной остановки включают платное OBSERVE.

При исчерпании OBSERVE либо нехватке топлива для следующего MOVE команда
получает `params.pause = fuel`, `execute_time = 0`. Это бесплатная пассивная
остановка без due-события. Заправка не запускает флот: требуется ResumeFleet.
Если у удержания нет последующих действий, сначала нужно составить новый план.

### Продолжение полёта

Одна кнопка «Продолжить» открывает диалог с `fuelMode`:

- `available`: использовать только бак. На MOVE_IN_SYSTEM при нехватке оплачивается
  доля прежней прямой и времени; флот пассивно останавливается в POINT, исходная
  MOVE остаётся pending. Следующие действия у исходной цели не выполняются.
  Переход между системами/галактиками неделим: без полного запаса не начинается.
  То же правило действует для условного локального перехода между планетой,
  луной и обломками: у них общий physical anchor, промежуточной POINT нет.
- `segment`: перевести из грузового дейтерия только дефицит ближайшего MOVE.
  Остальные участки автоматически из груза не заправляются.
- `route`: сразу переместить в бак расчётный верхний запас оставшегося маршрута,
  включая возврат. Используется штатный one-way preview по последовательности
  целей, без повторного учёта MOVE → переход → MOVE. Промежуточная выгрузка
  не затрагивает топливный резерв. Будущее бессрочное OBSERVE имеет бесконечный
  расход и явно отклоняется в этом режиме.

Проверка повторяется при обработке PlayerQueue. При нехватке либо exception
заправка и снятие паузы откатываются существующим runtime commit.
Старые запросы `useCargoFuel` остаются совместимы. ACK по-прежнему означает
принятие команды, не её игровой результат. Резерв соответствует текущему составу
и известному маршруту: бой, находки экспедиции и изменение пути цели могут
изменить фактический расход.

### Прогресс полного маршрута

Приватный snapshot владельца содержит `route_progress`: суммарный вес MOVE,
пройденный вес и активный диапазон для локальной интерполяции. Обычный MOVE
имеет вес 1; при остановке его вес делится между уже пройденной и оставшейся
частями. Шкала 0–100% включает весь обратный путь и не разворачивается при возврате.
Это доля выполнения перелётов, не физическая дистанция и не wall-clock таймер.
OBSERVE, бой, экспедиция, выгрузка и пассивная остановка не двигают шкалу.
Новая остановка хранит малые progress metadata в существующих params.
Для старых остановок доля восстанавливается read-only по истории MOVE/OBSERVE;
нормализация выполняется только при явном продолжении, не при рендере страницы.
Чужому игроку полный маршрут и его progress metadata не передаются.

## Передача флоту

TRANSPORT на CoordinateType::FLEET принимает только `fleetId`; клиентский
`lastKnownPosition` не используется. Сервер рассчитывает точку и время встречи
по траектории текущего активного участка получателя. После прибытия повторно
проверяются видимость и фактическая близость: дистанция не более 0.05.

У планеты/луны исключается только базирующийся флот (`STATUS_IDLE`). Флот
в миссии, на паузе или выполняющий действие у объекта остаётся доступной целью.
Исключение — текущая команда `EXPEDITION`, включая её внутренние паузы:
флот скрыт в галактике и списке целей; ручной ID и передача груза также запрещены.
Исходящий и обратный `MOVE` миссии экспедиции остаются видимыми и доступными.
Если встреча позже конца текущего MOVE, прогноз учитывает движение объекта
по орбите, а не фиксирует прежний `motionEnd`. Будущие команды получателя
не исполняются прогнозом; его доступность и положение проверяются при передаче.
Дозаправка не снимает паузу получателя. Старый `pause=target` у перевозчика
можно продолжить явно: перелёт пересчитывается от фактической позиции без
повторной погрузки или передачи ресурсов через расстояние.

Дейтерий груза при `refuel = true` пополняет бак; иначе остаётся грузом.
При нехватке вместимости пропорционально передаётся часть ресурсов, остаток
остаётся отправителю. Свободное место учитывает ещё не израсходованное
предварительно оплаченное топливо активного перелёта получателя.

Верхний резерв топлива для цели FLEET рассчитывается по наибольшему радиусу
орбит её системы, включая служебные. Поэтому движение/остановка цели внутри
этой системы не уменьшает допустимый максимум между preview, ACK и PlayerQueue.
Для другой системы учитывается также наибольший возможный выход после встречи.
Резерв не подменяет точную встречу и фактическое списание топлива по MOVE. Дейтерий
для получателя по-прежнему загружается в трюм, отдельно от топлива перевозчика.
Лимиты бака/груза, ресурсов планеты и обычных миссий сохраняются.

Проверка: `FleetRendezvousFuelSwooleTest.php` — 16 сценариев, настоящие отдельные
Swoole Tables, SQL=0: движение к/от звезды, своя/другая система, пределы погрузки,
остановка после preview, дозаправка на активной траектории и у планеты/луны,
прогноз после прибытия к объекту и продолжение старого `pause=target`.

Если цель изменила курс, путь встречи перестраивается от фактической точки
без повторной погрузки и без потери последующих пользовательских действий.
После 12 перенаправлений — пауза, а не бесконечное преследование.

Отдельно в изолированной диагностике воспроизведён существующий риск S2:
`completeCommand()` со старой MOVE после очистки цепочки может переписать
позицию уже вернувшегося отправителя. Груз получателю при этом повторно не
передаётся. Защита от такого replay не входит в исправление топливного preview.

## Составной маршрут

Пример: транспорт на две планеты и возврат. Погрузка нужна только до вылета.

```json
{
  "version": "версия из control.version",
  "fuel": 1000,
  "resources": {"901": 100},
  "steps": [
    {"kind": "mission", "mission": 10, "speedFactor": 10, "percent": 50,
      "coordinates": {"type": 1, "galaxy": 1, "system": 8, "orbit": 4, "objectType": 1}},
    {"kind": "mission", "mission": 10, "speedFactor": 10, "percent": 100,
      "coordinates": {"type": 1, "galaxy": 1, "system": 7, "orbit": 4, "objectType": 1}},
    {"kind": "return"}
  ]
}
```

`percent` — число 0–100 от **оставшегося** груза при прибытии.
Доля одинакова для металла, кристалла и грузового дейтерия. Бак не выгружается
на промежуточной остановке; кредиты экспедиции остаются на борту до конечной
выгрузки. При доставке флоту сохраняются правила вместимости и `refuel`.

Сервер компилирует и проверяет весь план без runtime-мутаций.
Проверки действия общие с обычной отправкой миссии: тип цели, владелец,
состав кораблей, технологии, лимиты, дружба/склад, длительность и САБ.
При входе в этап проверка повторяется с фактическим состоянием и точкой старта.
Если цель стала недоступна, флот останавливается с `pause=plan` и `planError`,
а не пропускает действие. После исправления плана требуется «Продолжить».

Текущая миссия Fleet меняется при старте соответствующего этапа. Группа САБ
создаётся/пополняется при входе в её этап, а не при сохранении далёкой будущей
атаки. Новая группа и вступление в существующую входят в откат сохранения плана.
Частичная выгрузка и её executed marker коммитятся вместе; повтор выполненной
команды не применяет процент ещё раз. Ошибка коммита допускает повтор scheduler.

Передислокация — последний этап, поскольку меняет домашнюю базу. Удержание
бессрочное и требует явного продолжения. Колонизация расходует колонизатор:
при отсутствии других кораблей дальнейший маршрут естественно прекращается.
Будущие действия проверяются по уже существующим объектам; редактор не
моделирует заранее ещё не созданную колонию/результаты боя/находки экспедиции.
Для произвольного плана топливо задаётся вручную; при нехватке действует
существующая пассивная остановка, а не автоматическая дозаправка.

## Сохранение и API

Существующий pipeline: WebSocket ACK → PlayerQueue → EventLoop → ActualData.
`status=ok` означает принятие команды, не завершение игрового действия.
Новые действия: StopFleet, ResumeFleet, SetFleetCommands (`fleetId`, `plan`).
План содержит `version` текущей цепочки: устаревшая версия отклоняется повторно
при обработке события. Схемы MySQL, RepositorySaver и архитектура PlayerQueue
не изменялись. Pause/hold и маршрут сохраняются в существующих params команд.
Буфер `PlayerQueue.data` увеличен с 512 до 16384 байт: три обычных этапа
раньше обрезались при serialize. Размер проверяется до выделения ID/записи;
слишком большой payload получает обычный error вместо принятия повреждённой
команды. Это не добавляет persistence/reliable delivery в PlayerQueue.

Изменения Fleet/команд, передача между двумя Fleet и погрузка нового плана
защищены локальным compensation rollback. Ошибка отката логируется отдельно
как CRITICAL. Отметка выполненной передачи включена в тот же runtime commit;
повтор её исполнения не передаёт груз второй раз.

## Узкие проверки

```bash
php tests/FleetFreeSpaceTest.php
php tests/FleetPlanTest.php
docker exec -w /var/www/html swoole_app php tests/FleetPlanSwooleTest.php
docker exec -w /var/www/html swoole_app php tests/FleetResumeCargoSwooleTest.php
docker exec -w /var/www/html swoole_app php tests/FleetResumeModesSwooleTest.php
php tests/FleetSpecialMissionsTest.php --export-special |
  docker exec -i -w /var/www/html swoole_app php tests/FleetFreeSpaceSwooleTest.php
```

Последняя команда создаёт отдельные Swoole Tables; с дополнительным `--mysql`
использует TEMPORARY SQL-таблицы и проверяет чтение сохранённых строк обратно.
Игровые строки не изменяются.
FleetPlanSwooleTest использует свежие отдельные Tables и запрещает SQL:
две доставки, оборона/экспедиция с редактированием в процессе, атака/САБ,
переработка, шпионаж с продолжением маршрута. Раунды боя — в Swoole Process.
Есть проверка handler → PlayerQueue → выполнение всех 12 этапов и отказа
переполненного payload без постановки события.

Ограничения: нет распределённой транзакции между runtime и MySQL или гарантий
доставки PlayerQueue; ACK не сообщает исход игрового действия. Прогноз встречи
не знает ещё не материализованные будущие участки цели; переход в другую
систему во время расчёта может потребовать новой команды владельца. Изменение
маршрута цели не даёт гарантии успешного бесконечного преследования.

## Исходный этап управления: исторические проверки

- 16 новых изолированных сценариев: технологии, видимость/самонаведение,
  остановка посреди перелёта/перехода, исчерпание, ручное продолжение, перехват,
  частичная передача, runtime failure + rollback/retry, идемпотентность передачи,
  редактор/stale version, ACK/PlayerQueue и монотонность времени удержания.
- Native Swoole: удержание, дозаправка, остановка, исчерпание; реальный saver,
  TEMPORARY MySQL и загрузка прочитанных SQL-строк обратно в отдельные Tables.
- Регрессии: специальные миссии (11), приглашения (7), отзыв (18), время
  возврата (8), топливо после боевых потерь (5 групп, включая 72 однородных
  и 15 смешанных вариантов), push и лимиты Fleet.
- Настоящий SPA snak1: редактор/окно отправки, desktop и 390/320 px,
  отказ невалидного плана без изменения игры, requestId/error/serverTime,
  callback завершился, горизонтальной прокрутки редактора нет.
- Полный реальный игровой сценарий удержание → дозаправка → продолжение
  на snak1 не запускался: логистика 0, подготовка аккаунта запрошена отдельно.
  Эти этапы проверены изолированно, в том числе с native Swoole/MySQL.

## Проверка составных маршрутов

- `FleetPlanTest`: 11 сценариев, включая все 11 действующих действий на prepare,
  частичные выгрузки, сохранение активной команды, смену владельца цели,
  rollback/retry/идемпотентность, откат созданной САБ и перестроение перехвата
  с сохранением метаданных следующих этапов.
- `FleetPlanSwooleTest`: 9 сценариев на настоящих отдельных Tables, SQL=0,
  в том числе две экспедиции на одной орбите с последующей сменой миссии:
  кредиты обеих находок доставляются домой, завершённое состояние очищается.
- Настоящий SPA snak1: отказ шпионажа без зонда; маршрут на текущей планете
  с двумя выгрузками 50% остатка и конечной выгрузкой; ACK/callback/ActualData;
  загрузка будущего плана и его редактирование во время обычного транспорта.
- Desktop и 390 px: перестановка этапов, выбор своей планеты и получение
  экспедиционной орбиты в другой системе для будущего этапа маршрута.
- Дальний browser-перелёт не ускорялся: проверка его полного физического
  завершения отдельно от изолированного исполнения маршрутов не проводилась.
