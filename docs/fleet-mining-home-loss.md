## Поведение

Потеря ресурсного дома не прекращает MINING у другого своего объекта.
Флот получает собственную резервную планету/луну; его срок, режим, состав,
груз и опыт сохраняются. Резерв топлива пересчитывается из места работы.
Выбранное finish=stay по-прежнему означает базирование у объекта добычи;
finish=return/отзыв возвращает к актуальному дому, а не к захваченной базе.

Ранее prepareDestination явно запрещал захват при таком зависимом добытчике.
Запрет снят после подключения экономического handoff, не просто удалён.

## Lifecycle и долговечность

1. Существующий world-barrier/recovery, расчёт стоянки/ухода последней охраны.
2. Только если охраны действительно нет — группировка удалённых MINING по siteId.
3. Общий settle до момента утраты дома для ВСЕХ работников каждого объекта.
4. Нулевая фаза rehome: новый дом/fallback и новый резерв в одном journal с
   актуальными носителями carry. Нет второго начисления груза/расхода.
5. Обычный commit потери старой базы получает свежие снимки ПОСЛЕ journal.
   Его rollback не может вернуть добытчику старый экономический before.
6. Новый контроль создаётся существующим CAPTURE; продолжается обычный scheduler.

MiningCheckpoints разрешает запись трёх уже существовавших полей приписки;
изменения схемы БД/размеров Tables нет. При восстановлении принимается целый
before либо after строки, но не произвольная смесь её полей. Смешанные
before/after РАЗНЫХ journal-строк обрабатывает существующий recovery.
В команде остаётся miningHomeLost с потерянным siteId, новой планетой и временем.
После успешного rehome повторная обработка не находит старую приписку.

Если собственной резервной планеты/луны вообще нет, удалённая работа
экономически закрывается до обычной pause=base. Эту ветку живой QA ниже
не проверяет: у обоих тестовых аккаунтов планеты существуют.
