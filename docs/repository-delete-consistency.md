# B039 — согласованность удаления runtime-записи

Исправлено 01.11.2026. Из production-кода изменён только BaseRepository.
Frontend, протокол, enum, SQL-схема и правила миссий не менялись.

## Причина и исправление

delete/discard удаляли индексные ссылки до непроверенного Table::del, затем
ставили DELETE marker без проверки set. Отказ мог оставить живую main row
без индексов либо удалить её без корректной отметки для MySQL. Ошибка более
поздней индексной группы также не возвращала уже изменённые ранние группы.

Дополнительно restoreDeletedRow сначала восстанавливал строку через add,
а отмену tombstone выполнял отдельным set: его отказ оставлял строку в памяти
с DELETE для следующего saver. Теперь:

- delete/discard используют removeRuntimeRow с before-образами строки, всех
  затронутых unique/non-unique групп (включая части) и старого marker.
- Результаты native del/set и чтения проверяются; при отказе возвращается
  именно before, включая отсутствие main row/marker и порядок ID в группах.
- Discard учитывает actual и attempted образы, если они различаются; чужая
  unique-ссылка не удаляется даже при отсутствии attempted main row.
- restoreDeletedRow выполняет восстановление и отмену DELETE в одной границе
  writeRuntimeRow с одним финальным marker. Обычный markForUpdate не изменён.
- Общий rollback переиспользован из B006. Если вернуть before не удалось,
  выдаются CRITICAL и исключение с исходной причиной, не ложный успех.

Это локальная компенсация одной записи, не SQL-транзакция всего действия
и не блокировка между процессами. Существующие B038 runtimeId и составные
ключи настроек сохранены. Публичные сигнатуры add/update/delete/discard/restore
не менялись; внутренний helper получил необязательный точный marker восстановления.

## Native-проверки

```bash
docker exec -w /var/www/html swoole_app php tests/RepositoryDeleteProbe.php --dev-readonly
docker exec -w /var/www/html swoole_app php tests/RepositoryWriteProbe.php --dev-readonly
docker exec -w /var/www/html swoole_app php tests/EntitySettingsWriteProbe.php --dev-readonly
```

Читается SELECT-снимок основной dev-БД в SQL READ ONLY транзакции. Отказы
вводятся только в локальных native Table-копиях, без основного worker,
EventLoop, SQL-записей или второго игрового сервера/мира.

До production-патча исходная матрица130 дала40 PASS/90 FAIL. Финальная
расширенная матрица —160/160 PASS, в том числе после последнего restart:

- DELETE main row и marker, unique и несколько non-unique групп, вторая часть.
- False/исключение до и после изменения; true с неверным after проверяется
  чтением. Неизменившаяся часть индекса не считается ошибкой только из-за no-op.
- Точные main/index/marker before-образы; отсутствующий/clean/dirty/DELETE marker.
- Restore: отказы основной строки, каждого индексного пути и финального marker;
  отсутствие незащищённой второй записи, повторные discard/restore.
- Отсутствующая main row, чужой unique-владелец, различающиеся actual/attempted
  группы и явная ошибка неудавшегося rollback. Последний CRITICAL ожидаем
  в отдельном журнале CLI-пробы, не в работающей игре.

Регрессии B006 —15 групп PASS; B038 —29/29 PASS, повторены после restart.
Статика: php -l для двух PHP-файлов, Python AST и scoped diff-check — PASS.

## Оставшиеся ограничения

- Main работает после финального restart; свежий startup/WS найдены в журнале,
  ERROR/CRITICAL/Fatal/PHP warnings0. Старые логи не очищались.
- SIGKILL, SQL crash-atomicity, конкурентные writers и автоматическое
  исправление уже повреждённых индексных групп этим не покрываются.
- Полное расформирование возвращает ресурсы/корабли и сохраняет AccountData
  до нескольких удалений. Отказ позднего шага требует компенсации всего
  действия, а не одного delete. Это статический архитектурный риск, отдельно
  записан в found-bugs.md; живой отказ с дублированием не вводился.
- Отдельно найден B042: transient PlayerQueue накапливает SQL markers,
  хотя не входит в обычный saver. Три CLI-события дали0 строк и3 DELETE markers
  при2048 выделенных слотах; переполнение в работающем мире не вызывалось.
  Это прежний дефект, не исправлялся расширением таблицы или новым протоколом.
- B029 (повторное использование максимального ID после restart) не исправлен:
  проверка отсутствия удалённого флота не доказывает долговечность генератора ID.
