# B038 — защищённая запись настроек эффективности

Исправлено 01.11.2026 на основном dev-сервере. Из production-кода изменены
только BaseRepository и EntitySettings. Frontend, протокол, SQL-схема,
игровые ID и формулы производства не менялись. B039 остаётся отдельным этапом.

## Причина

EntitySettings переопределял add/update и напрямую вызывал Table::set:
его false не проверялся, а успешная запись строки перед ошибкой marker
не компенсировалась. Поэтому строка и признак для saver могли расходиться.
Унаследовать общий add буквально нельзя: ключ Table вычисляется из
planet_id/entity_id, но в самой строке и SQL-таблице колонки id нет.

Общий writeRuntimeRow стал protected и получил необязательный runtimeId.
Обычные репозитории по-прежнему берут ID из row.id. EntitySettings передаёт
свой прежний ключ planet_id*1000+entity_id отдельно, без искусственной колонки.
Оба метода используют существующие проверки записи, чтения результата и
точное восстановление before-образа при отказе, включая отсутствие marker.
Сигнатуры публичных add/update/get и формат сохранённых ключей прежние.

## Native-диагностика

```bash
docker exec -w /var/www/html swoole_app php tests/EntitySettingsWriteProbe.php --dev-readonly
docker exec -w /var/www/html swoole_app php tests/RepositoryWriteProbe.php --dev-readonly
```

Проверяется SELECT-снимок текущей dev-БД в SQL-транзакции READ ONLY.
Инъекция отказов работает с локальными native Table-копиями одного CLI,
не меняет память основного worker и не запускает второй сервер/игровой мир.

До production-патча все24 сценария B038 провалили требование «исключение плюс
точный before-образ». После —24/24: add новой/существующей строки и update,
отказ основной строки/marker до записи, false/исключение после записи,
ложный успешный ответ без записи. Ещё5 проверок: корректный составной ключ
без id-колонки, чтение/update эффективности, правильный dirty marker,
неизменность остальных настроек, startup add(sync=false). Итого29/29 PASS,
в том числе повтор после окончательного restart. Регрессия B006 —15 групп PASS.

Живая проверка запускается так (нужна новая пустая собственная Selenium-сессия):

```bash
python3 tests/EntitySettingsLiveTest.py --dev --session ID --efficiency 70
python3 tests/EntitySettingsLiveTest.py --dev --session NEW_ID --efficiency 100
```

Live-тест сам не готовит SQL-fixture, не отправляет стройку/флот и не меняет
эффективность. Он использует приватные credentials QA из окружения контейнера,
не записывает их/токены в файлы или вывод. Чтение страниц может штатно создать
default-настройки, как и обычный клиент. Параметр — ожидаемое подготовленное
значение рудника1; у рудника2 ожидаются100%, planetId26 проверяется явно.

Повторы со старой авторизованной Selenium-сессией прервались и НЕ засчитаны:
raw-login сменил токен того же QA, диалог авторизации перекрыл форму входа
(WebDriver element click intercepted). Финальный повтор выполнен в новой
пустой сессии; в тест добавлен соответствующий guard. Клиент ради этого не менялся.

## Границы и состояние

- Это защита одной runtime-записи от отказа, не SQL-транзакция игрового мира,
  многопроцессная изоляция или гарантия на случай SIGKILL посреди записи.
- Native-отказ в живом worker намеренно не вводился. Нестандартный70% —
  offline SQL-fixture для startup/чтения; публичного UI/API изменения
  эффективности сейчас нет. Ветка update проверена native-диагностикой.
- Оба штатных stop сохранили мир. Финальный сервер работает; свежий startup
  найден в журнале, WebSocket запущен, ERROR/CRITICAL/Fatal/PHP warnings0.
- Старые журналы не очищались, массовых игровых изменений/отзыва сессий не было.
  Обе QA-настройки восстановлены. Реестр B039 не закрыт и его delete/discard
  не исправлялись вместе с B038.
