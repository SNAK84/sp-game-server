# B042 — SQL-отметки временной PlayerQueue

Исправлено01.11.2026 на основном dev. Клиент и WebSocket-протокол не менялись.

## Причина и изменение

`PlayerQueue::$tableName` пуст, в main она инициализируется без RepositorySaver.
Тем не менее наследуемые add/update создавали UPDATE marker, а после исполнения
delete оставлял DELETE marker с тем же ID. Временная очередь опустошалась,
но syncTable продолжала расти: обычный saver её не обслуживал.

При заполнении native Table следующий marker не записывался. Защищённый add
корректно отказывал, но новые команды становились недоступны из-за накопленных
служебных отметок уже удалённых событий. Это накопление с числом событий за
запуск, а не с числом одновременно ожидающих команд.

Минимальное изменение в BaseRepository:

- markForUpdate/markForDelete пропускают репозитории с пустым tableName;
- writeRuntimeRow не пишет и явный marker восстановления для такого репозитория;
- постоянные репозитории сохраняют прежние SQL markers и проверяемый rollback.

В текущем production-коде единственный репозиторий с пустым tableName — PlayerQueue.
У неё остаётся syncTable2048 с meta.last_id; ID не обнуляется при обработке
или отказе команды. Main row, индексы,512-байтная колонка, внешний буфер,
его квоты/TTL и B036 savePendingForRestart/restorePendingAfterRestart не менялись.
Restart-снимок читает реальные ready-строки и payload, не SQL markers.

## Отложенное ограничение и границы

Accounts::authByToken хранит один account.frame последнего запроса, а
EventLoop::sendActualData отправляет обновления только туда. Два соединения
одного аккаунта забирают подписку друг у друга. Это воспроизведено при нагрузке,
зафиксировано в found-bugs.md для отдельного протокольного этапа/Android.
Соединения, отправка ActualData и модель подписок здесь не переписывались.
Внешние payload всё ещё имеют штатные квоты/TTL; бесконечная очередь не обещается.
