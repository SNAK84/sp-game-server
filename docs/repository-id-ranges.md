# B029: долговечные диапазоны ID

01.11.2026. Только текущий backend `/opt/sp-game`; SPA и протокол не менялись.
Пользователь согласовал отдельную служебную таблицу и допустимые пропуски ID.

## Причина и контракт

Раньше `loadAll()` восстанавливал `last_id` из `MAX(id)` оставшихся строк.
Удаление самой новой сущности и restart уменьшали счётчик; следующий объект
получал старый ID. Это наблюдалось у Fleet81 и команд352+.
Также прежний `nextId()` делал `incr`, затем отдельное чтение meta: два worker
могли прочитать одинаковое более позднее значение. Неатомарный fallback удалён.

Теперь для числовых persistent BaseRepository применяется общий allocator:

1. Служебная InnoDB-таблица `repository_id_ranges(repository, high_water)`.
   При запуске граница только поднимается: учитываются загруженные ID,
   сохранённый high_water и native AUTO_INCREMENT существующей игровой таблицы.
2. До выдачи первого ID резервируется1024 номера. `SELECT ... FOR UPDATE`,
   увеличение high_water и commit выполняются отдельным непостоянным соединением.
   Оно не наследуется из master и не входит в транзакцию игрового checkpoint.
3. После commit диапазон публикуется в двух shared `Swoole\Atomic\Long`,
   созданных до fork. CAS выдаёт именно захваченный номер, без SQL на каждый ID.
   Refill сериализуется `flock`, открываемым заново, а не унаследованным FD.
4. При restart старый остаток не восстанавливается: новый диапазон начинается
   выше долговечной границы. При гибели worker между commit и публикацией
   теряются только номера, не уникальность. `setLastId` не понижает границу.
5. Ошибка SQL/commit/блокировки не разрешает выдачу неподтверждённого ID.
   Уже подтверждённый запас можно использовать без доступной MySQL.

Игровые таблицы, ID существующих сущностей, enum, API и WebSocket DTO не менялись.
Небольшой служебный счётчик не увеличивает строки игровых Swoole Table или
512-байтовый payload PlayerQueue. Временный PlayerQueue остаётся runtime-only,
но теперь возвращает непосредственно результат атомарного `incr`.
Репозитории с родительским ID, составные ключи и явные сохранённые ID не
перенумеровываются; public tokens боевых докладов имеют отдельную реализацию.
Явный `SpaceBattles::nextId()` защищён, хотя его default ID не AUTOID.

Гарантия относится к выделению ID через новый allocator, при сохранности
служебной таблицы и надёжном commit MySQL. Проверено
`innodb_flush_log_at_trx_commit=1`. Потеря/откат самой БД или ручная вставка
ID в обход allocator — другой контракт. Исторические коллизии до внедрения
нельзя однозначно восстановить и этот этап их не переписывает.

## Ссылки и граница внедрения

- FLEET-target хранит fleetId; доступность/владелец проверяются существующим
  rendezvous pipeline. Новая инкарнация не должна получать ID погибшего флота.
- Сенсорный контакт связан с Fleet/command ID, viewer/source/version; фаланга
  хранит снимок по Fleet ID. Это runtime-буферы, после полного restart пустые.
  Их DTO, сроки и правила раскрытия не менялись.
- Команды, replay/version guards и сохранённые сообщения/доклады не получают
  новых ссылок задним числом. Утечка или неверная адресация из-за прошлых
  совпадений ID не была доказана.
- Перед остановкой старого main обычный рейс QA132 выдал команды до433,
  хотя SQL MAX после очистки был406. Этот наблюдавшийся runtime floor433
  перенесён в служебную таблицу до запуска нового main. Остальные пространства
  инициализировались из текущих строк/native AUTO_INCREMENT.
