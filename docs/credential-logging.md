# B017 — секреты в диагностических логах

Исправлено и проверено 01.11.2026 (Москва) на основном dev-сервере.
Задача ограничена логированием: протокол, авторизация, игровые команды,
схема БД и сохранение состояния не перерабатывались.

## Причина и исправление

Вызовы Logger и console передавали полные результаты login, аккаунты,
запросы регистрации и сообщения WebSocket. В отдельных строках PIN и части
токена встраивались непосредственно в текст. Общая сериализация контекста
Logger не исключала секреты, а exception trace мог содержать аргументы функций.

В этих местах оставлены только диагностические поля: идентификатор подключения,
аккаунта/запроса, mode/action, результат, класс/место ошибки, длина входа и код
ошибки JSON. PIN, пароль, хеш пароля и токены туда не передаются. Тексты писем,
JSON сообщений в сети и обработка ответов не изменены.

Logger дополнительно рекурсивно маскирует чувствительные именованные поля
массивов и публичных/JsonSerializable-объектов перед обоими каналами вывода.
Обрабатываются варианты регистра и разделителей, вложенность ограничена;
исходные объекты и массивы не изменяются. В SQL Duplicate entry скрывается
значение, но сохраняются SQLSTATE/индекс. В trace остаются места вызовов без
аргументов. Это защита именованных полей и конкретного SQL-сообщения,
а не универсальное обнаружение секретов в произвольном тексте.

SPA использует статический `Message.toLog()` с разрешёнными
requestId/mode/action/status/errorCode. Полные payload и сообщения SyntaxError,
которые могут содержать фрагмент некорректного JSON, в console больше не выводятся.

## Проверки

- `php -l` для семи изменённых PHP-файлов и CredentialLoggerProbe — успешно.
- Python AST для live-проверки, проверка пробелов diff — успешно.
- `docker exec -w /var/www/html swoole_app php tests/CredentialLoggerProbe.php`:
  24 варианта чувствительных полей × 5 уровней Logger; вложенные массивы,
  stdClass/JsonSerializable, SQL Duplicate entry, цикл, trace с аргументами,
  неизменность входных данных — успешно. DEBUG включается только в этом CLI,
  настройки основного процесса не изменяются.
- `python3 tests/CredentialLoggingLiveTest.py --dev --session <owned-session>`:
  32 проверки пройдены; 206 записей console и 249 свежих строк Docker проверены,
  совпадений с известными тесту секретами — 0. Проверены и свежие файловые логи.
  Одна намеренно вызванная ошибка обработчика сопоставлена по requestId;
  неожиданных серверных ошибок и runtime-ошибок браузера нет.

Реальные операции на QA-аккаунте qaown_260924: login, запросы overview/fleets,
новое соединение с прежним токеном, logout, отказ старому токену, новый login;
в браузере — штатная форма входа, reconnect, logout/relogin и reload.
Ответы сохранили рабочий контракт, console не содержит проверяемых секретов.
Финальный SPA: Overview, WS OPEN, ожидающих callback 0, runtime-ошибок 0.

Контролируемые проверки: неверный токен, регистрация с заведомо невалидным
логином (без создания аккаунта/письма), неверный PIN, некорректный JSON,
ошибка типа входного параметра galaxy и дальнейшая работоспособность соединения.
Отдельные клиентские фикстуры проверяют parse-error и логирование offline-очереди;
их тестовый запрос в сеть не отправлялся. Обычный logout может сохранять старое
Data.token по отдельному B040 — этот пункт здесь не исправлялся.

Второй игровой сервер/мир не запускался, игровых приказов и изменения ресурсов
для этой проверки не было. Пароль/хеш/токены QA обрабатывались только в памяти
теста, в аргументы команд, отчёт и файлы результатов не записывались.

## Применение и ограничения

Основной сервер штатно остановлен с подтверждённым сохранением и запущен снова.
Начало текущего контейнера: `2026-10-31T23:19:13.315052802Z`
(01.11.2026 02:19 Москва). Свежий startup без ошибок, сервер работает.
Изменения уже применены; дополнительный перезапуск не требуется.

Старые логи не удалялись и могут содержать исторические секреты. Сессии остальных
игроков намеренно не отзывались; QA-токены менялись только штатным login/logout.
Необработанный произвольный текст в новых будущих log-call по-прежнему требует
проверки разработчиком. B038/B039, B040 и пересмотр протокола — отдельные этапы.
