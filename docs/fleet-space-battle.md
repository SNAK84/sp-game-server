# Пространственный бой: серверное ядро 3Б.1а

23.10.2026. Реализован и изолированно проверен бой Fleet ↔ Fleet. Это **не вся
миссия перехвата**: публичная отправка/редактор и кнопка «Перехват» не включены.
Изменения только в `/opt/sp-game`; SPA, старые движки, PlayerQueue и
RepositorySaver в этом подэтапе не менялись.

## Граница реализации

`FleetSpaceBattleService::engage()` принимает существующую ATTACK/FLEET-команду
уже прибывшего флота. Повторно проверяет владельцев, доступный контакт,
состояния и реальную встречу с допуском 0,05 единицы расстояния. Наблюдение
не телепортирует атакующего и не подменяет геометрию полёта.

Сейчас ядро допускает цель на внутрисистемном MOVE, OBSERVE или паузе с рабочей
цепочкой команд. Базирование, сама EXPEDITION, переход и активные другие действия
не допускаются. Это граница текущего server-only подэтапа, не утверждение о
готовности всех разрешённых игровых сценариев. Подключить их или явно определить
ограничения необходимо до публичного запуска.

## Хранение и расчёт

- `SpaceBattles`: собственный ID checkpoint и случайный battleId; не planetId
  и не ID целевого флота. 128 runtime-слотов по 262 144 байта состояния.
  Нативная таблица резервирует память заранее; объём не равен длине текущего JSON.
- `SpaceDebrisFields`: неподвижная POINT боя, металл/кристалл, battleId, timestamp.
  Отдельная таблица `space_debris_fields`, без вымышленных объектов или орбит.
- Оба репозитория используют обычный BaseRepository/RepositorySaver для MySQL.
  Инициализация создаёт только две новые таблицы; старые схемы не расширяются.
- `FleetBattleService`: один существующий TaskWorker pool/mailbox и общий лимит
  занятых workers для планетарных и пространственных раундов. TaskWorker только
  считает раунд; gameplay Tables меняет EventLoop. Новый боевой калькулятор,
  отдельный процесс на каждый корабль или второй пул не создавались.
- Сохранён прежний ритм раундов: не чаще одного нового раунда в секунду,
  прежние roundLimit/timeout/seed и защита от позднего ответа старого задания.
  Подкрепление входит в следующий ещё не переданный на расчёт раунд.
- Во время боя блокируются только флоты-участники. Планетарные ресурсы,
  очереди, оборона и луна этим боем не изменяются.

## Prepare, commit и компенсация

```text
встреча/проверки → snapshot участников → running → finished
→ prepare результата/архива → runtime commit → settled
→ publish доклада → активация маршрута атакующего → applied
→ flush связанных строк → SQL DELETE checkpoint → освобождение runtime-слота
```

Перед остановкой цели сохраняются только затрагиваемые fleet/command rows.
Вычисляются фактическая точка, оплаченный остаток топлива и достигнутый прогресс
участка. Старый MOVE становится pending с `pause=battle`, сохранённый маршрут
не удаляется. Непотраченное prepaid-топливо не исчезает при прерывании движения.

Группы, Factors, бонусы и опыт готовятся существующим адаптером атаки.
`battleWait.scope=space` не интерпретируется как planetId. Даже при потерянном
checkpoint такой wait остаётся fail-closed, не запускает новую планетарную атаку.

Результат заранее содержит точные before/after rows для флотов, групп кораблей,
команд, POINT-обломков и сообщений. При ошибке записи восстанавливаются уже
затронутые строки **и индексы**, включая случай отказа после фактического set.
Для живых восстановленных строк снимается DELETE marker. Исходная ошибка
сохраняется в логе; сбой самой компенсации логируется CRITICAL и сохраняет
блокировку боя. Это локальный механизм адаптера, не generic transaction framework.

Отказ SQL-подготовки архива не меняет gameplay. Если публикация доклада упала
после commit, `settled` остаётся заблокированным; retry публикует доклад и
продолжает маршрут, но не начисляет потери/опыт/добычу заново. Частично сохранённый
или неожиданно изменённый набор защищённых строк не перезаписывается догадками.

После `applied` checkpoint не копится в runtime навсегда. Его очистка проверяет
dirty/delete markers всех строк результата и текущих цепочек команд участников
(включая запущенный возврат). Затем ставит DELETE, сохраняя слот занятым до SQL ACK.
Отказ DELETE оставляет marker и слот для retry. Только подтверждённое удаление
освобождает runtime-строку. Доклад остаётся в прежнем архиве BattleReports.

## Результат боя

- Потери и опыт рассчитываются существующим калькулятором. Опыт — сумма группы,
  распределённая поровну по кораблям; средний опыт флота пересчитывается.
- Бак выжившего уменьшается по доле оставшейся **вместимости**, не по доле числа
  кораблей. Топливо из бака в добычу не попадает.
- Физический груз выжившего при потере вместимости пропорционально ограничивается
  свободным трюмом после бака. Переполнение не сохраняется.
- Победитель любой стороны забирает до 50% металла/кристалла/дейтерия уничтоженных
  участников проигравшей стороны, в пределах оставшейся вместимости победителей.
  Используется существующий алгоритм распределения добычи. Валюты не включены
  в захват: их отдельное правило здесь не вводилось.
- Обломки по существующему `FleetDebrisPercent` остаются в POINT. Луны в пространстве
  не образуются. Поиск полей не использует ограниченный 2048 байтами общий ID-list
  индекс системы; проверены 300 отдельных полей в одной системе.
- Сохраняются исторические имена/участники, обычный публичный боевой доклад и два
  существующих сообщения. EventLoop использует обычную доставку ActualData.
- Выжившие атакующие продолжают свою существующую очередь. Сам default return
  должен добавить будущий launcher; ядро не выдумывает его за игрока.
- Выжившие защитники и их подкрепления остаются на паузе до команды игрока.
  Принятые, но не успевшие войти в раунд подкрепления не получают потерь/опыта.
- Владельцы двух сторон знают точку текущего боя для подкреплений. Третий игрок
  не получает такое наблюдение; после боя это не становится скрытым сопровождением.

## Оставшиеся риски и следующий подэтап

- Общая проблема B006 записана отдельно. Компенсация нового адаптера не делает
  автоматически безопасными другие FleetControl pipelines.
- При отказе самой компенсации требуется диагностика заблокированного боя.
  Автоматическое снятие защиты с неизвестного partial state запрещено.
- Локальный runtime commit не даёт crash-atomic SQL flush разных repositories.
  Частичный restore остаётся архитектурным риском. RepositorySaver не менялся.
- Нет нового межпроцессного transaction lock: используется текущий последовательный
  EventLoop. Конкурентные writers и нагрузка множества боёв не доказаны этими тестами.
- Слоты ограничены; длительная неисправность SQL удерживает applied checkpoints
  до ACK. Это безопасный backpressure, а не бесконечная ёмкость.
- `SpaceDebrisFields::inSystem()` сканирует runtime-поля; очистку пустых полей и
  нагрузку нужно проверить с реализацией реальной переработки.
- В 3Б.1б ещё нужны ATTACK/FLEET launcher и MOVE по наблюдению, политика потери
  контакта/сообщение, default return, полёт подкреплений, реальная POINT-переработка,
  UI выбора целей/перехвата и browser-тест. Порог технологии для альтернативного
  поведения при потере контакта пока не утверждён.
- Этапы обследования/захвата/добычи объектов 4–5 не начинались.
